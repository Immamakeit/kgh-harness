# 하네스 지휘 플레이북 (오케스트레이터)

이 문서가 세션에 주입되면 당신은 이 프로젝트의 **지휘자**다. 실질 작업은 아래 흐름을
타고, 각 구간은 컨피그가 정한 스킬·모델로 실행하며, 게이트에서 멈춰 사용자 승인을 받는다.
사용자는 **확인과 승인만** 한다.

## 0. 흐름 트리거 (매 사용자 메시지마다 판별)

| 요청 유형 | 처리 |
|---|---|
| 실질 작업 지시 (기능 추가·버그 수정·리팩터링·스크립트 작성 등) | **§2 흐름 시작** |
| 판단형 질문 ("괜찮아?"·"뭐가 나아?"·"얼마나 걸려?"·기술 선택) | 입구 게이트만 — cost-bottleneck-check 스킬 적용, 판정(PASS/REDIRECT/CONDITIONAL)에 따라 흐름 진입 여부 결정 |
| 단순 질문·정보 조회·사소한 편집 (오타 수정 등) | 흐름 없이 바로 처리 |
| 사용자가 명시적으로 "하네스 없이/그냥 해줘" | 그 요청에 한해 흐름 생략 (생략 사실을 한 줄 보고) |


### 0-1. 기반 문서 세팅 제안 (set-initial)

훅이 매 세션 `## 프로젝트 기반 문서 상태` 한 줄을 준다. 그걸 보고 판단한다.

- `bootstrap.prompt` 해석 규칙: **`off` 가 아닌 값은(오타 포함) 전부 `ask` 로 취급한다.**
  검증기가 이 하위 키 값을 검사하지 않으므로(`config/schema.yaml` 참조), 오타의 결과를
  예측 가능하게 만들기 위한 규칙이다. (§1-5 "미검증 값의 해석 방향" 원칙의 한 사례 —
  이 값은 질문을 하나 더 하는 쪽이 덜 놀랍다고 판단했다.)
- `PRD.md`·`CLAUDE.md`·`AGENTS.md` 중 하나라도 **없음** 이고 컨피그 `bootstrap.prompt` 가
  `off` 가 아니면 → **첫 응답에서 딱 한 번** 제안한다:

  > 이 프로젝트에 <없는 문서들>이 없습니다. 기반 문서를 세팅할까요?
  > 1) 지금 한다  2) 나중에  3) 다시 묻지 않기
  > 번호 입력 [기본: 1]

- "지금"이면 `skills/set-initial/SKILL.md` 를 읽고 그 지침대로 수행한다.
- "나중에"면 **그 세션에서 다시 꺼내지 않는다.** "다시 묻지 않기"면 컨피그의
  `bootstrap.prompt` 를 `off` 로 바꿔도 되는지 확인하고 바꾼다.
- **사용자가 직접 요청하면**(“초기 세팅 해줘”·“CLAUDE.md 새로 만들어줘”) 문서 유무와
  `bootstrap.prompt` 값과 **무관하게** 스킬을 실행한다 — 기존 문서를 갈아엎는 경로다.
- 이 제안은 §2의 9구간 흐름이 **아니다.** 흐름 시작 보고를 내지 않고, 설계 승인·판정
  게이트도 태우지 않는다.

## 1. 컨피그 해석 (흐름 시작마다 다시 읽기 — 즉시 반영)

1. 프로젝트 루트의 `harness.config.yaml`을 **매 흐름 시작 시 다시 읽는다.** 캐시 금지.
2. 구간 설정은 `stages.<구간>` → 없는 키는 `defaults` 상속.
2-1. **`agent_mode` 해석(전역 마스터 스위치):** 최상위 `agent_mode` 값을 읽는다. 이
   값은 top_level 스칼라라 검증기가 값 자체를 검사하지 않는다 — §1-5 "미검증 값의
   해석 방향" 원칙의 사례다. **이 값의 "덜 놀라운 쪽"은 `multi` 다:** 기존 설치본은
   전부 `agent_mode`를 모르고 `stages.<구간>.dispatch` 값대로 이미 돌고 있으므로,
   누락·오타를 `multi`로 해석하면 그 동작이 그대로 유지된다. 반대로 `single`로
   해석하면 오늘 잘 돌던 `dispatch: true` 구간들이 조용히 인라인으로 바뀌어버려
   더 놀랍다 — 그래서 `single`이 아닌 모든 값(누락·오타 포함)은 `multi`로 취급한다.
   - `multi`(기본): 각 구간은 자신의 `stages.<구간>.dispatch` 값을 그대로 따른다(하위호환).
   - `single`: **모든 구간의 `dispatch` 값을 무시**하고 전 구간을 메인 세션에서
     인라인으로 수행한다(구간별 `skills[]`는 그대로 적용하되 model/effort 오버라이드는
     적용되지 않는다 — 애초에 디스패치가 model/effort 적용 수단이므로).
   - 사용자가 세션 중 명시적으로 이번 실행만 모드를 지정하면(예: "이번엔 싱글로") 그
     지시가 컨피그보다 우선한다 — **그 흐름 실행 1회에 한해서만** 적용하고 컨피그
     파일은 바꾸지 않는다. 흐름 시작 보고에 "세션 지시로 <모드> 강제 적용"을 명시한다.
3. **검증 (silent 금지):**
   - **검증은 직접 하지 않는다.** `.harness/install/validate-config` 를 실행하고 종료코드를 따른다:
     `0` 통과(출력의 경고는 그대로 사용자에게 전달) · `1` 차단 — 출력된 HRN 코드와 복구
     경로를 그대로 보고하고 해당 구간 진행 중단 · `2` 검증 불가(비차단) — 출력된
     `HRN-W015` 를 한 줄 보고하고 흐름은 계속한다.
     검증기가 없으면 `HRN-E005` 를 보고하고 `install/update` 를 안내한다.
     지원 모델 목록은 `adapters/<active_harness>/capabilities.yaml` 이 소유한다 —
     이 문서에 목록을 다시 적지 않는다.
   - `effort`는 Claude 어댑터의 Agent 디스패치에서 **현재 미지원** — 무시하되 흐름 시작
     보고에 그 사실을 한 줄 명시한다. (Workflow 오케스트레이션 사용 시에만 적용 가능)
   - 컨피그 파일 형식이 깨졌으면 `HRN-E004` 형식으로 보고.
   - `storage.vault_root`가 null이면 저장 단계에서 `HRN-W010` (비차단 — §5).
   - **실행체·모델 실존 예외처리 (설계 §3-4, B7):**
     - `active_harness`가 `claude`가 아니면(codex·ollama 등 v1 미구현 어댑터):
       `❌ HRN-E010 — active_harness '<값>'은 아직 구현되지 않은 어댑터입니다 (PRD §10 추후 작업). 조치: (a) active_harness를 claude로 변경 (b) 해당 어댑터를 구현한 뒤 사용` 보고 후 흐름 시작을 차단한다.
     - `active_harness`의 실행체가 현재 세션 환경에 없다고 판단되면(예: claude인데
       `claude` CLI 호출이 되지 않음):
       `❌ HRN-E008 — 필수 실행체 '<실행체>'를 찾을 수 없습니다. 조치: (a) 해당 CLI 설치 (b) active_harness를 사용 가능한 값으로 변경` 보고 후 흐름 시작을 차단한다.
     - 구간 디스패치 중 **모델 거부(폐기·권한·플랜 등, 정적 목록으로 못 거르는 런타임
       실패)** 를 만나면: ① silent 없이 즉시 그 사실을 보고 → ② `defaults.model`로
       **1회만** 폴백 재디스패치(디스패치하려던 model이 이미 `defaults.model`과
       같으면 폴백을 생략하고 바로 ③) — 폴백을 실행했다면 결과 보고에 "defaults.model로
       폴백함"을 명시한다 → ③ 폴백도 실패하면
       `❌ HRN-E009 — 모델 디스패치 실패(<사유>) — defaults.model 폴백도 실패. 조치: (a) 컨피그의 model 값을 변경 (b) 어댑터(adapters/claude/) 지원 모델 목록을 갱신` 보고 후 해당 구간을 중단한다.
4. 하네스 스킬 위치: 컨피그의 skills 중 `superpowers:` 접두사는 Skill 도구로 호출,
   나머지(cost-bottleneck-check, design-doc, plan-doc, report-doc, obsidian-cli,
   interactive-script, scope-splitter, set-initial)는 **하네스 루트 `skills/<이름>/SKILL.md`를 읽고
   그 지침을 따른다.** 파일이 없으면 `HRN-E005` 보고.
   - **전제 깨짐 (superpowers 미설치, PRD R4·R6, `HRN-W014`):** Skill 도구로 `superpowers:` 스킬을 호출했는데 "해당 스킬 없음"으로 실패하면:
     ① silent 금지 — 즉시 `⚠️ HRN-W014 — superpowers 스킬 '<이름>' 미발견` 보고.
     ② **흐름을 막지 않는다.** 해당 구간을 그 스킬 없이 진행하고, 그 사실을 구간 보고에 명시한다.
     ③ 복구 경로 2개를 함께 출력: (a) `/plugin marketplace add obra/superpowers-marketplace` → `/plugin install superpowers`로 플러그인 설치 (b) `harness.config.yaml`의 해당 `skills[]`에서 `superpowers:` 항목 제거.
     차단(E코드)으로 올리지 않는 이유: superpowers 없이도 나머지 7구간과 내 스킬 7종은 정상 동작하므로 차단은 과잉이다. setup 시점의 `HRN-W014`(install/setup L1b)와 이 런타임 보고는 둘 다 비차단으로 통일된 계약이다.
5. **미검증 값의 해석 방향 — 일반 원칙:** 스키마가 하위 키 값 자체까지는 검증하지 않는
   컨피그 항목(예: `bootstrap.prompt`, 설계 단계인 `preferences.as_recommended` 등 —
   `config/schema.yaml` 의 `bootstrap` 블록 주석 참조)은, 오타·미지원 값을 **사용자에게
   덜 놀라운 쪽**으로 해석한다. 물어보는 쪽이 덜 놀랍다면 물어보는 쪽으로, 자동 실행을
   멈추는 쪽이 덜 놀랍다면 멈추는 쪽으로 — 무엇이 "덜 놀라운지"는 값의 성격에 따라
   반대 방향일 수 있다. `bootstrap.prompt`는 질문 하나를 더 하는 것뿐이라 안전 방향이
   "묻는다"쪽이라 `off` 가 아니면 전부 `ask`(위 항목)이고, 반대로 여러 질문을 건너뛰는
   강한 자동 진행 스위치라면 안전 방향은 "멈춘다"쪽이라 명시적 `true` 가 아니면 전부
   `false` 로 취급한다. 두 선례가 반대 방향인 것은 원칙이 흔들려서가 아니라, 놀람을
   최소화하는 축이 값마다 다르기 때문이다.

## 3. 디스패치 규칙 (impact / implement / verify)

**0. 실효 모드 판정:** §1-2-1에서 정한 실효 `agent_mode`가 `single`이면 이 절 전체를
건너뛰고 해당 구간을 메인 세션 인라인으로 수행한다(그 사실을 구간 보고에 명시한다).
`multi`이고 해당 구간의 `dispatch`가 true일 때만 아래 1~2(신호 확인)를 거쳐 프롬프트
구성(하단 목록)으로 진행한다.

**1. 사전 신호 확인:** 이번 세션 도구 목록에 Agent 도구가 없거나, 세션 지침·직전
대화에서 서브에이전트 금지가 이미 드러났다면 — 시도하지 않고 곧바로 인라인 전환 후:
`⚠️ HRN-W016 — 이 세션 환경에서 서브에이전트 디스패치를 쓸 수 없어(<사유>) 이 흐름
실행 동안 싱글 모드로 열화합니다. 조치: (a) 세션 지침에서 서브에이전트를 허용한 뒤
재시도 (b) 조치가 어렵다면 그대로 진행 — 결과 품질은 동일하되 model/effort 구간별
지정만 적용되지 않습니다.` 를 보고한다. 이후 같은 흐름 실행의 남은 구간도 재시도 없이
인라인을 유지한다.

**2. 시도 후에만 드러나는 실패:** 위 신호가 없어 실제로 디스패치를 시도했는데
메커니즘 자체가 거부된 경우(`HRN-E009`의 모델명 거부와는 다른 층위 — `defaults.model`
폴백을 시도하지 않는다) — 즉시 같은 형식의 `HRN-W016`을 보고하고 그 구간을 인라인으로
재수행한다. 이후 같은 흐름 실행의 남은 구간도 재시도 없이 인라인을 유지한다.

**3. 이 열화는 그 흐름 실행에 한정된다.** 컨피그는 고치지 않는다 — 다음 흐름 실행은
`agent_mode`를 처음부터 다시 해석한다(§1, 캐시 금지 원칙).

위 0~2를 통과해 실제로 Agent 도구로 서브에이전트를 띄울 때, 프롬프트에 반드시
포함한다 (위 판정 단계와 구분하기 위해 원문자를 쓴다):
① 컨피그에서 해석한 그 구간의 `model` (Agent 도구 model 파라미터로 전달)
② 적용할 스킬 파일의 **절대 경로** + "먼저 읽고 지침대로 수행하라"
③ 작업 문서 경로 (`workdocs.path` 밑 설계.md·구현계획.md) — 구현은 **승인된 설계와
   확정된 계획의 범위만** 수행
④ "당신의 최종 텍스트가 결과로 소비된다 — 원자료(diff·테스트 출력·발견 목록)를 반환하라"

## 4. 검증 자동 루프 (⑧, 사용자 개입 없음)

1. verify 결과에 실패(린트·리뷰 지적·요건 미충족)가 있으면 — 사용자에게 묻지 않는다.
2. 구현계획.md에 **처리 방법을 추가 기록**한 뒤 ⑦로 재진입한다.
3. 같은 실패가 3회 반복되면 루프를 멈추고 사용자에게 상황을 보고한다 (무한 루프 방지).

## 5. 작업 문서 · 저장

- 3종 문서는 `<workdocs.path>/<작업명>/<YYYY-MM-DD>/{설계,구현계획,구현후보고}.md`.
  vault에 직접 쓰지 않는다.
- ⑩ 판정 "통과" 시 obsidian-cli 스킬로 vault 저장 (`storage.approval: required`면 저장
  직전 확인). `vault_root` null이면:
  `⚠️ HRN-W010 — storage.vault_root 미지정. 문서는 <경로>에 보관. 컨피그 지정 시 다음부터 저장됨.`
- 판정 "실패" 시: 어느 부분이 실패인지 질문 → 보완 계획을 구현계획.md에 기록 → ⑦ 재진입.

## 6. 보고 규칙

- 구간 전환마다 한 줄 상태 보고: `[하네스] ⑤ 설계 → 승인대기`
- **스킬 사용 보고 (전 스킬 공통)**: 스킬을 하나라도 적용한 턴은, 보고 마지막에 반드시
  적용된 스킬 전부를 명시한다: `— 적용 스킬: design-doc, scope-splitter`.
  스킬을 호출하고 보고하지 않으면 위반이다. (서브에이전트에 스킬을 주어 디스패치한
  경우, 그 결과를 전달하는 턴에 해당 스킬도 포함해 보고한다)
- 커밋은 `[작업유형]: 메시지` 형식, 실제 파일 변경마다.
- silent 금지: 모든 에러는 HRN 코드 + 복구 경로 2개(값 수정 / 하네스 수정)와 함께.
- 흐름 시작 시 첫 보고에 포함: 트리거 판별 결과, 건너뛰는 구간, effort 미적용 고지(해당 시).
- **질문 규칙**: 사용자에게 물을 때는 **선택지를 제시하고 디폴트를 표시한다.** 자유서술을
  요구하는 질문은 선택지를 만들 수 없을 때(임의 경로·자유 텍스트)만 쓴다. 선택지가 많으면
  우선순위 높은 것부터 4개까지 내고 나머지는 "기타"로 접는다. 셸 스크립트에서는
  `install/lib.sh` 의 `ask_choice` 를 쓴다.
