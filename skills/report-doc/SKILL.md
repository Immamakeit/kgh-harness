# Report-Doc (구현후보고 굳히기 + 판정 요청)

## 핵심 원칙

보고서는 **실물로 확인된 사실**만 담고, **나쁜 소식일수록 그대로** 적는다.
사용자는 보고서만 읽고 "통과/실패" 한 단어로 판정할 수 있어야 한다.

## 1. 실물 대조 (작성 전 의무)

- 보고서에 적을 모든 주장(파일 신설·수정·커밋·테스트 결과)을 **실물로 확인**한다:
  워킹트리 diff, 실제 파일, git log, 테스트 출력.
- 작업 기록과 실물이 **불일치하면 보고서를 쓰지 않는다** — 불일치 내역을 표로 정리해
  표면화하고 사용자 확인을 기다린다. 존재하지 않는 것을 근거로 쓰면 허위 보고다.

## 2. 비은닉 (검증 결과 기재 규칙)

- 검증 3항목(린트 / 코드리뷰 / 요건 충족)을 **각각** 기재한다.
- **"실행 못 함"은 "통과"가 아니다.** 도구 미설정·환경 제약으로 실행하지 못한 검증은
  그 사유와 함께 "실행 못 함/미검증"으로 명시하고, 어디서 확인 가능한지 적는다.
- 스킵·실패·미검증 항목을 요약에서 누락시키지 않는다. 특히 이번 변경의 영향권에
  있는 미검증 경로는 반드시 짚는다.

## 3. 문서 굳히기

- 위치: `.harness/work/<작업명>/<YYYY-MM-DD>/구현후보고.md` (설계.md·구현계획.md 옆.
  컨피그 `workdocs.path` 우선. vault 직접 쓰기 금지 — 저장은 판정 통과 후 obsidian-cli 몫)
- 템플릿: 구현후보고 템플릿 준수 — 변경 요약 · 커밋(`[작업유형]: 메시지` 형식) ·
  검증 결과(3항목) · 직접 확인 시나리오 · 사용자 판정 + frontmatter + ≤10자 요약.
- status: `보고`.

## 4. 직접 확인 시나리오

- 사용자가 **순서대로 따라 하면 바로 확인되는** 단계로 쓴다. 각 단계에 **기대 결과**를 단다.
- 정상 경로 1개 이상 + 부정 케이스(401·404 등) 포함.
- 가능하면 사용자 눈높이 수단(브라우저·화면)을 우선하고, 없으면 복붙 가능한 명령(curl)으로.

## 5. 판정 요청 (응답 종료 형식)

최종 응답은 반드시 이 구조로 끝난다:

> **판정해주세요 — "통과" 또는 "실패"만 입력하시면 됩니다.**
> - 통과 → 산출 문서 3종을 vault에 저장하고 마무리합니다.
> - 실패 → 어느 부분이 실패인지 여쭙고, 보완 계획을 세워 구현 단계로 재진입합니다.

- 판정을 복잡하게 만들지 않는다 — 조건·단서가 있으면 보고서 본문(검증 결과)에 쓰고,
  판정 요청 자체는 통과/실패 이지선다로 유지한다.

## 완료 기준 (제출 전 자가 점검)

- [ ] 모든 주장이 실물 확인됨 (불일치 시 보고 중단·표면화했는가)
- [ ] 검증 3항목 각각 기재, "실행 못 함"이 "통과"로 둔갑하지 않음
- [ ] 구현후보고.md가 `.harness/work/<작업명>/<날짜>/`에 템플릿대로 존재
- [ ] 직접 확인 시나리오: 단계별 + 기대 결과 + 부정 케이스
- [ ] 최종 응답이 "통과/실패만 입력" 구조로 종료
- [ ] 사용 보고 (하네스 공통 규칙): 그 턴 보고 마지막에 `— 적용 스킬: report-doc`
      (여러 스킬 적용 시 쉼표로 병기). 미보고 = 위반
