# Branch-Strategy (GitHub 원격 브랜치 보호)

## 핵심 원칙

**이 스킬은 남의 GitHub 계정 설정을 바꾼다.** 로컬 git hook이 아니라 원격 서버
상태를 고치는 파괴적 조작이다. set-initial의 규율(파괴 전 안전장치·질문 계약·
사후 통보 금지)을 그대로 승계하되, 대상이 파일이 아니라 **원격 API 상태**이므로
되돌릴 길은 git이 아니라 **GET 스냅샷**이다.

**이 스킬은 `CLAUDE.md`를 쓰지 않는다.** 브랜치 절 문서화는 `set-initial` Q3의
소유다. 불일치를 발견하면 보고만 하고, 고치거나 set-initial을 대신 호출하지 않는다.

**classic Branch Protection API(`PUT .../branches/{branch}/protection`)만 쓴다.**
신형 Repository Rulesets API(`POST .../rulesets`)는 v1 범위 밖이다 — 더 유연해
보여도 실측 없이 손대지 않는다. "rulesets가 최신이니 그쪽으로 하자"는 유혹이
들면 §비대상을 다시 읽는다.

대응 절을 1:1로 묶는다 — 규칙이 근거 없이 창작되지 않았음을 보이기 위함이다.

## 0단계 — 전제 점검 (건너뛰기 금지, 실패 시 즉시 차단)

순서를 지킨다 — 뒤 단계의 판정은 앞 단계 통과를 전제한다.

| # | 점검 | 실패 시 | 코드 |
|---|---|---|---|
| 1 | `gh` 설치 여부 (`command -v gh`) | 차단 | `HRN-E008`(재사용) |
| 2 | `gh auth status` 성공 | 차단 | `HRN-E011` |
| 3 | `gh api -i /user`의 `X-Oauth-Scopes` 헤더에 `repo` 포함 | 차단 | `HRN-E012` |
| 4 | `git remote get-url origin` 존재 + 호스트가 `github.com` | 차단 | `HRN-E013` |
| 5 | `gh api repos/{o}/{r} --jq .permissions.admin` == `true` (조회 실패 포함) | 차단 | `HRN-E014` |
| 6 | 통과 시: 현재 보호 상태 **GET** → 스냅샷 저장 | — | — |
| 7 | 협력자 수 조회 (`.../collaborators`) — 기본값 결정에 사용 | 조회 실패 시 1명으로 열화 + 고지 | — |

**git 원격 확인(4번)은 로컬 `git remote` 명령으로만 한다.** `git ls-remote` 등으로
실제 네트워크를 두드리지 않는다 — 원격이 실존하는지 확인할 필요가 없다(존재 여부는
5번 `gh api repos/{o}/{r}` 조회가 이미 판정한다). 불필요한 네트워크 호출을 피한다.

각 차단은 **관찰한 사실을 그대로 인용**한다 — 결론만 적지 않는다:

```
❌ HRN-E012 — GitHub 토큰에 repo 스코프가 없습니다.
   관찰: `gh api -i /user`의 X-Oauth-Scopes 헤더 실제값 — "gist, read:org"
   조치 1: gh auth refresh -s repo 로 스코프 추가 후 재시도
   조치 2: repo 스코프를 가진 PAT로 재로그인
```

`E013`은 "원격 없음"과 "GitHub 아님"을 하나로 묶는다(이후 절차가 동일하게 "적용 대상
없음"으로 수렴하므로). `E014`는 "admin 아님"과 "조회 자체가 안 됨"(403/404)을 묶는다.

6번에서 저장하는 스냅샷 경로: `<workdocs.path>/branch-strategy/<날짜>/before-protection.json`
(워크플로 밖 독립 실행이면 현재 작업 디렉토리 하위 동일 구조). 보호가 없으면(404)
그 사실 그대로("보호 없음, 404") 저장한다 — 되돌리기(§4)의 근거가 된다.

7번 조회 실패(권한/네트워크)는 **가장 보수적인 값(협력자 1명, 승인수 기본 0)으로
열화**하고 그 사실을 질문 전에 한 줄 고지한다 — silent 열화 금지.

## 1단계 — 위협 모델 고지 (과장 금지)

질문 전에 반드시 다음 네 가지를 사용자에게 그대로 보여준다. **하나라도 생략하거나
과장(예: "이걸 켜면 아무도 못 건드립니다")하면 위반이다:**

1. 공개 저장소라도 협력자로 초대되지 않은 사람은 애초에 push가 불가능하다 —
   "지나가던 개발자의 직접 푸시"는 이 규칙 이전에도 불가능하다.
2. 이 규칙이 실제로 막는 것은 (a) 소유자 본인의 실수 (b) 포크 PR의 무단 병합
   (c) force push·브랜치 삭제 — 이 세 가지다.
3. `enforce_admins: false`인 상태에서 admin이 직접 push하면 **경고만 찍히고
   push는 통과한다.** "막는다"는 admin에게는 완전하지 않다.
4. 협력자가 1명(owner)뿐이면 `required_approving_review_count ≥ 1`은 자기 PR을
   자기가 승인하지 못하게 막는 **자기잠금 함정**이 된다.

이미 보호가 적용돼 있으면(0단계 6번 GET이 200) 그 값을 함께 보여주고, 지금 고르려는
값과 **같으면 Q1 이전에 그 사실을 고지**한다("이미 적용된 값과 동일합니다 — 그래도
다시 적용할까요?") — 멱등적 재적용이 무의미한 반복이 되지 않게 먼저 알린다.

## 질문 계약 (번호 · 직접 입력 · 건너뛰기 · 기본번호 — 4요소 전부)

set-initial과 같은 규율. 예외 없음 — 이 스킬의 모든 질문에 자유서술 예외를 두지
않는다(선택지를 만들 수 없는 질문이 없으므로).

**번호는 표시 순서와 항상 일치한다.** 추천을 앞으로 재배열했으면 번호도 다시
매긴다 — 플레이북 §6 질문 규칙과 같은 규율이다.

### Q1 — 마스터 스위치

협력자 수(0단계 7번)로 기본번호가 갈린다. 예시(협력자 1명 기준):

```
현재 상태: main 브랜치 보호 없음
협력자: 1명 (testowner, admin)

어떤 조합을 적용할까요?
  1) 표준 — PR 필수 · 승인 0명(협력자 1명 기준) · force-push 금지 · 삭제 금지 · 관리자 예외 있음 (추천)
  2) 최소 — force-push·삭제만 금지, PR은 강제하지 않음
  3) 엄격 — 표준 + 관리자도 규칙 적용(enforce_admins) — 협력자 2명 이상일 때만 권장
  4) 직접 입력 (세부 항목을 하나씩 정한다)
  5) 건너뛰기 (미리보기만 보고 적용 안 함)
번호 입력 [기본: 1]:
```

- 협력자가 2명 이상이면 1번 문구의 "승인 0명"이 "승인 1명"으로 바뀐다.
- **"엄격"을 협력자 1명 상태에서 고르면** 즉시 경고하고 재확인한다:
  `협력자가 본인뿐이라 enforce_admins를 켜면 앞으로 어떤 변경도 PR 승인자를 구하지
  못해 병합이 막힙니다. 그래도 진행할까요? [Y/N, 기본 N]`
- "직접 입력"을 고르면 하위 항목을 같은 4요소로 순서대로 묻는다: PR 필수 여부 →
  승인 인원수(자유 입력, 범위 0~6 안내) → force-push 허용 여부 → 삭제 허용 여부 →
  enforce_admins 여부. 이미 정해둔 안전 기본값이 있어도 이 경로에서는 전부
  다시 확인 대상이다 — 사용자가 명시적으로 "직접"을 골랐기 때문이다.
- **묻지 않고 항상 넣는 값** (선택지로 낼 가치가 없음): `dismiss_stale_reviews: false`,
  `require_code_owner_reviews: false`, `required_status_checks: null`. "직접 입력"
  경로에서도 이 세 값은 노출하지 않는다.

### Q2 — 최종 적용 확인 (미리보기 필수)

Q1(및 하위 질문) 응답을 **실제 `gh api` 요청 바디로 조립해 그대로 보여준 뒤에만** 묻는다:

```
아래 설정을 testowner/testrepo 의 main 에 적용합니다:
  PUT /repos/testowner/testrepo/branches/main/protection
  { "required_pull_request_reviews": {"required_approving_review_count": 0,
    "dismiss_stale_reviews": false, "require_code_owner_reviews": false},
    "enforce_admins": false, "allow_force_pushes": false, "allow_deletions": false,
    "required_status_checks": null, "restrictions": null }

적용할까요? [Y/N, 기본: N]
```

기본은 **N**이다 — 명시적 승인 전에는 원격 상태를 바꾸지 않는다.

**사용자가 Q1 선택과 최종 확인을 한 메시지에 미리 줘도**(예: "1번으로 하고 Y로
진행해줘") 이 미리보기 텍스트는 반드시 그대로 출력한 뒤에 적용한다 — 생략하지
않는다. 사전 승인은 "확인 절차를 건너뛰어도 된다"가 아니라 "확인에 대한 답을
미리 알려준다"는 뜻이다.

## 2단계 — 적용

- `PUT .../protection`은 GitHub API 자체가 **전체 치환**이라 멱등적이다. 매번
  완전한 desired-state 객체를 보낸다 — 별도 상태 비교 로직 불필요.
- 표준/엄격 프리셋에는 `PATCH /repos/{o}/{r}` (`delete_branch_on_merge: true`)도
  포함한다. 최소 프리셋에는 포함하지 않는다(브랜치 보호와 무관).
- 여러 요청 중 일부만 실패하면(예: protection은 성공, `delete_branch_on_merge`
  PATCH만 실패) **경고, 비차단** — 성공분은 이미 반영됐다:
  `⚠️ HRN-W019 — 브랜치 보호 설정 일부만 적용됐습니다. 성공: PUT .../protection.
  실패: PATCH .../repos/{o}/{r} (<실패 사유>). 조치 1: 실패 항목을 GitHub 웹에서
  수동 설정 조치 2: 잠시 후 이 스킬을 다시 실행(멱등적 재적용)`

## 3단계 — set-initial 경계 확인

적용 완료 후 대상 프로젝트의 `CLAUDE.md`를 읽는다:

- 브랜치 절이 있고 방금 적용한 값과 문면이 다르면(예: "main 직접 커밋"인데 PR 필수를
  걸었다) **한 줄로 불일치를 보고**한다: `참고 — CLAUDE.md에 "main 직접 커밋"이라
  적혀 있는데 방금 PR 필수 보호를 걸었습니다. set-initial 스킬을 다시 실행해 3단계
  Q3를 갱신하세요.` **CLAUDE.md를 대신 고치지 않는다. set-initial을 자동 호출하지
  않는다.**
- 브랜치 절 자체가 없으면(set-initial 미실행 프로젝트) 안내만 하고 넘어간다.

## 4단계 — 되돌리기 안내 (항상 출력)

0단계 6번 스냅샷을 근거로 두 경로 중 하나를 항상 한 줄로 알린다:

- 적용 전이 **보호 없음(404)** 이었다면: `되돌리려면: gh api -X DELETE
  repos/{o}/{r}/branches/{branch}/protection`
- 적용 전에도 **다른 보호 설정이 있었다면**: 스냅샷 JSON을 `PUT`으로 복원하는
  명령을 그대로 보여준다(GET 응답의 `enabled` 래퍼 필드는 PUT 요청의 평평한
  필드로 벗겨서 매핑한다).

작업 문서(사용 중이면 `구현후보고.md` 등)에도 같은 명령을 남긴다 — 사용자가
즉시 실행하지 않아도 나중에 참고할 수 있게 한다.

## 비대상 (v1)

- classic Branch Protection API만 다룬다 — 신형 Repository Rulesets API는 v1
  범위 밖이다(요청을 받아도 classic API로 안내한다).
- GitHub 외 호스트(GitLab·Bitbucket 등) — v1은 GitHub만.
- `main` 외 브랜치 동시 보호 — v1은 대상 저장소의 default_branch 1개만.
- CODEOWNERS 생성·필수화, `required_status_checks`(CI 게이트) 자동 설정 — 항상
  각각 `false`/`null`로 둔다.
- 신규 저장소 생성 시 자동 적용·템플릿화, 드리프트 주기 감지 — 1회성 호출 스킬이다.
- 9구간 워크플로 편입 — 명시적 요청으로만 실행된다(`core/playbook.md` 참조).

## 합리화 반박표

| 합리화 | 반박 |
|---|---|
| "협력자 1명이니 그냥 승인 0으로 조용히 넣자" | 조용히 넣는 것과 **알리고 넣는 것**은 다르다. 기본값은 맞지만 위협모델 고지(1단계)와 미리보기(Q2)는 생략할 수 없다 |
| "엄격이 제일 안전하니 추천하자" | 협력자 1명 상태의 엄격은 자기잠금이다. 추천이 아니라 **경고 + 재확인**이 맞는 반응이다 |
| "이미 GitHub 웹 UI로 설정 화면을 봤으니 GET은 생략해도 된다" | 이 세션이 본 것과 지금 상태가 같다는 보장이 없다. 매번 다시 GET한다 |
| "CLAUDE.md가 틀렸으니 이 김에 고쳐주자" | 이 스킬의 소관이 아니다. 고치면 set-initial과 소유권이 갈라진다 — 안내만 한다 |
| "적용까지 다 하고 나중에 되돌리는 법을 물어보면 알려주면 된다" | 사후 안내는 위반이다. 스냅샷은 적용 **전**에 뜨고, 되돌리기 명령은 적용 직후 항상 출력한다 |
| "PUBLIC이니 브랜치 보호가 없으면 누구나 push할 수 있다고 강조하자" | 사실과 다르다. 협력자 아닌 사람은 애초에 push 불가 — 위협모델을 정확히 전달한다(1단계) |
