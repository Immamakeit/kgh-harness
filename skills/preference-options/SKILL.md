# Preference Options (선호 기반 옵션 개인화 — 국면 A+B: 전역 + 프로젝트 오버라이드)

## 핵심 원칙

이 스킬은 질문을 만들지 않는다. **다른 스킬·플레이북이 이미 내는 번호 선택형
질문을 받아서, 그 옵션의 ①순서 ②기본번호 ③"(추천)" 표시만 조정한다.**

질문 계약의 네 요소(번호 · 직접 입력 · 건너뛰기 · 기본번호) 자체는 호출부의
책임이고 이 스킬이 절대 건드리지 않는다. "직접 입력"은 자유 텍스트를 대신
창작할 수 없으므로 **추천 후보에서 항상 제외한다** — set-initial의 창작 금지
원칙과 같은 논리다.

**근거 없는 추천은 없다.** 순서를 바꾸거나 기본번호를 옮길 때마다 반드시
"(이력 N회 중 M회)" 또는 "(이력 부족 — 스킬 기본값)" 둘 중 하나를 붙인다.
조용히 바뀌는 기본값은 이 스킬에서 금지된다.

**국면 A+B 범위**: 이 문서는 사용자 **전역** 프로필과 **프로젝트 오버라이드**
(`<프로젝트>/.harness/preferences.yaml`, 병합 규칙, `preferences.write_to`)를 함께
다룬다 — 아래 "프로필 파일"·"읽기 — 병합 규칙"·"쓰기 위치" 절 참조. 국면 B는 국면 A가
정한 프로필 스키마(`version`·`stats`·`pinned`·`updated`) 위에 그대로 얹힌다 — 두 파일의
내부 형식은 동일하고, 달라지는 건 "어느 파일을 보는가"뿐이다. `preferences.as_recommended`
(추천을 자동 채택하는 모드)는 국면 C 대상이다 — 이 스킬은 추천 계산·기록·열람·삭제만
제공하고, 그 추천을 자동으로 확정하는 건 하지 않는다.

## 입력 계약 (호출부의 책임)

이 스킬을 참조하는 스킬은 질문마다 **안정적인 `question_id`**를 준다
(예: `set-initial.commit_format`). 표시 문구가 나중에 바뀌어도 통계는 이 id로
누적된다 — 라벨 텍스트로 매칭하면 문구가 바뀔 때마다 학습이 끊긴다. 관례:
`<스킬명>.<질문요약_snake_case>`.

호출부는 옵션마다 안정적인 `option_id`(표시 문구와 별개)도 준다
(예: `conventional-commits`, `bracket-type`). "직접 입력"·"건너뛰기"는 각각
`option_id: custom` / `option_id: skip`으로 취급하되, **`custom`은 추천 후보에서
제외**한다(위 핵심 원칙).

## 프로필 파일 (국면 B — 전역 + 프로젝트 오버라이드)

| 파일 | 역할 | 레포 소속 |
|---|---|---|
| `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/harness/preferences.yaml` | 전역. 사람에게 붙는 취향 | **레포 트리 밖** |
| `<프로젝트>/.harness/preferences.yaml` | 프로젝트 오버라이드. **없어도 정상** | 대상 프로젝트 트리 **안** |

- 전역 경로는 install/validate_config.py의 `superpowers_state()`와 동일한 환경변수
  폴백 관례를 따른다.
- **전역 파일**은 이 스킬이 만들고 관리하는 사용자 전역 런타임 파일이지, 하네스
  소스도 배포물도 아니다. `.harnessignore`의 "레포 → 대상 프로젝트 복사" 파이프라인
  대상이 아니다. `install/setup`·`install/update`는 이 파일을 만들지도 건드리지도
  복사하지도 않는다.
- **프로젝트 파일**은 대상 프로젝트의 `.harness/` 바로 아래(`/work/`·`.meta`와 같은
  층위)에 있다 — 이 위치는 `install/update`가 `rsync --delete`로 배포물을 재복사하는
  범위 **안**이다. `install/lib.sh`의 `harness_copy`가 `/preferences.yaml`을 `/work/`·
  `.meta`와 같은 방식으로 제외 목록에 두므로 `update`가 이 파일을 지우지 않는다
  (그렇지 않으면 업데이트마다 프로젝트 학습이 사라진다).
- **lazy 생성**: 이 스킬이 처음 추천을 계산하거나 기록해야 하는데 대상 파일이 없으면,
  그 자리에서 아래 골격으로 새로 만든다(전역·프로젝트 두 파일 모두 같은 골격).

```yaml
version: 1
stats: {}
pinned: {}
updated: null
```

- **프로젝트 파일을 처음 만들 때 — `.gitignore` 안내 (T7)**: 전역 파일과 달리
  프로젝트 파일은 대상 저장소 git 추적 범위 **안**에 있다. 이 스킬이 프로젝트 파일을
  실제로 새로 생성하는 그 순간(이미 있으면 다시 묻지 않는다), 파일을 쓴 직후 한 줄
  안내한다:

  ```
  이 프로젝트에 선호 프로필을 새로 만들었습니다: .harness/preferences.yaml
  이 파일은 선택 이력을 담고 있어 이 저장소의 git 커밋에 포함될 수 있습니다.
  .gitignore에 추가할까요? [Y/n]
  ```

  (예/아니오 하나만 묻는 이진 확인이라 플레이북 §6의 번호 라벨 규칙 예외 —
  `ask_yn` 관용 형태를 그대로 따른다.) "예"(기본)면 `.harness/preferences.yaml`
  한 줄을 프로젝트 `.gitignore`에 추가한다(이미 있으면 중복 추가하지 않는다).
  "아니오"면 아무 것도 바꾸지 않고 안내만으로 끝낸다 — 이 스킬은 사용자 저장소의
  `.gitignore` 정책을 강제하지 않는다.

## 읽기 — 병합 규칙 (질문 단위 덮어쓰기)

두 파일을 합치지 않는다. **`question_id` 하나 단위로** 어느 파일을 볼지 정한다:

1. 프로젝트 파일에 그 `question_id`의 기록(`stats[question_id]` 또는
   `pinned[question_id]`)이 **하나라도 있으면**, 그 질문에 대해서는 **전역 파일을
   완전히 무시**하고 프로젝트 파일만 본다.
2. 프로젝트 파일에 그 `question_id` 기록이 **없으면** 전역 파일을 본다(국면 A와 동일
   동작 — 프로젝트 오버라이드가 없는 질문은 전역이 그대로 적용된다).
3. **합산하지 않는다.** 두 파일의 같은 `question_id` 카운트를 더해서 추천을 뽑지
   않는다 — 아래 예시와 반박표 참조.

```
전역:      commit_format: {conventional-commits: 12, bracket-type: 3}
프로젝트:  commit_format: {bracket-type: 4}
→ 추천: bracket-type   (전역의 conventional-commits 12는 이 질문에서는 보지 않는다 —
                        프로젝트 파일에 commit_format 기록이 있으므로 전역은 무시)
```

**표본이 임계값 미만이면 전역으로 넘어가지 않는다** — 파일 선택이 먼저고, 표본 3
규칙은 **고른 파일 안에서** 적용된다. 두 규칙이 겹치는 이 경우를 따로 적어 둔다:

```
전역:      commit_format: {conventional-commits: 12, bracket-type: 3}
프로젝트:  commit_format: {bracket-type: 2}          # 표본 2 → 임계값 3 미만
→ 추천: 스킬 표의 기본값, 근거 문구는 `(이력 부족 — 스킬 기본값)`
   (프로젝트에 기록이 있으므로 전역은 여전히 무시한다. 표본이 모자라니 그 프로젝트
    통계도 믿지 않고, 전역으로 되돌아가지도 않는다 — 셋 중 어느 것도 아닌 스킬 기본값)
```

이 조합은 사용자에게 **놀라울 수 있다**: 이 프로젝트에서 한두 번 고른 순간 전역의
강한 이력이 가려지면서 추천이 오히려 `(이력 부족 — 스킬 기본값)`으로 후퇴한다.
그래서 근거 문구를 반드시 붙인다 — 사용자가 "왜 갑자기 추천이 약해졌지"를 그 자리에서
읽을 수 있어야 한다. (2026-08-25 국면 B 관찰에서 이 조합이 실제로 재현됐고, 그때까지
이 문서의 예시는 표본 2에서 `bracket-type`을 추천한다고 적혀 있어 위 규칙과
모순이었다 — 예시 쪽을 규칙에 맞춰 고쳤다. `tests/skills/preference-options/green-results-b.md`
REFACTOR 1 참조.)

같은 호출에서 질문마다 결과가 다른 파일에서 나올 수 있다 — 예: `commit_format`은
프로젝트 파일에 기록이 있어 프로젝트를 보고, `branch_strategy`는 프로젝트 파일에
기록이 없어 전역을 본다. 이는 정상 동작이다(질문 단위 결정이므로).

**합산을 기각한 이유(반박은 아래 표에도 있음)**: 합산하면(`conventional-commits: 12,
bracket-type: 5` → 여전히 conventional-commits) **프로젝트에서 명시적으로 다르게
고른 선택이 전역 관성에 묻힌다** — 이 기능의 취지("이 프로젝트에서는 다르게 하고
싶다"는 신호를 존중하는 것)에 정면으로 반한다. 가중 합산도 기각한다 — 왜 그 추천이
나왔는지 사용자가 재현할 수 없기 때문이다.

## 쓰기 위치 — `preferences.write_to`

읽기(병합)와 쓰기는 분리된 결정이다. 새로 선택이 들어올 때 **어느 파일에 카운트를
올릴지**는 컨피그 `preferences.write_to`가 정한다:

```yaml
preferences:
  write_to: global        # global(기본) | project
```

- `global`(기본): 전역 파일의 `stats`/`pinned`에 기록한다. 지금까지(국면 A) 동작과
  동일 — 프로젝트를 명시적으로 지정하지 않는 한 아무것도 바뀌지 않는다.
- `project`: `<프로젝트>/.harness/preferences.yaml`의 `stats`/`pinned`에 기록한다
  (파일이 없으면 위 lazy 생성 + `.gitignore` 안내를 거친다).
- **미검증 값의 해석**(플레이북 §1-5 원칙 — 스키마는 이 하위 키 값 자체를 검사하지
  않는다): `write_to`가 정확히 `project`가 **아닌** 모든 값(부재·오타 포함)은
  `global`로 취급한다. `project` 오타를 조용히 `global`로 떨어뜨리는 쪽이 "덜
  놀랍다"고 판단한 근거는 — `project` 쓰기는 대상 저장소 git 커밋에 선택 이력이
  섞여 들어가는 부작용이 있는 반면(위 `.gitignore` 안내가 그 부작용을 겨냥한다),
  `global`은 사용자 홈 디렉터리에만 조용히 쌓이는 부작용 없는 기본값이기 때문이다.
  즉 오타 하나가 "이 프로젝트의 git 히스토리에 선택 이력이 새는" 쪽으로 넘어가면
  놀랍고, "원래 하던 대로 전역에 쌓인다" 쪽으로 떨어지면 놀랍지 않다 — `bootstrap.prompt`·
  `agent_mode`와 같은 원칙(놀람을 최소화하는 축이 값마다 다를 수 있다)의 또 다른
  사례다.

## 형식

```yaml
version: 1
stats:                             # 자동 축적 — 선택할 때마다 +1
  set-initial.commit_format:
    conventional-commits: 5
    bracket-type: 1
    skip: 0
pinned:                            # 사용자가 명시적으로 고정한 것 — 통계보다 항상 우선
  set-initial.branch_strategy: feature-branch-pr
updated: 2026-08-25T13:00:00+09:00
```

## 기록 절차 — 무엇을 남기고 무엇을 남기지 않는가

**남기는 것**: `question_id` + 선택된 `option_id`(안정 식별자, 표시 문구 아님) +
선택 시각(`updated`).

**절대 남기지 않는 것 (프라이버시 계약)**:
- **자유서술 답변의 원문** — 선택지를 만들 수 없는 질문의 답(예: set-initial
  1단계 "무엇을 만듭니까?"). 이 스킬은 애초에 그런 질문에 관여하지 않지만,
  혹시 호출부가 잘못 넘겨도 저장하지 않는다.
- **"직접 입력"으로 입력한 텍스트 원문** — `option_id: custom`으로 빈도만
  1 증가시키고 입력값 자체는 버린다.
- **프로젝트명·경로 등 식별 정보** — `question_id`는 스킬·질문 종류만 가리킨다.
  어느 프로젝트에서 나온 선택인지는 남기지 않는다(전역 프로필은 프로젝트 무관
  취향이어야 한다는 취지와도 맞다).

**명시적 고정(`pinned`)**: 사용자가 "이 질문은 앞으로 항상 X로 해줘"처럼 특정
`question_id`를 지목해 명시적으로 지시하면 `pinned[question_id] = option_id`로
기록한다. `stats`와 별개 트랙이며, 있으면 통계 계산 자체를 건너뛰고 항상 이긴다.

**어느 파일에 쓰는가 (국면 B)**: 위 "쓰기 위치" 절의 `preferences.write_to`가 정한
파일(기본 전역) 하나에만 쓴다 — 읽을 때(병합)와 달리 쓰기는 질문 단위로 파일을
바꾸지 않는다. `write_to: project`이고 그 파일이 아직 없으면, 쓰기 직전에 lazy
생성 + `.gitignore` 안내(위 "프로필 파일" 절)를 거친 뒤 기록한다.

## 추천 계산 절차

호출부가 옵션 목록(각 옵션의 `option_id`·표시 문구·표의 기본값)을 주면, 이 순서로
추천 옵션과 근거 문구를 정한다.

0. **파일 선택 (국면 B, 위 "읽기 — 병합 규칙" 적용)**: 이 `question_id`에 대해
   프로젝트 파일에 `stats[question_id]` 또는 `pinned[question_id]` 기록이 있으면
   아래 1~3 단계에서 **프로젝트 파일만** 읽는다. 없으면 **전역 파일만** 읽는다.
   (프로젝트 파일 자체가 없어도 정상 — 이 경우 항상 전역으로 떨어진다.)
1. **`pinned[question_id]`가 있으면** 그 `option_id`를 추천으로 쓴다.
   근거 문구: `(고정됨)`.
2. **없고, `stats[question_id]`의 표본 합계가 3 이상이면** 최다 득표
   `option_id`를 추천으로 쓴다. 근거 문구: `(이력 N회 중 M회)` — N은 전체 표본,
   M은 그 옵션의 득표. `custom`·`skip` 표본도 합계에는 포함하되 추천 후보로는
   고르지 않는다(위 핵심 원칙 — "직접 입력"은 추천 제외).
3. **그 외(표본 없음 또는 3 미만)** — 호출부가 표에서 정해둔 기본값을 그대로
   쓴다. 근거 문구: `(이력 부족 — 스킬 기본값)`.
4. 추천 `option_id`를 1번·`[기본: 1]`로 올리고, 그 문구 뒤에 근거를 붙인다.
   **번호는 표시 순서와 일치시킨다**(재배열했으면 다시 매긴다) — 플레이북 §6
   선택지 라벨 규칙. 추천 표시는 `(추천)` 꼬리표를 쓴다("(a)(b)" 같은 알파벳
   라벨을 쓰지 않는다 — 그건 HRN 복구 경로 표기이지 선택지 표기가 아니다).
   **나머지 옵션(추천으로 뽑히지 않은 것들)은 원래의 상대 순서를 그대로 유지한다** —
   추천 하나만 맨 앞으로 끌어올릴 뿐, 나머지를 다시 빈도순으로 재배열하지 않는다
   (재배열 규칙이 여러 겹이면 표를 예측할 수 없다). "직접 입력"·"건너뛰기"는
   재배열 대상이 아니다 — 항상 원래 자리(보통 끝쪽)를 지킨다. **동률 처리(v1
   범위 밖, 남는 허점):** 표본이 여러 `option_id`에 동률로 갈리면 우선순위
   규칙이 없다 — 이 경우 호출부가 넘긴 원래 표 순서상 먼저 오는 쪽을 추천으로
   쓰되, 이 규칙은 정식으로 검증되지 않았다.

예시(호출부가 이미 낸 질문에 이 스킬이 개입한 결과):

```
Q1. 커밋 메시지 형식
  1) Conventional Commits      예) feat: add login    ← 이력 5/6 (추천)
  2) [작업유형]: 메시지         예) [feat]: 로그인 추가
  3) 직접 입력
  4) 건너뛰기 (규칙 안 적음)
번호 입력 [기본: 1]:
```

표본이 부족하면:

```
Q2. 커밋 단위
  1) 파일 변경마다              ← 이력 부족 — 스킬 기본값
  2) 기능 단위로 모아서
  3) 직접 입력
  4) 건너뛰기
번호 입력 [기본: 1]:
```

## 손상·쓰기 실패 — 절대 질문 자체를 막지 않는다

두 파일(전역·프로젝트) 중 이번에 관여한 쪽에서 발생한 문제만 그 파일을 지목해
보고한다 — 다른 파일에는 영향이 없다.

- **관여한 파일이 손상돼 파싱이 안 되면**: `⚠️ HRN-W017 — 선호 프로필 파일(<경로>)
  손상/파싱 실패. 프로필 없이 스킬 기본값으로 진행합니다. 조치: (a) 파일을 고치거나
  삭제(다음 접근 시 재생성) (b) preferences.as_recommended를 꺼서 추천 계층을 우회`
  를 보고하고, 위 절차 3번(스킬 기본값)으로 그대로 진행한다. `<경로>`에는 실제로
  손상이 확인된 파일 경로(전역 또는 프로젝트)를 그대로 적는다. **질문 자체를
  멈추지 않는다.**
- **기록 쓰기가 실패하면**(권한 등): `⚠️ HRN-W018 — 선호 프로필 쓰기 실패(<경로>),
  권한 등. 이번 선택은 학습에 반영되지 않지만 진행은 계속합니다. 조치: (a) 프로필
  디렉터리 권한 확인 (b) 전역이면 CLAUDE_CONFIG_DIR로 쓰기 가능한 경로 지정,
  프로젝트면 preferences.write_to를 global로 되돌림` 을 보고하고, 방금 낸 질문·답
  자체는 정상 처리한다.

두 코드 모두 **결과를 절대 막지 않는다** — 추천 계층이 실패해도 질문 계약(번호·
직접입력·건너뛰기·기본번호)은 항상 정상 동작해야 한다.

## 열람

사용자가 "내 선호 프로필 보여줘"라고 명시 요청하면 **전역·프로젝트 두 파일 모두**
대상으로 한다(국면 B — 병합해서 보여주지 않는다, 있는 그대로 각각 보여준다):

1. 두 경로를 모두 그대로 보여준다(전역은 항상, 프로젝트는 대상 프로젝트에서
   실행 중일 때).
2. 어느 파일이 없으면 그 파일에 한해 "아직 없습니다(아직 이력이 쌓이지 않았습니다)"
   라고 말한다 — lazy 생성을 이 요청만으로 트리거하지 않는다(볼 게 없는데 빈 파일을
   만들 이유가 없다). 두 파일 다 없으면 둘 다 없다고 말하고 끝낸다.
3. 있는 파일은 각각 `stats`·`pinned`·`updated` 내용을 **가공 없이 그대로**
   보여준다(요약하거나 해석하지 않는다 — 사용자가 원본을 확인할 권리가 우선한다).
   두 파일을 병합해서 하나로 합쳐 보여주지 않는다 — 병합은 추천 계산 때만 쓰는
   내부 절차이지 열람의 정의가 아니다.

## 삭제 (초기화)

사용자가 "선호 프로필 초기화해줘"라고 명시 요청하면 **항상 확인을 받는다.**
`preferences.as_recommended` 값과 **무관하다** — 이 스킬은 국면 A라 그 컨피그
자체를 아직 참조하지 않지만, 설사 나중에(국면 C) 자동 채택 모드가 켜져 있어도
이 규칙은 그대로 유지된다.

**국면 B — 어느 파일을 지울지 먼저 확인한다.** 프로젝트 파일이 존재하면 "전역만
/ 프로젝트만 / 둘 다" 중 하나를 묻는다(둘 다 없으면 이 질문 없이 바로 "이미
없습니다"). 되돌릴 길이 파일마다 다르므로 근거도 따로 붙인다:

- **전역 파일**: 레포 트리 밖에 있어 git이나 `.bak` 같은 이 저장소의 되돌릴 길
  확보 장치가 **전혀 미치지 않는다.** 지우면 그걸로 끝이다.
- **프로젝트 파일**: 대상 저장소 git 추적 대상일 **수 있다**(위 `.gitignore` 안내를
  받아들이지 않았다면 커밋 이력에 남아 있을 수도 있다) — 다만 작업 트리에서 지우는
  이 동작 자체는 git이 추적 중이 아닌 한 마찬가지로 되돌릴 길이 없다. 커밋 이력
  존재 여부를 이 스킬이 대신 확인해주지 않는다 — 확인이 필요하면 사용자가 직접
  `git log -- .harness/preferences.yaml`로 본다.

```
선호 프로필을 초기화합니다.
  경로: ~/.claude/harness/preferences.yaml
  기록: stats 3개 질문, pinned 1개

되돌릴 방법이 없습니다(git·백업 대상 밖의 파일입니다). 진행할까요? [y/N]
```

확인되면 지목된 파일(들)을 삭제한다. 파일이 애초에 없으면 "이미 없습니다"라고만 답하고 아무
동작도 하지 않는다.

## 완료 기준 (제출 전 자가 점검)

- [ ] 추천마다 근거 문구(`(고정됨)` / `(이력 N회 중 M회)` / `(이력 부족 — 스킬
      기본값)`) 중 하나가 붙는다 — 조용한 재배열이 없다
- [ ] `question_id`+`option_id`만 기록했다 — 자유서술·직접입력 원문을 저장하지 않았다
- [ ] "직접 입력"을 추천 후보로 올리지 않았다
- [ ] 표본이 3 미만이면 통계를 무시하고 스킬 표 기본값을 썼다
- [ ] `pinned`가 있으면 통계보다 그것을 우선했다
- [ ] 질문 계약 4요소(번호·직접입력·건너뛰기·기본번호)를 건드리지 않았다
- [ ] 선택지 번호가 표시 순서와 일치하고, 추천은 `(추천)` 꼬리표로 표시했다
- [ ] 프로필 파일 손상·쓰기 실패가 있어도 질문 자체는 정상 진행했다(W017/W018)
- [ ] 열람은 가공 없이, 삭제는 항상 확인 후에 처리했다
- [ ] (국면 B) 프로젝트 파일에 해당 `question_id` 기록이 있으면 전역을 무시하고
      프로젝트만 봤다 — 합산하지 않았다
- [ ] (국면 B) 새 기록은 `preferences.write_to`가 정한 파일 한 곳에만 썼다
- [ ] (국면 B) 프로젝트 파일을 처음 만든 순간 `.gitignore` 안내를 냈다(이미
      있으면 다시 묻지 않았다)
- [ ] 사용 보고 (하네스 공통 규칙): 그 턴 보고 마지막에 `— 적용 스킬: preference-options`

## 합리화 반박표

| 합리화 | 반박 |
|---|---|
| "이력이 뚜렷하니 그냥 그 옵션으로 자동 확정하자" | 이 스킬은 표시만 바꾼다. 자동 채택은 국면 C(`as_recommended`)의 몫이고, 그마저도 사용자 입력을 기다리는 질문 계약 자체는 안 건드린다 |
| "자유서술 답도 같이 저장해두면 다음에 더 잘 맞출 수 있다" | 프라이버시 계약 위반이다. 프로젝트 고유 정보가 섞여 있을 수 있고, 이 스킬이 다루는 건 선택지 통계뿐이다 |
| "표본이 1~2개여도 패턴이 보이니 반영하자" | 임계값 3은 잘못된 학습이 조용히 나쁜 기본값이 되는 걸 막는 방지책이다. 표본이 적을 때는 스킬 기본값이 더 안전하다 |
| "직접 입력한 텍스트도 다음번 옵션 후보로 넣어주자" | 자유 텍스트를 대신 창작할 수 없다는 게 이 스킬의 전제다. `custom` 빈도만 세고 후보에서는 뺀다 |
| "손상된 파일이니 그냥 새로 밀고 시작하자" | 사용자 확인 없이 지우지 않는다. W017로 경고하고 이번 회차는 스킬 기본값으로 넘어갈 뿐, 파일 자체는 다음 접근까지 그대로 둔다 |
| "근거 문구까지 매번 붙이면 질문이 길어지니 생략하자" | 근거 없는 추천은 이 스킬에서 금지다. 짧은 꼬리표 하나(`(이력 5/6)`)면 충분하다 |
| "번호는 그대로 두고 추천 표시만 옆에 붙이면 되지" | 추천을 앞으로 재배열했는데 번호를 그대로 두면 번호와 표시 순서가 어긋난다 — 플레이북 §6이 명시적으로 금지한 사고 패턴이다 |
| "전역·프로젝트 카운트를 합치면 표본이 늘어서 추천이 더 정확해진다" | **금지.** 합산하면 프로젝트에서 명시적으로 다르게 고른 선택이 전역 관성(더 큰 표본)에 묻힌다 — 이 기능(프로젝트별 취향 존중)의 취지에 정면으로 반한다. 가중 합산도 같은 이유로 기각 — 왜 그 추천이 나왔는지 사용자가 재현할 수 없다 |
| "프로젝트 파일에 그 질문 기록이 하나뿐이어도 표본 3 임계값(§핵심 원칙)을 적용해 전역과 같이 봐야 하지 않나" | 임계값은 "같은 파일 안에서" 통계를 신뢰할지 판단하는 기준이지, 파일 선택 기준이 아니다. 프로젝트 파일에 기록이 있으면 표본 수와 무관하게 그 파일만 본다 — 표본이 1개뿐이면 3-미만 규칙(스킬 기본값 사용)이 그 안에서 그대로 적용될 뿐, 전역으로 넘어가 합치지 않는다 |
| "`write_to` 오타는 그냥 차단(E004)하면 되지, 왜 조용히 global로 떨어뜨리나" | 이 값은 `bootstrap.prompt`·`agent_mode`와 같은 급의 top_level 하위 스칼라라 스키마가 값 자체를 검사하지 않는다(플레이북 §1-5). 검사하지 않는 값을 차단할 수는 없으므로 남는 선택은 "무엇으로 취급할지"뿐이고, `project`가 대상 저장소 git에 남는 부작용이 있는 쪽이라 오타를 그쪽으로 떨어뜨리면 더 놀랍다 |
