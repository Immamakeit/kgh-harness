# Plan-Doc (구현계획 굳히기 + 범위 게이트)

## 핵심 원칙

**계획서에는 승인된 설계의 범위만 들어간다.** 계획의 내용은 scope-splitter(작업 분리)와
writing-plans(계획 작성)가 만들고, 이 스킬은 그 결과를 계약대로 응고시키고 범위를 지킨다.

## 1. 범위 게이트 (계획서 작성 전에 처리)

승인된 설계의 범위 밖 요구(비대상 항목 포함 요구, 새 기능 추가)가 들어오면 —
**계획서에 넣기 전에** 멈추고 선택지를 제시한다:

> 이 항목은 승인된 설계의 비대상입니다. 어떻게 할까요?
> **(a) 설계 수정 → 재승인 → 이번 계획에 반영**  **(b) 별도 작업으로 분리** (이번 계획은 그대로)

- 사용자가 고르기 전까지 계획서에는 **승인된 범위만** 담는다.
- **기정사실화 금지**: "일단 편입해뒀으니 확인해달라"는 선택지가 아니라 추인 유도다.
  편입된 문서를 보여주며 묻는 것도 같은 위반이다.
- 범위 밖 항목의 상세 설계·예시 코드를 미리 만들지 않는다 (그건 (a) 경로의 설계 단계 몫).
- 요구한 사람이 사용자 본인이어도 동일하다 — 사용자의 요구는 범위 변경의 *사유*지
  변경 절차의 *생략*이 아니다.

## 2. 문서 굳히기

- 위치: `.harness/work/<작업명>/<YYYY-MM-DD>/구현계획.md` (설계.md 옆.
  컨피그 `workdocs.path` 우선. vault 직접 쓰기 금지 — 저장은 판정 통과 후 obsidian-cli 몫)
- 템플릿: 구현계획 템플릿 준수 — 작업 범위 · 작업 대상 · 작업 방법(**예시 포함**) ·
  작업 비대상 · 체크리스트 + frontmatter + ≤10자 요약.
- status: `작성중` → 완성 시 `확정`. 다른 상태값 창작 금지.
- 게이트 동작은 컨피그를 따른다: `stages.plan.gate`가 `auto`(기본)면 계획 확정 후
  구현으로 자동 진행, `optional`이면 사용자 확인 후 진행. 단, **미해결 오픈 이슈**
  (답 없이는 구현이 갈라지는 질문)가 있으면 gate 설정과 무관하게 질문하고 멈춘다.

## 3. 계획 내용 계약

- 태스크는 **독립 구현 + 독립 검증** 단위 (scope-splitter 원칙). 태스크마다 검증 절차 명시.
- 순서에 근거를 단다 (충돌 회피·의존성). 병렬 가능 여부 표시.
- **비대상 승계 의무**: 승인된 설계의 비대상 **전 항목**이 계획의 비대상 섹션에 그대로
  나타나야 한다. 범위 게이트 (a)로 편입된 항목만 예외 — 변경 이력(일자·사유)과 함께
  범위로 이동하고, 설계 문서 갱신을 체크리스트에 넣는다.
- 답을 좌우하는 미확인 정보는 오픈 이슈로 명시하고 가정을 적는다.

## 완료 기준 (제출 전 자가 점검)

- [ ] 계획의 모든 태스크가 승인된 설계 범위 안 (범위 밖 요구는 선택지 제시로 처리했는가)
- [ ] 구현계획.md가 `.harness/work/<작업명>/<날짜>/`에 템플릿 5섹션 + ≤10자 요약으로 존재
- [ ] 설계 비대상 전 항목이 계획 비대상에 승계됨
- [ ] 태스크마다 독립 검증 절차 존재, 작업 방법에 예시 포함
- [ ] status = `확정` (오픈 이슈 있으면 `작성중` + 질문으로 종료)
- [ ] 사용 보고 (하네스 공통 규칙): 그 턴 보고 마지막에 `— 적용 스킬: plan-doc`
      (scope-splitter 등 함께 적용된 스킬은 쉼표로 병기). 미보고 = 위반
