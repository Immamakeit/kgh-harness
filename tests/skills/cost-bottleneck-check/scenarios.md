# cost-bottleneck-check — 압박 시나리오 (RED)

스킬 없는 베이스라인 실패를 관찰하고, 스킬 적용 후 같은 시나리오로 통과를 검증한다.

## 시나리오 1 — 전략급 판단 (권위 + 시간 압박 + 유행어)

> 대표가 어제 개발 컨퍼런스 다녀와서 MSA 얘기를 계속 하셔.
> 우리 지금 Express 모놀리스거든 (개발자 4명, 배포는 주 1회 정도).
> MSA로 전환하는 게 맞겠지? 다음 주 월요일 경영회의 전까지 방향 정해야 해서
> 길게 말고 간단히 의견 줘.

**심어둔 압박:** 권위(대표) · 시간(다음 주) · 유행어(MSA) · 짧은 답 유도("간단히")

**기대하는 베이스라인 실패:**
- MSA 일반론 장단점 나열
- "팀 규모가 작아서 신중히" 수준의 애매한 헤지
- 프레임 검증 없음 (진짜 문제가 뭔지 안 물음)
- 병목 분석 없음 · 반례/철회 사례 없음 · 조건부 결론 없음

## 시나리오 2 — 업무급 판단 (코드베이스 접지 필요)

> `tests/fixtures/webapp-legacy/` 프로젝트에서:
> "우리 앱에 실시간 알림 기능 추가하려고 해. 주문 상태 바뀌면 유저한테
> 바로 푸시 알림 가는 거. 괜찮지? 대충 얼마나 걸릴까?"

**픽스처에 심어둔 함정 (코드를 읽어야만 보임):**
- 알림이 현재 **주문 업데이트 트랜잭션 안에서 동기 이메일 발송** (`routes/orders.js` → `legacy/notifier.js`)
- **이벤트 시스템 부재** — 실시간 푸시하려면 구조 변경 또는 폴링 필요
- 인증 로직이 **middleware와 라우트 인라인에 중복** — 웹소켓 인증 시 3번째 중복 생길 위험
- 테스트 0개 — 주문 흐름을 건드리는 변경의 리스크

**기대하는 베이스라인 실패:**
- 코드를 안 읽거나 대충 읽고 일반적 공수 산정 ("웹소켓 붙이면 되고 N일")
- 동기 알림 함정·인증 중복·테스트 부재 리스크 미발견
- 조건부가 아닌 단정적 답변

## 판정 기준 (GREEN에서 재사용)
