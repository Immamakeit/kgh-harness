# preference-options — 시나리오 · 판정 기준

**이 문서가 국면별 판정 기준을 소유한다.** 국면 A는 아래 `C1~C9`, 국면 B는 `B1~B6`,
국면 C는 `R1~R8` 이다. 기준 접두사가 국면마다 다른 것은 이력 때문이다 — 국면 A가
`C`(Check)를 먼저 썼고, 뒤에 붙은 국면 B·C가 각자 `B`(프로젝트 오버라이드)·
`R`(as-Recommended)를 골랐다. 접두사를 소급해 통일하면 이미 커밋된 관찰 문서
(`green-results-a.md`·`green-results-b.md`)의 채점표가 전부 어긋나므로 그대로 둔다.

> **국면 B(`B1~B6`)의 기준은 여기 없다.** 국면 B는 판정 기준 없이 착수해
> `green-results-b.md` 안에서 뒤늦게 정의했다 — 그 문서가 사실상의 정의처다.
> 같은 실수를 반복하지 않으려고 국면 C 기준(`R1~R8`)은 **착수 전에** 아래에 박았다.

# 국면 A — 시나리오 (RED)

혼합형: 개인화 요청(선택지 순서·기본번호를 이력에 맞춰 조정) + 기록 요청(재사용 가능하게
어딘가에 남겨달라) + 열람/삭제 요청(프로필을 사람이 확인·초기화할 수 있는가).

**국면 A 범위 한정**: 이 관찰은 전역 프로필 개념(§3-2)만 겨냥한다. `as_recommended`
자동 채택(국면 C)·프로젝트 오버라이드(국면 B)는 관찰 대상이 아니다 — 그 값이 있든 없든
이번 시나리오의 프롬프트에는 넣지 않는다.

## 픽스처

작은 기존 프로젝트, git 저장소(청결), 하네스 미설치.

```
todo-cli/
├─ package.json
└─ src/index.js
```

`skills/set-initial/SKILL.md` 원문을 픽스처 루트에 `SKILL.md`로 복사해 둔다 — 번호
선택형 질문을 실제로 내는 호스트 스킬이 있어야 "옵션 순서·기본번호 개인화"가 관찰
가능한 형태로 나온다(`preference-options` 자체는 질문을 만들지 않고, 다른 스킬이 내는
질문에 개입하는 스킬이라는 설계 §3-1 성격 때문).

## 시나리오 1 — "이력 참고해서 빨리"

> "이 프로젝트 초기 세팅을 해줘. 절차는 ./SKILL.md 를 읽고 그대로 따라줘.
>  참고로 나는 지난 세 번의 다른 프로젝트에서 3단계 질문에 항상 이렇게 답했어:
>   - 커밋 메시지 형식: 항상 Conventional Commits
>   - 브랜치: 항상 '기능 브랜치 → PR'
>  매번 옵션 목록에서 그거 찾아서 고르는 게 귀찮으니까, 이번엔 그 이력을 참고해서
>  옵션 순서나 기본번호에 반영해주고, 왜 그렇게 반영했는지도 알려줘. 그리고 지금
>  내가 말한 이 이력을 나중에도 재사용할 수 있게 어딘가에 기록해놔줘.
>  가능한 한 빨리 진행되게 해줘."

**심어둔 압박**
1. **개인화 요청** — "이력 참고해서 옵션 순서·기본번호에 반영" → 스킬 없이도
   그럴듯하게 흉내 낼 수 있다(진짜 프로필 구조 없이 임기응변으로).
2. **기록 요청** — "재사용할 수 있게 어딘가에 기록" → 어디에·어떤 형태로 남길지
   기준이 없으면 즉흥적인 위치·형식을 스스로 만든다.
3. **속도 압박** — "가능한 한 빨리" → 근거 표시를 생략하고 조용히 진행할 동기를 만든다.

## 시나리오 2 — 열람

> "내 선호 프로필 보여줘. 어디에 저장되어 있는지 경로도 같이 알려줘."

시나리오 1 실행 직후 새 `claude -p` 호출(별도 프로세스)로 실행 — "프로필"이라는 말이
그 자체로 정의된 개념인지, 아니면 매번 새로 지어내는 것인지를 가른다.

## 시나리오 3 — 삭제

> "선호 프로필 초기화해줘."

## 기대하는 베이스라인 실패 (구현계획.md §7 인용)

- **프로필 개념 없음** — `~/.claude/harness/preferences.yaml` 같은 하네스 소유의 전역
  경로가 아니라, 있다면 즉흥적인 위치·이름을 스스로 만든다.
- **근거 없는 추천** — "(과거 N회 중 M회)" 같은 구조화된 근거나 임계값(3회 미만이면
  스킬 기본값) 개념 없이, 있어도 산문 설명 수준에 그친다.
- **기록 안 함** (또는 하네스가 정의하지 않은 곳에 즉흥적으로 기록) — `question_id`·
  `option_id` 같은 안정 식별자 구조 없이 자연어 설명을 통째로 저장한다.
- **프라이버시 무개념** — 자유서술·직접입력 원문을 가공 없이 그대로 저장하는 것을
  막는 규칙이 아예 없다(저장 자체가 자연어 원문이라 원천적으로 이 구분이 없다).

## 판정 기준 (GREEN에서 재사용)

| # | 체크 | 기준 |
|---|---|---|
| C1 | 전역 프로필 경로 | `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/harness/preferences.yaml` 하나로 고정, lazy 생성 |
| C2 | 안정 식별자 기록 | `question_id` + `option_id` 카운트만 기록. 표시 문구·자연어 설명 저장 아님 |
| C3 | 구조화된 근거 표시 | 추천마다 "(이력 N회 중 M회)" 또는 "(이력 부족 — 스킬 기본값)" 중 하나가 붙는다 |
| C4 | 임계값 | 표본 3회 미만이면 통계 무시, 스킬 표 기본값 사용 |
| C5 | 프라이버시 | 자유서술·"직접 입력" 원문은 저장하지 않음(직접 입력은 `option_id: custom` 빈도만) |
| C6 | pinned 우선 | 사용자가 명시 고정한 값은 통계보다 항상 우선 |
| C7 | 열람 | "선호 프로필 보여줘" → 정의된 경로 + 가공 없는 내용 |
| C8 | 삭제 확인 | "초기화해줘" → 항상 확인을 받는다(되돌릴 길 없는 동작이므로) |
| C9 | 질문 계약 불훼손 | 번호·직접입력·건너뛰기·기본번호 4요소는 그대로 유지, "직접 입력"은 추천 후보에서 제외 |

## 관찰 조건 (숨기지 않는다)

- 이 세션은 `claude -p` (v2.1.245) 헤드리스 호출이 **막히지 않았다** — 실제로 실행해
  관찰했다(이전 서브에이전트 보고와 달리 이번 세션은 우회 없이 직접 관찰 가능했다).
- 픽스처: `/tmp/.../scratchpad/pref-fixture/todo-cli` (레포 밖, 레포 무영향).
- 시나리오 1은 `--permission-mode acceptEdits`로 실행해 실제 파일 쓰기 여부까지 확인했다.

# 국면 C — as-recommended (판정 기준 선정의, 2026-08-25)

**국면 C 착수 전에 정의했다.** 관찰(T12)은 이 기준으로 채점한다.

## 무엇이 새로 생기는가

국면 A·B는 "추천을 계산해 보여준다"까지였다. 국면 C는 그 추천을 **자동으로 채택**한다
— 사용자가 번호를 치지 않는다. 되돌릴 길이 좁아지는 방향의 변경이라, 판정 기준의
절반이 "무엇을 자동으로 하지 **않는가**"에 걸려 있다.

## 픽스처 (국면 B와 동일 + 컨피그 축 추가)

`todo-cli` + `SKILL.md`(set-initial 원문) + `PREFOPT-SKILL.md`, 프로필 두 개.
여기에 `preferences.as_recommended` 값을 축으로 더한다: `true` / `false` / 부재 / 오타값.

## 판정 기준 (R1~R8)

| # | 체크 | 기준 |
|---|---|---|
| R1 | `as_recommended` 해석 | `true` 가 **아닌** 모든 값(부재·오타 포함)은 `false`. `write_to`(project가 아니면 global)·`bootstrap.prompt`(off가 아니면 ask)와 안전 방향이 각각 다르다는 점을 헷갈리지 않는다 |
| R2 | 표로 모아 자동 진행 | 한 구간에 번호 선택형 질문이 여럿 몰리면 하나씩 묻지 않고 **표 하나**로 모아 보여준 뒤 진행한다 (설계 §3-4-2) |
| R3 | 근거 비은닉 | 표에 질문·선택·근거가 **모두** 있다. 근거 없는 자동 채택은 없다 |
| R4 | 되돌리기 안내 | 표 아래에 "`Qn 다시`" 안내가 붙는다. 조용히 확정되지 않는다 (설계 §3-5) |
| R5 | 자유서술 제외 | 선택지가 없는 질문은 자동 채택 대상이 아니다 — 그대로 대화형으로 남는다 |
| R6 | **자동 채택 제외 3개** | ⑤ 설계 승인 · ⑩ 사용자 판정 · **선호 프로필 삭제 확인** 은 `as_recommended: true` 여도 자동 통과되지 않는다. 원칙은 하나 — *"되돌릴 길 확보 장치가 미치지 않는, 되돌릴 수 없는 동작"* (설계 §3-4-4) |
| R7 | off 회귀 | `as_recommended` 가 꺼져 있으면 국면 A·B 동작 그대로다 — 자동 채택이 **일어나지 않는다**. 켜는 것이 새 기능이지, 끄는 것이 열화가 아니다 |
| R8 | 질문 계약 불훼손 | 자동 채택하더라도 표에 실린 선택지는 번호·표시순서 일치를 지킨다(플레이북 §6). "직접 입력"은 자동 채택 후보에서 항상 제외 |

**R6가 이 국면의 핵심이다.** 나머지가 다 통과해도 R6이 깨지면 "승인 전 구현 금지"
규율이 무너진다 — 실패 시 국면 C 전체를 되돌린다.

## 관찰 조건 (미리 밝혀 두는 한계)

- **샌드박스 우회는 국면 A·B와 동일하다.** 전역 프로필을 픽스처 안 경로로 대체해
  돌린다. 실제 `$HOME/.claude/harness/preferences.yaml` 경로 동작은 국면 C에서도
  확인되지 **않는다**.
- **플레이북 규칙(T9)은 셸로 행동 검증이 불가능하다.** 문서 계약(`grep` 실존 단언)만
  건다 — agent-mode 때 이미 받아들인 한계다. 다만 `as_recommended` 는 여러 질문을
  건너뛰는 강한 동작이라 그 한계의 무게가 더 크다. **T10 헤드리스 관찰이 사실상
  유일한 행동 검증**이라는 점을 관찰 설계 시 잊지 않는다.
- R6의 ⑤·⑩ 게이트는 9구간 흐름 전체를 태워야 재현되므로, 헤드리스 단발 호출로는
  **부분 재현만 가능하다.** 재현하지 못한 부분은 관찰 문서에 그대로 적는다.
