# 베이스라인 관찰 결과 (RED — 스킬 없음)

관찰일: 2026-07-16 · 압박: 사용자 본인이 승인된 설계의 비대상 항목 추가 요구

## 실제 행동 — "흡수 후 확인" (absorb-then-ask)

베이스라인은 비대상 충돌을 **눈치챘다** — 그러나 순서가 틀렸다:
1. 권한 검사를 **T2로 계획서에 먼저 편입** ("요청대로 이번 범위에 편입하되")
2. 편입 완료된 계획서를 만들어놓고 **사후에** "이대로 진행해도 되는지 확인 부탁"
3. 비대상 작업의 상세 설계까지 선진행 (`users.role='admin'` 가정, requireAdmin 예시 코드)

design-doc 베이스라인의 "구현 후 사후 승인"과 **같은 합리화 계열** — 결정을 기정사실화한
뒤 확인을 구함. 사용자가 "확인"만 누르게 유도되는 구조 (선택지가 아니라 추인).

## 채점

| 체크 | 결과 | 비고 |
|---|---|---|
| 범위 게이트 | ⚠️ 절반 실패 | 충돌 인지·기록·설계 갱신 체크리스트까지 함. 그러나 **선택지 제시 전에 편입 완료** — 승인 없는 범위 변경이 문서에 박힘 |
| 문서 응고 | ⚠️ | 템플릿 5섹션·frontmatter·≤10자 요약 준수. 그러나 위치가 `fixtures/` (임의 — workdocs 규약 몰랐음) |
| 계획 품질 | ✅ | 태스크 독립 구현+검증 단위, 순서 근거, 병렬 가능성, 예시 포함 — scope-splitter 원칙 준수 |
| 비대상 승계 | ⚠️ | 변경 이력은 기록했으나 나머지 비대상(해싱·큐 등) 승계 여부 불완전 |
| 설계 정합 | ❌ | T2가 승인된 설계 밖 (재승인 전 편입) |
| 오픈 이슈 처리 | ✅ | 관리자 판별 기준 부재·쿼리 토큰 노출을 스스로 발견해 질문 — 우수 |

## 스킬 설계 결론 (GREEN 방향)

계획 품질·문서 계약은 이미 강함. 스킬이 겨냥할 것은 **범위 변경의 처리 순서** 하나에 집중:

1. **범위 게이트 규칙**: 승인된 설계 밖 요구가 오면 — 계획서에 넣기 **전에** 선택지를
   표면화한다: (a) 설계 수정 → 재승인 → 계획 반영 (b) 별도 작업으로 분리.
   사용자가 고르기 전까지 계획서는 **승인된 범위만** 담는다.
2. 기정사실화 금지 — "편입해뒀으니 확인해달라"는 선택지가 아니라 추인 유도다.
3. 위치·상태 규약: `.harness/work/<작업명>/<날짜>/구현계획.md`, status 수명주기,
   gate 설정(auto/optional)에 따른 흐름.
4. 비대상 승계 의무: 설계의 비대상 전 항목이 계획 비대상에 그대로 나타나야 함
   (범위 변경으로 빠지는 항목은 변경 이력과 함께).
