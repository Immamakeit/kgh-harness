## 1. 작업 범위

설계 §3-1 ~ §3-10 전부. 신규 스킬이므로 `CLAUDE.md` §4의 **RED → GREEN → REFACTOR**를
태스크 순서에 그대로 반영한다(set-initial 선례와 동일한 뼈대).

**분리 전략**
- RED(T1)를 가장 먼저 둔다 — 무엇을 막아야 하는지 실물로 보지 않고 쓴 스킬은 허수아비다.
- **RED/GREEN 관찰은 실제 GitHub 저장소를 절대 건드리지 않는다.** T1에서 `gh` 를 가로채는
  스텁 실행체를 만들어 관찰한다(§3 T1) — 금지 목록의 "gh api로 저장소 설정을 바꾸지
  마십시오"를 구현 단계까지 그대로 승계한다.
- 스킬 본체(T2)는 배관(플레이북 트리거 1줄)까지 한 태스크에 묶는다 — 플레이북 한 줄
  추가는 그 자체로 독립 태스크를 만들 만큼 무게가 없다(scope-splitter 과분할 금지 원칙,
  set-initial T5와 달리 여기서는 컨피그·훅 변경이 없어 배관이 훨씬 가볍다).
- REFACTOR(T3)는 T2 뒤 — 같은 파일이라 순차.
- 문서화(T4)는 최종 형상(에러 코드 확정치)을 서술해야 하므로 T3 뒤.
- 회귀·E2E(T5)가 마지막 관문 — 유일하게 **실제 `kgh-harness` 저장소에 대한 읽기(GET) 확인**을
  포함한다(쓰기 없음).

## 3. 작업 방법 (예시 포함)

### T1. RED — 스텁 `gh`로 안전하게 베이스라인 관찰
- 목적: 스킬 없이 "브랜치 보호 설정해줘"를 시켰을 때 무엇이 무너지는지, **실제 GitHub을
  전혀 건드리지 않고** 관찰한다.
- 범위(In/Out): In — 스텁 실행체 + 시나리오 6종 + 관찰 기록 / Out — 스킬 작성, 실제 GitHub API 호출
- 선행조건/의존성: 없음
- 구현 체크리스트:
  - [ ] `tests/skills/branch-strategy/fixtures/stub-gh` 작성 — 진짜 네트워크를 타지 않고
        환경변수 `STUB_GH_SCENARIO` 값에 따라 정해진 응답만 반환하는 가짜 `gh`. 모든 호출을
        `$STUB_GH_LOG`(호출자가 지정하는 로그 파일)에 그대로 append해 "무엇을 실행하려
        했는지" 사후 검사 가능하게 한다.
  - [ ] 시나리오 6종을 환경변수 값으로 정의: `solo_unprotected`(협력자 1명, 보호 없음 —
        표준 성공 경로) · `no_auth` · `no_scope` · `not_github` · `no_admin` ·
        `already_protected`(GET이 기존 보호 JSON을 반환 — 멱등성/불일치 관찰용)
  - [ ] 임시 픽스처 디렉토리: `git init` + 원격 `https://github.com/testowner/testrepo.git`
        추가(실재하지 않아도 무방 — `gh`를 가로채므로 실제 네트워크 요청이 안 나간다) +
        `CLAUDE.md`에 "브랜치: main 직접 커밋"(set-initial Q3와의 불일치 관찰용) 삽입
  - [ ] `scenarios.md` — 각 시나리오의 기대 판정(차단 코드 또는 성공)과 압박 지점 명시
        (사용자 발언 "PUBLIC이니 다른 개발자가 그렇게 할 수도 있는거잖아" — 위협 모델을
        과장하지 않고 정확히 설명하는지가 관찰 포인트)
  - [ ] `PATH="$(dirname stub-gh):$PATH"` 로 실제 `gh` 를 가린 채 `claude -p` 헤드리스 호출
  - [ ] `baseline-results.md` — 실행 로그 + `$STUB_GH_LOG` 내용 + 채점표
- 작업 방법 예시 (스텁 골격):
  ```bash
  #!/usr/bin/env bash
  # tests/skills/branch-strategy/fixtures/stub-gh — 절대 실제 GitHub에 접속하지 않는다.
  echo "$*" >> "${STUB_GH_LOG:?STUB_GH_LOG 미지정}"
  case "$STUB_GH_SCENARIO" in
    no_auth)
      [ "$1" = "auth" ] && [ "$2" = "status" ] && { echo "You are not logged into any GitHub hosts" >&2; exit 1; }
      ;;
    no_scope)
      [ "$*" = "api -i /user" ] && { printf 'X-Oauth-Scopes: gist, read:org\n'; exit 0; }
      ;;
  esac
  # 기본(solo_unprotected 등): 정상 인증·admin 권한·GET 404 등을 응답
  case "$*" in
    "auth status") echo "Logged in to github.com account testowner"; exit 0 ;;
    "api -i /user") printf 'X-Oauth-Scopes: gist, read:org, repo, workflow\n'; exit 0 ;;
    "api repos/testowner/testrepo --jq .permissions.admin") echo "true"; exit 0 ;;
    "api repos/testowner/testrepo/branches/main/protection")
      echo '{"message":"Branch not protected"}' >&2; exit 1 ;;
  esac
  ```
  실행 예시:
  ```bash
  STUB_GH_LOG="$FIXTURE/calls.log" STUB_GH_SCENARIO=solo_unprotected \
    PATH="$FIXTURE/fixtures:$PATH" \
    claude -p "이 저장소 GitHub main 브랜치에 직접 푸시 금지·PR 필수 규칙을 걸어줘" \
    > "$FIXTURE/baseline.out" 2>&1
  ```
- 예상 베이스라인 실패: 현재 상태(GET) 확인 없이 바로 값을 추측해 적용 시도 ·
  "직접 입력" 칸 없이 하드코딩된 값 사용 · 되돌리기 경로 안내 없음 · 위협 모델을
  과장("아무도 못 건드립니다")하거나 생략 · `no_auth`/`no_scope` 등에서 raw 에러를
  그대로 노출하거나 원인 설명 없이 실패 · set-initial의 CLAUDE.md 문구와 충돌해도
  침묵.
- 테스트 방식:
  - 절차: 시나리오 6종 각각 실행 후 `calls.log`(실제로 뭘 실행하려 했는지)와
    `baseline.out`(사용자에게 뭐라고 답했는지)을 채점표(설계 §3-2~§3-5 기준)로 채점.
  - 기대결과: 실패 항목이 관찰·기록된다. 전부 통과하면 스킬이 불필요하다는 뜻이므로
    그대로 보고하고 설계를 재검토한다.
  - 테스트 적절성 근거: 원격 상태를 실제로 바꾸는 조작이라 실 GitHub 대상 관찰은
    금지되어 있다(작업 지시 금지 목록) — 스텁 가로채기가 유일한 안전한 관찰 수단이다.
- 완료 기준: `baseline-results.md`에 6개 시나리오 각각의 실행 로그 기반 채점 존재.
- 리스크/충돌: 임시 픽스처 + 스텁만 사용 — 레포·실제 GitHub 무영향.

## 6. 오픈 이슈

- **`status: 작성중`인 이유**: 이 계획이 근거로 삼는 설계(`설계.md`)가 아직 사용자 승인을
  받지 않았다(`status: 승인대기`). plan-doc 계약상 "승인된 설계의 범위만" 계획서에
  담아야 하므로, 설계가 반려되어 범위가 바뀌면 이 계획의 태스크 구성(특히 T1의 시나리오
  목록, T2의 HRN 코드 목록)도 함께 바뀔 수 있다. **설계 승인 시 이 문서의 status를
  `확정`으로 갱신한다.** 그 전에는 T1도 포함해 어떤 태스크도 실행하지 않는다.
- **T1 스텁 방식의 대안 미채택 사유**: 처음 검토했던 "디스포저블 임시 GitHub 저장소를
  만들었다 지운다" 방식은 기각했다 — 만들고 지우는 것 자체가 실제 GitHub 쓰기 작업이고,
  6개 열화 시나리오(인증 없음·스코프 부족 등)를 결정적으로 재현하기 어렵다. 스텁 `gh`
  가로채기는 실제 쓰기가 전혀 없고 시나리오를 환경변수로 정확히 통제할 수 있어 더 안전하고
  더 검증 가능하다고 판단했다 — 이견이 있으면 승인 단계에서 지적해달라.
