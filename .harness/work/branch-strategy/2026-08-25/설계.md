# 설계 — branch-strategy (원격 GitHub 브랜치 보호 규칙 스킬)

## 1. 요구사항 / 의도

사용자 발언 원문:

> "하네스 브랜치전략세우기(메인브랜치에 직접 푸시 금지 등) 하는 방법"
> "GITHUB 자체에서 원격 MAIN 에 직접 푸시나, PR없는 병합을 막아야한다 이거야. PUBLIC이니 다른개발자가 그렇게 할 수도 있는거잖아"

즉 대상은 **로컬 git hook이 아니라 원격(GitHub) 저장소 설정**이다. 하네스가 새 스킬
`branch-strategy` 로 대상 프로젝트의 GitHub 저장소에 브랜치 보호 규칙을 대화형으로
세워준다.

오늘(2026-08-25) `Immamakeit/kgh-harness` 의 `main` 에 실측 적용을 완료했고 이 설계는
그 실측 결과를 근거로 삼는다(§2). set-initial 선례(질문 계약·0단계 안전장치·되돌릴 길)를
그대로 승계한다 — 이 작업은 §2 흐름의 신규 기능 지시이나, set-initial과 마찬가지로
**9구간 워크플로 밖의 독립 유틸리티 스킬**로 설계한다(근거는 §3-9, §4 비대상).

## 3. 설계안

### 3-1. 스킬 개요

- 이름: **`branch-strategy`** (작업명과 동일 — set-initial 선례를 따름).
- 위치(향후 구현): `skills/branch-strategy/SKILL.md`. `core/playbook.md` 직독 계약을 그대로 따른다(신규 컨피그 키 불필요, §3-9 근거).
- 대상 v1: **GitHub만.** classic Branch Protection API(`PUT .../branches/{branch}/protection`)만 쓴다 — 신형 Repository Rulesets API는 다루지 않는다(§4 비대상, 오늘 실측이 classic API로만 검증됨).
- 트리거: set-initial과 달리 **세션 시작 시 능동 제안을 하지 않는다.** 사용자의 명시적 요청("브랜치 보호 설정해줘", "메인에 직접 푸시 막아줘" 등)으로만 실행된다 — §2의 `impact` 구간과 같은 계약("명시 지시"). 이유: 이 스킬은 **원격 저장소의 실제 상태를 바꾸는 파괴적 조작**이라 set-initial의 "문서가 없으면 제안" 같은 자동 유인이 부적절하다(문서 부재는 사실이지만, 보호 규칙 부재는 "사고가 나야 아는" 성격이 아니라 언제든 사용자가 판단해서 청할 사안).

### 3-2. 위협 모델 (설계 근거로 인용 — 요구사항의 원문 근거)

실측(§2)이 보여주는 사실을 그대로 스킬 문서에 박아 넣는다:

1. 공개 저장소라도 **협력자로 초대되지 않은 사람은 애초에 push 불가.** "지나가던 개발자의 직접 푸시"는 이 규칙 이전에도 불가능하다.
2. 이 규칙이 실제로 막는 것은 (a) 소유자 본인의 실수, (b) 포크에서 온 PR의 무단 병합, (c) force push·브랜치 삭제.
3. `enforce_admins: false` 인 상태에서 admin이 직접 push하면 **경고만 찍히고 push는 통과**한다 — "막는다"는 표현이 admin에게는 완전하지 않다는 사실을 사용자에게 그대로 알린다.
4. 협력자가 1명(owner)뿐이면 `required_approving_review_count≥1` 은 자기 자신을 자기 PR에서 잠그는 함정이 된다.

스킬은 이 네 가지를 **적용 전 요약**으로 사용자에게 보여준다(과장된 안전 주장 금지 — "이걸 켜면 아무도 못 건드립니다" 류의 문구를 쓰지 않는다).

### 3-3. 0단계 — 전제 점검 + 되돌릴 길 (set-initial 0단계 사상 승계)

되돌리기 전 무엇 하나도 적용하지 않는다. 순서:

1. `gh` 설치 확인 → 없으면 **차단**, `HRN-E008`(기존 코드 재사용 — PRD상 "필수 실행체·도구 미발견"과 동일 성격, 신규 코드 불필요).
2. `gh auth status` → 로그인 안 됨 → **차단**, `HRN-E011`(신규).
3. 토큰 스코프에 `repo` 없음(`gh api -i /user` 의 `x-oauth-scopes` 헤더로 확인) → **차단**, `HRN-E012`(신규). 이 API가 성공해야 이후 판정도 신뢰할 수 있으므로 인증 확인(2) 바로 다음에 둔다.
4. `git remote get-url origin` 이 없거나 호스트가 `github.com`이 아님 → **차단**, `HRN-E013`(신규) — "원격 없음"과 "GitHub 아님"을 하나로 묶는다(§3-5 근거).
5. `gh api repos/{o}/{r} --jq .permissions.admin` 이 `false`(또는 저장소 조회 자체가 403/404) → **차단**, `HRN-E014`(신규) — 이 API가 admin 아닌 계정도 조회는 종종 가능하므로, "admin 아님"과 "권한 없어 조회 자체가 안 됨"을 같은 코드로 묶는다.
6. 여기까지 통과하면 **현재 보호 상태를 GET** 하고, 결과를 `.harness/work/branch-strategy/<날짜>/before-protection.json` 에 스냅샷 저장(되돌리기용, §3-8). 404(보호 없음)면 그 사실 그대로 저장.
7. 협력자 수를 `gh api repos/{o}/{r}/collaborators` 로 조회(§3-6 기본값 로직에 사용). 조회 실패 시 **가장 보수적인 가정(1명, 승인수 0)으로 열화**하고 그 사실을 한 줄 보고한다.
8. 현재 상태 요약 + §3-2 위협 모델을 사용자에게 보여준 뒤에만 질문(§3-4)으로 넘어간다.

set-initial과 같은 원칙: **"파괴적 조작 전 안전장치 = 현재 상태 공개 + 되돌릴 길 확보 + 사후 통보 금지."** 여기서 "되돌릴 길"은 git이 아니라 6단계의 JSON 스냅샷이다(원격 설정은 git으로 되돌릴 수 없다).

### 3-4. 질문 계약 (번호·직접 입력·건너뛰기·기본번호 — set-initial과 동일 규율)

**Q1 — 마스터 스위치.** 협력자 수(§3-6)로 기본번호가 갈린다.

```
현재 상태: main 브랜치 보호 없음 (또는: 이미 적용됨 — 아래 값과 동일/다름)
협력자: 1명 (Immamakeit, admin)

어떤 조합을 적용할까요?
  1) 표준 — PR 필수 · 승인 0명(협력자 1명 기준) · force-push 금지 · 삭제 금지 · 관리자 예외 있음 [추천]
  2) 최소 — force-push·삭제만 금지, PR은 강제하지 않음
  3) 엄격 — 표준 + 관리자도 규칙 적용(enforce_admins) — 협력자 2명 이상일 때만 권장
  4) 직접 입력 (세부 항목을 하나씩 정한다)
  5) 건너뛰기 (미리보기만 보고 적용 안 함)
번호 입력 [기본: 1]:
```

- 협력자가 2명 이상이면 1번의 "승인 0명"이 "승인 1명"으로 바뀌고, 문구도 그렇게 표시한다.
- **"엄격"을 협력자 1명 상태에서 고르면** 즉시 경고: "협력자가 본인뿐이라 enforce_admins를 켜면 앞으로 어떤 변경도 PR 승인자를 구하지 못해 병합이 막힙니다. 그래도 진행할까요? [Y/N, 기본 N]".
- "직접 입력"을 고르면 하위 항목을 각각 같은 4요소 계약으로 순서대로 묻는다: PR 필수 여부 → 승인 인원수(자유 입력, 범위 0~6 안내) → force-push 허용 여부 → 삭제 허용 여부 → enforce_admins 여부. 이미 결정된 안전 기본값(force-push 금지·삭제 금지)이 있어도 "직접 입력" 경로에서는 그것도 다시 확인 대상이다 — 사용자가 명시적으로 "직접"을 골랐기 때문이다.
- **묻지 않고 항상 넣는 값**(선택지로 낼 가치가 없음, set-initial의 "묻지 않고 항상 넣는 항목"과 같은 예외 규율): `dismiss_stale_reviews: false`, `require_code_owner_reviews: false`, `required_status_checks: null`(CI 미구성 프로젝트가 다수일 것이므로) — "직접 입력" 경로에서도 이 세 값은 굳이 노출하지 않는다(과다 질문 방지, scope-splitter 원칙).

**Q2 — 최종 적용 확인 (미리보기 필수).** Q1(및 하위 질문) 응답을 실제 `gh api` 요청 바디로 조립해 **그대로 보여준 뒤에만** 묻는다:

```
아래 설정을 Immamakeit/kgh-harness 의 main 에 적용합니다:
  PUT /repos/Immamakeit/kgh-harness/branches/main/protection
  { "required_pull_request_reviews": {"required_approving_review_count": 0, ...},
    "enforce_admins": false, "allow_force_pushes": false, "allow_deletions": false, ... }

적용할까요? [Y/N, 기본: N]
```

기본을 **N**으로 둔다 — design-doc의 "명시적 승인 전에는 없다" 정신을 원격 상태 변경에도 그대로 적용한다(구현 승인 게이트가 아니라, 이 스킬 자체의 실행 게이트).

### 3-5. 전제 부재 열화 경로 표

### 3-6. 협력자 수 기반 기본값 로직

- **적용 근거**: 오늘 실측이 "협력자 1명일 때 승인수 1은 자기 자신을 잠그는 함정"임을 직접 증명했다(§2). 이걸 알고도 기본값을 획일적으로 1로 두면 스킬이 사용자를 그 함정에 밀어넣는 것이므로, 읽어서 반영하기로 판단했다.
- 규칙: 협력자(owner 포함) 수 `N` 에 대해 `N == 1` → 승인수 기본 0, `N ≥ 2` → 승인수 기본 1. `enforce_admins` 는 `N` 과 무관하게 기본 `false`("엄격" 프리셋을 고를 때만 별도 확인).
- 조회 실패(권한/네트워크) 시 `N = 1` 로 열화(가장 보수적 = 가장 안전한 값 쪽으로) — 이 사실을 질문 전에 한 줄 고지한다.

### 3-7. 적용 절차 — 멱등성

- `PUT .../protection` 은 GitHub API 자체가 **전체 치환**이다(부분 PATCH가 아님). 매번 완전한 desired-state 객체를 보내므로, 같은 답으로 두 번 실행해도 결과는 한 번 실행과 동일하다 — **멱등성은 API 특성에서 자연히 나온다**, 스킬이 별도 상태 비교 로직을 가질 필요가 없다.
- 단, "이미 적용된 값과 같다"는 사실은 Q1 이전에 §3-3-6에서 GET한 현재 상태와 비교해 사용자에게 보여준다(적용할 필요가 없다는 사실을 먼저 알리는 것도 "결과 비은닉"이다).
- `delete_branch_on_merge` 는 `PATCH /repos/{o}/{r}` 로 별도 호출(오늘 실측 절차와 동일) — Q1의 표준/엄격 프리셋에 포함, 최소 프리셋에는 미포함(브랜치 보호와 무관한 설정이므로).

### 3-8. 되돌리기

- §3-3-6에서 저장한 `before-protection.json` 을 근거로 두 가지 되돌리기 경로 제공:
  - 적용 전이 **보호 없음(404)** 이었다면: `DELETE /repos/{o}/{r}/branches/{branch}/protection`.
  - 적용 전에도 **다른 보호 설정이 있었다면**: 스냅샷 JSON을 그대로 `PUT` 해서 복원(GET 응답 스키마와 PUT 요청 스키마가 다른 필드는 스킬이 매핑 표로 문서화 — 예: GET의 `enabled` 래퍼를 PUT의 평평한 필드로 벗기는 변환).
- 스킬 실행이 끝나면 항상 "되돌리려면: `<복원 명령 또는 DELETE 명령>`" 한 줄을 출력한다 — 사용자가 즉시 실행하지 않아도 다음에 참고할 수 있게 작업 문서에도 같은 명령을 남긴다.

### 3-9. set-initial과의 경계 (중복 정리 — 필수 결론)

**결론: CLAUDE.md 브랜치 절의 소유자는 set-initial(Q3)이다. branch-strategy는 CLAUDE.md를 쓰지 않는다.**

- set-initial Q3는 "로컬 작업 관례를 문서에 어떻게 적을 것인가"(선언, 강제력 없음)를 다룬다. branch-strategy는 "GitHub이 실제로 무엇을 차단하는가"(집행, 서버 사이드)를 다룬다. 계층이 다르다 — 같은 사실의 두 표현이 아니다.
- 두 스킬이 같은 파일을 쓰면 어느 쪽이 최신인지 드리프트가 생긴다(이 저장소의 `CLAUDE.md:23` 이 이미 그 사례). 소유권을 하나로 고정해 드리프트 원인을 없앤다.
- branch-strategy는 적용 완료 후 대상 프로젝트의 `CLAUDE.md` 에 브랜치 절이 있으면 읽어서, 방금 적용한 값과 문면이 다르면(예: "main 직접"이라 적혀 있는데 PR 필수를 걸었다) **불일치를 한 줄로 보고**하고 "set-initial 스킬을 다시 실행해 3단계 Q3를 갱신하세요"라고 안내한다. CLAUDE.md를 대신 고치지 않는다(자동 편집도, 자동 재호출도 하지 않는다 — 사용자가 판단).
- CLAUDE.md에 브랜치 절 자체가 없으면(set-initial을 아직 안 돌린 프로젝트) 안내만 하고 넘어간다 — 생성은 set-initial 소관.
- 이 경계는 신규 컨피그 키를 요구하지 않는다(§2 표에서 확인한 대로 스키마 변경 불필요).

### 3-10. 문서 반영 (범위에 포함 — 별도 승인 불필요, 규모가 작다)

- `README.md` 에 "브랜치 보호" 절 신설(set-initial 절 옆) — 사람용 호출법 + 에이전트용 한 줄.
