# 설계 — agent-mode (싱글/멀티 에이전트 모드 전역 스위치)

## 1. 요구사항 / 의도

사용자 발언(그대로): **"싱글에이전트모드, 멀티에이전트모드 둘 중에 하나 선택할 수 있어야함."**

이미 확정된 결정(재논의 대상 아님, 그대로 인용):

- **전역 스위치가 마스터다.** 싱글 모드면 `stages.<구간>.dispatch: true` 는 **무시**된다.
- 멀티 모드인데 실행 환경이 서브에이전트를 쓸 수 없으면 **차단하지 않고 싱글로 열화하고
  경고한다**(비차단).

**근거 사건 (실측, 인용):**

`.harness/work/set-initial/2026-08-25/구현후보고.md:53-55` —

> 코드리뷰: 수행함 (2회차까지). 사용자가 세션 지시로 서브에이전트 디스패치를 허용해
> 컨피그대로 `verify.dispatch: true` · `superpowers:requesting-code-review` 를 실행했다.
> (앞서 이 항목을 "미수행"으로 적었던 것은 그 지시 이전 상태다 — 지시 후 실제로 돌렸다.)

같은 패턴이 하루 전 `public-release` 세션에도 있었다
(`.harness/work/public-release/2026-08-24/구현후보고.md:52-56`): 컨피그는
`impact`·`implement`·`verify` 를 `dispatch: true` 로 정해뒀는데, 그 세션은
Agent 도구 사용이 금지돼 있어 "서브에이전트 디스패치 없이 메인 세션 자체 리뷰로 대체"했고
"제3자 리뷰는 미수행 — 이 항목은 '통과'가 아니라 '대체 수행'"이라고 스스로 기록했다.

**문제의 핵심**: 컨피그는 멀티 모드를 원했지만 실행 환경(세션 지침)은 싱글로만 동작했다.
이 어긋남을 표현할 컨피그 키가 없어서, 매번 즉흥적으로 "대체 수행"·"미수행" 같은 상태값을
문서에 창작해야 했다. `agent_mode` 는 이 어긋남을 **명시적으로 선언 가능한 상태**로
바꾸는 것이 목적이다 — 컨피그가 "이 프로젝트는 원래 싱글로 돈다"를 말할 수 있게 하고,
동시에 "멀티로 설정했는데 환경이 못 받쳐준 경우"를 흐름이 알아서 흡수하게 한다.

## 3. 설계안

### 3-1. 키 이름·위치 — 최상위 `agent_mode:` (근거)

`defaults` 하위가 아니라 **최상위**에 둔다.

- `defaults` 의 존재 이유는 "구간 미지정 시 상속" — 즉 `stages.<구간>.model` 처럼 **구간별로
  오버라이드 가능**하다는 것이 전제다(`core/playbook.md` §1 2항). `agent_mode` 를
  `defaults` 밑에 두면 "그럼 `stages.design.agent_mode` 로 구간별 오버라이드가 되는가?"라는
  질문이 자연히 따라오는데, **이미 확정된 결정("전역 스위치가 마스터다")과 정면으로 충돌한다.**
  이 스위치는 구간별로 갈라지면 안 된다.
- `active_harness` 가 이미 "구간과 무관하게 흐름 전체를 지배하는 전역 스위치"의 선례다
  (`harness.config.yaml:4`, 최상위 단독 키). `agent_mode` 는 성격이 같다 — **실행 메커니즘을
  결정하는 전역 스위치**. 같은 층위에 둔다.
- `stages.keys` 스키마에는 `agent_mode` 를 **추가하지 않는다** — 구간별 오버라이드 키를
  아예 존재하지 못하게 막아, "전역이 마스터"라는 규칙을 스키마 구조로도 강제한다
  (누군가 `stages.verify.agent_mode: multi` 를 넣으면 `HRN-E004` 미지 키로 차단됨).

### 3-2. 값과 기본값

값: `single | multi`. 기본값: **`multi`**.

**근거 — 하위호환이 곧 기본값 근거다.** 이 레포를 포함해 이미 배포된 컨피그는 전부
`agent_mode` 를 모른다. PRD §4가 이미 "구간별 model/effort는 각 구간을 서브에이전트로
디스패치하여 적용한다"를 아키텍처로 확정했고, 현재 `harness.config.yaml`·템플릿 모두
`impact/implement/verify` 에 `dispatch: true` 를 실제로 걸어뒀다. 키가 없는 상태의 실제
동작(=각 구간이 자기 `dispatch` 값을 따름)을 그대로 이어받는 값은 `multi` 다. 기본값을
`single` 로 하면 키를 추가하는 것만으로 기존 설치본의 실행 방식이 조용히 바뀐다 —
"컨피그 값 변경은 즉시 반영"(PRD §1)이 "아무것도 안 바꿨는데 동작이 바뀜"이 되어버려
사고다.

**"multi"의 정확한 의미 — 새로 정의**: `multi` 는 "무조건 디스패치"가 아니라 **"구간별
`dispatch` 값을 그대로 존중"** 이다(오늘의 상태 그대로). `single` 은 "**전 구간의 `dispatch`
값을 무시**하고 전부 메인 세션 인라인으로 수행"이다. 이 비대칭 정의 덕에 "싱글이면
`dispatch:true` 가 무시된다"는 확정 사실이 정확히 구현된다 — 멀티는 기존 판단을 그대로
쓰고, 싱글만 그것을 덮어쓴다.

### 3-3. 스키마 등록 — `bootstrap` 선례를 그대로 따른다

```yaml
top_level:
  agent_mode: { type: enum, values: [single, multi], default: multi, validated_by: schema }
  # 주의: top_level 스칼라 값은 구조(키 존재)만 검사된다 — validate_config.py 는
  # top_level 에 대해 필수 여부만 확인하고 enum 값 자체는 검사하지 않는다
  # (active_harness 만 어댑터 조회로 간접 검증됨. §2 실측 참조).
  # single 이 아닌 값은(오타 포함) 전부 multi 로 취급한다 — 플레이북 §1, bootstrap.prompt
  # 해석 규칙(§0-1)과 동일한 안전측 기본화.
```

`validate_config.py` 의 검사 로직(top-level 루프에 `check_type` 미호출)은 **고치지
않는다** — 이것은 `bootstrap` 이 이미 받아들인 한계이고, 이 설계도 같은 한계를 그대로
받는다. 대신 스키마 주석 + 플레이북 해석 규칙(3-5)으로 오타의 결과를 예측 가능하게 만든다.
검증기 로직 확장은 이 작업의 범위 밖이다(§4 비대상).

### 3-4. "환경이 서브에이전트를 쓸 수 없다"의 판단 기준 — 이 설계의 핵심

두 계층으로 나눈다. 이 구분이 없으면 플레이북이 "언제 열화할지"를 말할 수 없다.

**(A) 시도 전에 이미 아는 경우 (사전 신호)**

- 이번 세션의 도구 목록에 Agent 도구 자체가 없다.
- 세션 지침·직전 대화에서 서브에이전트 사용 금지가 이미 명시됐다(실측 사례 둘 다 이
  경로였다 — "이 세션은 Agent 도구 사용이 금지돼 있어").

이 경우 **디스패치를 시도조차 하지 않는다.** 실패를 만들어 낭비할 필요가 없다 —
`active_harness` 실행체 부재를 사전에 감지해 `HRN-E008` 로 차단하는 것과 같은 층위의
판단이다(`core/playbook.md` §1 3항, "실행체·모델 실존 예외처리"). 차이는 그쪽은
**차단**, 이쪽은 **비차단 열화**라는 이미 확정된 결정뿐이다.

**(B) 시도해봐야만 아는 경우 (사후 신호)**

정적 목록으로 못 거르는 런타임 거부 — Agent 도구는 있고 금지 신호도 못 봤는데, 실제
호출이 메커니즘 층위에서 실패하는 경우(샌드박스·조직 정책 등). 이건 `HRN-E009`(모델명이
거부됨 → `defaults.model` 1회 폴백)와 **다른 층위의 실패**다 — 모델을 못 찾은 게 아니라
디스패치 메커니즘 자체가 안 되는 것이므로, `defaults.model` 폴백은 의미가 없다(모델을
바꿔봐야 여전히 디스패치가 안 된다). 이 경우 **폴백을 시도하지 않고 곧바로 그 구간을
인라인으로 재수행**한다.

**공통 처리 — 열화는 "그 흐름 실행" 단위로 눌어붙는다(sticky).** (A)든 (B)든 한 번
열화하면, **같은 흐름 실행 안의 남은 구간들도 재시도 없이 인라인을 유지**한다(3구간마다
매번 실패를 반복해 보고를 도배하지 않기 위함). 단, **컨피그 파일은 건드리지 않는다** —
다음 흐름 실행(또는 다음 세션)은 `agent_mode` 를 처음부터 다시 해석한다(PRD §1 "즉시
반영, 캐시 금지" 원칙을 그대로 따름). 환경이 영구적으로 디스패치 불가라면 매 흐름마다
같은 열화가 한 번씩 반복되는데, 이는 세션마다 한 번의 헛디스패치 시도 + 경고 한 줄의
낮은 비용이며, 반대급부로 "환경이 나아졌는지"를 컨피그가 아니라 실제로 계속 확인하게
해준다 — 상태를 파일에 박제하지 않는다.

### 3-5. 플레이북 변경 — 위치와 구체 문구(초안)

**§1 컨피그 해석**, 2항("구간 설정은 stages.<구간> → 없는 키는 defaults 상속") 뒤에
신설:

> **2-1. `agent_mode` 해석(전역 마스터 스위치):** 최상위 `agent_mode` 값을 읽는다.
> `single` 이 아닌 모든 값(누락·오타 포함)은 `multi` 로 취급한다.
> - `multi`(기본): 각 구간은 자신의 `stages.<구간>.dispatch` 값을 그대로 따른다(하위호환).
> - `single`: **모든 구간의 `dispatch` 값을 무시**하고 전 구간을 메인 세션에서
>   인라인으로 수행한다(구간별 `skills[]`는 그대로 적용하되 model/effort 오버라이드는
>   적용되지 않는다 — 애초에 디스패치가 model/effort 적용 수단이므로).
> - 사용자가 세션 중 명시적으로 이번 실행만 모드를 지정하면(예: "이번엔 싱글로") 그
>   지시가 컨피그보다 우선한다 — **그 흐름 실행 1회에 한해서만** 적용하고 컨피그
>   파일은 바꾸지 않는다. 흐름 시작 보고에 "세션 지시로 <모드> 강제 적용"을 명시한다.

**§3 디스패치 규칙(impact/implement/verify)**, 도입부에 신설:

> **0. 실효 모드 판정:** §1-2-1에서 정한 실효 `agent_mode` 가 `single` 이면 이 절 전체를
> 건너뛰고 해당 구간을 메인 세션 인라인으로 수행한다(그 사실을 구간 보고에 명시).
> `multi` 이고 해당 구간의 `dispatch` 가 true 일 때만 아래를 수행한다.
>
> **1. 사전 신호 확인:** 이번 세션 도구 목록에 Agent 도구가 없거나, 세션 지침·직전
> 대화에서 서브에이전트 금지가 이미 드러났다면 — 시도하지 않고 곧바로 인라인 전환 후:
> `⚠️ HRN-W016 — 이 세션 환경에서 서브에이전트 디스패치를 쓸 수 없어(<사유>) 이 흐름
> 실행 동안 싱글 모드로 열화합니다. 조치: (a) 세션 지침에서 서브에이전트를 허용한 뒤
> 재시도 (b) 조치가 어렵다면 그대로 진행 — 결과 품질은 동일하되 model/effort 구간별
> 지정만 적용되지 않습니다.` 를 보고한다. 이후 같은 흐름 실행의 남은 구간도 재시도 없이
> 인라인을 유지한다.
>
> **2. 시도 후에만 드러나는 실패:** 위 신호가 없어 실제로 디스패치를 시도했는데
> 메커니즘 자체가 거부된 경우(`HRN-E009` 의 모델명 거부와는 다른 층위 — `defaults.model`
> 폴백을 시도하지 않는다) — 즉시 같은 형식의 `HRN-W016` 을 보고하고 그 구간을 인라인으로
> 재수행한다. 이후 같은 흐름 실행의 남은 구간도 재시도 없이 인라인을 유지한다.
>
> **3. 이 열화는 그 흐름 실행에 한정된다.** 컨피그는 고치지 않는다 — 다음 흐름 실행은
> `agent_mode` 를 처음부터 다시 해석한다(§1, 캐시 금지 원칙).

### 3-6. 하위호환

`agent_mode` 가 없는 기존 컨피그(이 레포 자신 포함)는 스키마 기본값 `multi` 로 해석되고,
동작은 **오늘과 완전히 동일**하다(각 구간이 자기 `dispatch` 값을 따름). 마이그레이션이나
경고가 필요 없다 — `workdocs`·`storage` 등 기존 선택적 최상위 키들도 부재 시 조용히
기본값을 쓰는 것과 동일한 취급이다(부재 경고를 내는 다른 선례가 없다).

### 3-7. 에러/경고 코드

신규 1건: **`HRN-W016`** — "서브에이전트 디스패치 불가, 싱글 모드로 열화(비차단)".
`E` 가 아니라 `W` 인 이유: 확정 결정("차단하지 말고 열화")에 따라 흐름을 멈추지 않기
때문. 복구 경로 2개(세션 지침 조정 / 그대로 진행)를 표준 형식대로 붙인다. PRD §8 표에
행을 추가해야 코드가 "실행체 전용" 상태를 벗어나 진실의 기준에 등재된다(§4 범위에 포함).

## 4. 작업 범위 / 비대상

- **범위:** §3-1 ~ §3-7 전부 — 스키마 등록(`agent_mode`), 플레이북 §1·§3 개정, PRD §8
  코드표 갱신, 회귀 테스트(구조 검증 수준).

- **비대상:**
  - **`stages.<구간>.agent_mode` 같은 구간별 오버라이드 키 신설** — 3-1의 근거대로
    전역 마스터 원칙과 정면 충돌하므로 스키마에 추가하지 않는다.
  - **`install/validate_config.py` 를 고쳐 top-level enum 값을 실제로 검증하게 만드는 것**
    — `bootstrap` 이 이미 받아들인 한계를 그대로 받는다(§3-3). 검증기 로직 강화는 별도
    작업(모든 top-level 값 검증을 한 번에 올리는 리팩터)의 몫이다.
  - **`install/setup` 대화형 질문에 `agent_mode` 선택지 추가** — `bootstrap.prompt` 선례와
    동일하게 템플릿 기본값 제공으로 충분하다고 본다(그때도 setup에 질문을 추가하지
    않았다). 필요성이 실제로 드러나면 별도 작업으로 뺀다.
  - **구간별 개별 재시도 정책 고도화** (예: 매 구간마다 디스패치를 다시 시도) — 3-4의
    sticky 열화(그 흐름 실행 동안 1회 열화 후 유지)로 충분하다고 본다. 세션마다 반복
    비용이 낮다는 것이 근거다.
  - **열화 발생 시 컨피그 파일 자동 수정(`agent_mode` 를 `single` 로 다시 써넣는 등)** —
    컨피그는 사용자 소유의 단일 진실원이다(PRD §1). 런타임 관찰로 파일을 조용히
    덮어쓰지 않는다.
  - **Codex/Ollama 어댑터에서의 `agent_mode` 의미 정의** — 두 어댑터 모두 v1 미구현
    스텁이다(PRD §10). 어댑터가 실제로 생길 때 그 어댑터의 디스패치 능력에 맞춰
    재정의한다.
  - **"서브에이전트 사용 금지" 사전 신호의 기계적 자동 판별(코드화)** — 이 판단은 지금
    구조상 플레이북 프로프트를 읽는 메인 세션(LLM)의 판단에 맡겨진다. 결정적 스크립트로
    승격하는 것은 PRD §4 "결정적 코드 리졸버로의 승격은 흐름이 실사용으로 검증된 뒤"
    원칙에 따라 이 작업의 범위 밖이다.
