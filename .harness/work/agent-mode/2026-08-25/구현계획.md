# 구현 계획 — agent-mode

> 설계: `.harness/work/agent-mode/2026-08-25/설계.md` (2026-08-25, **승인대기** — 아직
> 승인되지 않았다. **status를 `확정`으로 올리지 않는 사유는 §6 오픈 이슈 1번 참조.**)

## 1. 작업 범위

설계 §3-1 ~ §3-7 전부. 새 스킬을 만드는 작업이 아니라 **스키마·플레이북·PRD 코드표 개정 +
구조 검증 회귀 테스트**이므로 `CLAUDE.md` §4의 RED→GREEN→REFACTOR(스킬 제작 규율)는
대상이 아니다 — 대신 scope-splitter의 "충돌 최소화 분해" 원칙(하위호환 → 적용 확장 →
회귀 고정)을 따른다.

**분리 전략**
- 스키마(T1)를 먼저 둔다 — 플레이북 문구(T2·T3)가 참조할 키가 스키마에 먼저 존재해야
  `validate-config` 로 즉시 확인할 수 있다.
- T2(§1 해석 규칙)와 T3(§3 디스패치 규칙)는 같은 파일(`core/playbook.md`)의 서로 다른
  절이라 **순차 진행이 안전**하다(동시 편집 시 diff 충돌 가능성). T2가 정의하는 "실효
  모드" 개념을 T3가 그대로 인용하므로 순서도 T2 → T3.
- T4(회귀 테스트)는 T1의 스키마 형상이 확정된 뒤에만 정확한 케이스를 짤 수 있다 — T1 후행.
- T5(PRD §8 코드표 갱신)는 T3에서 확정되는 `HRN-W016` 메시지 문구를 그대로 인용해야
  하므로 T3 후행. T1·T4와는 **병렬 가능**(다른 파일).
- 구간별 오버라이드 키를 스키마에 추가하지 않는 것(설계 §4 비대상)이 전제이므로,
  `stages.keys` 는 어떤 태스크에서도 건드리지 않는다 — 회귀 위험이 낮다.

## 3. 작업 방법 (예시 포함)

### T1. 스키마 등록 — `agent_mode`
- 목적: 컨피그가 "이 프로젝트는 싱글/멀티 중 무엇으로 도는가"를 표현할 수 있게 한다.
- 범위(In/Out): In — `top_level` 항목 1개 + 템플릿·루트 컨피그 반영 / Out —
  `stages.keys` 에 오버라이드 키 추가, `validate_config.py` 로직 변경
- 선행조건/의존성: 없음
- 구현 체크리스트:
  - [ ] `config/schema.yaml` `top_level` 에 `agent_mode: { type: enum, values: [single, multi], default: multi, validated_by: schema }` 추가 + 검증 한계 주석(설계 §3-3 문구 그대로)
  - [ ] `config/harness.config.template.yaml` 최상위(`active_harness:` 바로 아래)에 `agent_mode: multi` + 설명 주석 추가
  - [ ] `harness.config.yaml`(이 레포 자신)에도 동일하게 `agent_mode: multi` 명시(기본값과
        같아도 의도를 문서화 — `bootstrap` 때와 동일한 관례)
  - [ ] `stages.keys` 에는 손대지 않았는지 diff로 재확인(설계 §4 비대상 준수 확인)
- 작업 방법 예시:
  ```yaml
  # config/harness.config.template.yaml
  active_harness: claude          # claude | codex(추후) | ollama(추후)
  agent_mode: multi                # single | multi(기본) — 전역 마스터 스위치.
                                    # single이면 stages.<구간>.dispatch 값은 전부 무시된다.
                                    # 주의: 이 값은 검증기가 검사하지 않는다 — single이 아닌
                                    # 값은(오타 포함) 전부 multi로 취급된다(플레이북 §1).
  ```
- 테스트 방식:
  - 절차: `./install/validate-config` 를 템플릿 기반 컨피그와 루트 컨피그 각각에 실행.
    이어서 `agent_mode: bogus` 로 일부러 오타 낸 사본을 만들어 같은 명령 실행.
  - 기대결과: 정상 값 두 컨피그 모두 `검증 통과`, exit 0. 오타 사본도 **구조 검사는
    통과**(exit 0) — 이것이 설계 §3-3에서 의도적으로 받아들인 한계이며, "차단되지
    않는다"는 것 자체가 이 테스트의 통과 조건이다.
  - 테스트 적절성 근거: 미지 최상위 키는 `HRN-E004` 로 전체 흐름을 차단하므로(실측)
    스키마 등록 누락이나 오타는 그 즉시 전체 정지로 이어진다 — 최우선으로 확인해야 한다.
- 완료 기준: 위 두 조건(정상 통과 + 오타도 구조상 통과) 충족.
- 리스크/충돌 가능성: 스키마·컨피그 파일만 건드림. T2·T3(playbook.md)와 파일이 달라
  충돌 없음.
