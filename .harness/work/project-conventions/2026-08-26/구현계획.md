## 1. 작업 범위

설계 §3-1 ~ §3-5 전부. 신규 스킬이 없으므로 `CLAUDE.md` §4의 RED→GREEN→REFACTOR
스킬 규율 대신, ⑦ 구현 구간 스킬(`superpowers:test-driven-development`)에 따라
**태스크마다 실패 테스트를 먼저 관찰**한다.

**분리 전략 (핵심 근거)**

- **①(스킬 해석)이 유일한 하드 블로커다.** T1~T3만 끝나도 후보 저장소에 손으로
  컨피그를 적어 실제로 쓸 수 있다. 나머지는 이력·표기 문제라 없어도 굴러간다.
- **`storage.docs`·문서명은 공통 인터페이스 변경이라 3단계로 쪼갠다**(scope-splitter
  원칙): T4 하위호환 키 추가 → T5 적용 확장 → T6 구버전 제거. 중간 어느 시점에
  멈춰도 동작하는 상태가 유지된다.
- **T2와 플레이북 §1-4는 한 태스크로 묶는다.** 설계 §3-1이 짚은 결합부다 — 한 곳만
  고치면 "검증은 통과하는데 실행이 스킬을 못 찾는" 더 나쁜 상태가 된다.
  scope-splitter의 "구조적으로 분리 불가면 억지 분리 금지" 조항을 적용한다.
- **T3(도그푸딩 함정)은 T2에서 분리한다.** T2 직후 이 레포에서 `project_path` 를 켜면
  8종 전부가 `HRN-E015` 로 터지는 것을 **실패로 관찰**한 뒤 T3에서 닫는다 — 관찰 없이
  방어를 먼저 넣으면 그 방어가 실제로 무는지 알 수 없다.
- T7~T8은 서로 다른 파일이라 T4~T6과 **병렬 가능**하다.

## 3. 작업 방법 (예시 포함)

### T1. 회귀 픽스처 — "자기 `skills/` 를 가진 대상"

- 목적: 지금은 프로젝트 스킬을 **못 쓴다**는 사실을 테스트로 못 박아, 이후 변경이
  무엇을 바꿨는지 대조 가능하게 한다.
- 범위(In/Out): In — 픽스처 + 현행 동작 단언 / Out — 해석 로직 변경
- 선행조건/의존성: 없음
- 구현 체크리스트:
  - [ ] `install/setup` 으로 temp 대상을 만든 뒤 **대상 루트에** `skills/myskill/SKILL.md` 생성
  - [ ] 컨피그 `stages.implement.skills` 에 `myskill` 추가
  - [ ] `validate-config` 가 **`HRN-E005` 로 차단**함을 단언 (현행 동작 고정)
  - [ ] 에러 메시지가 `.harness/skills/myskill/SKILL.md` 를 지목함을 단언 (프로젝트 경로를 아예 안 본다는 증거)
- 테스트 방식:
  - 절차: 위 픽스처로 `validate-config` 실행, 종료코드 1 + `HRN-E005` 확인.
  - 기대결과: 차단된다. **이것이 "현재는 실프로젝트에서 못 쓴다"의 실물 증거다.**
  - 테스트 적절성 근거: 설계 §2가 지적한 테스트 구멍("빈 대상으로만 검증")을 그 자리에서 메운다.
- 완료 기준: 새 케이스가 PASS(= 차단이 재현됨). 기존 240 PASS 유지.
- 리스크/충돌: 테스트 파일 단독. 소스 무변경.

### T2. `skills.project_path` + 탐색 확장 + `HRN-E015` (검증기 + 플레이북 동시)

- 목적: 프로젝트 스킬을 컨피그로 가리킬 수 있게 하고, 이름 충돌은 조용히 가리지 않고 차단한다.
- 범위(In/Out): In — 스키마 키·검증기 탐색·플레이북 §1-4·에러코드 / Out — realpath 동일 처리(T3)
- 선행조건/의존성: T1
- 구현 체크리스트:
  - [ ] `config/schema.yaml` `top_level` 에 `skills: { type: map, required: false }` + 서브스키마
        (`project_path: { type: string, nullable: true, default: null }`) + 해석 규칙 주석
  - [ ] `validate_config.py` — 프로젝트 루트를 `dirname(abspath(config_path))` 로 유도
  - [ ] 탐색 판정 4분기 구현: 하네스만 / 프로젝트만 / **양쪽(`HRN-E015` 차단)** / 없음(`HRN-E005`)
  - [ ] `project:<이름>` 접두사 해석 — 충돌을 푸는 수단. 접두사가 붙었는데 프로젝트 경로가
        `null` 이거나 파일이 없으면 `HRN-E005`
  - [ ] `HRN-E005` 복구 경로에 **프로젝트 경로도 함께** 안내하도록 문구 보강
  - [ ] `core/playbook.md` §1-4 를 같은 계약으로 갱신 (결합부 — 반드시 같은 커밋)
- 작업 방법 예시:
  ```yaml
  skills:
    project_path: skills     # null(기본) = 프로젝트 스킬 탐색 안 함
  stages:
    implement:
      skills: [superpowers:test-driven-development, project:tdd-augment-coding]
  ```
- 테스트 방식:
  - 절차: ① T1 픽스처에 `project_path: skills` 를 켜고 통과 확인 ② 같은 이름을 양쪽에
    두고 `HRN-E015` 차단 확인 ③ `project:` 접두사로 해소되는지 확인 ④ `project_path`
    부재/`null` 이면 **T1과 동일하게 차단**(하위호환) 확인 ⑤ 플레이북 §1-4 문서 계약 단언.
  - 기대결과: ①③④⑤ 통과, ② 차단.
  - 테스트 적절성 근토: 해석 경로 변경은 회귀 위험이 크고, 특히 ④(하위호환)가 깨지면
    기존 설치본이 전부 멈춘다 — 분기별 통합 검증이 필요하다.
- 완료 기준: 위 5케이스 통과 + 기존 회귀 FAIL 0 + `shellcheck` 경고 0.
- 리스크/충돌: `validate_config.py` 참조 실존 블록만 수정. T4~T8과 다른 파일·다른 절.

### T3. 도그푸딩 함정 방어 — `realpath` 동일 시 한 곳 취급

- 목적: 소스 레포처럼 프로젝트 루트와 `source_dir` 가 같은 자리인 경우 충돌 오판을 막는다.
- 범위(In/Out): In — 동일 경로 판정 / Out — 실제 도그푸딩 전환(비대상)
- 선행조건/의존성: T2
- 구현 체크리스트:
  - [ ] **먼저 실패를 관찰한다**: 이 레포 컨피그에 `skills.project_path: skills` 를 켜고
        `validate-config` 실행 → `HRN-E015` 가 스킬 수만큼 터지는 것을 기록
  - [ ] `os.path.realpath` 비교로 두 경로가 같으면 충돌 판정을 건너뛴다
  - [ ] 심볼릭 링크로 우회된 경우도 같은 취급이 되는지 확인(`realpath` 를 쓰는 이유)
  - [ ] 회귀 케이스 고정: 동일 경로 → 통과 / 다른 경로 + 같은 이름 → `HRN-E015`
- 테스트 방식:
  - 절차: temp에 소스 트리 복제본을 만들어 `project_path` 를 자기 `skills` 로 지정 → 통과.
    별도로 대상 설치본 + 대상 루트 동명 스킬 → 차단. 두 케이스를 같은 그룹에서 대조.
  - 기대결과: 앞은 통과, 뒤는 차단.
  - 테스트 적절성 근거: 같은 코드 경로가 정반대 결과를 내야 하므로, 대조 케이스가 아니면
    한쪽만 보고 "동작한다"고 오판할 수 있다.
- 완료 기준: 두 케이스 통과 + T2에서 관찰한 8회 터짐이 0회로 바뀜.
- 리스크/충돌: T2와 같은 파일이라 **T2 완료 후 순차 진행**. 병렬 불가.

  ```yaml
    format: "[{type}]: {message}"     # 기본 — 하네스 현행과 동일
    types: [feat, fix, refactor, docs, test, chore, style]
  ```
- 테스트 방식:
  - 절차: ① 기본값 통과 ② `format: "{type}: {message}"` 통과 ③ 치환자 빠진 format 차단
    ④ 빈 `types` 차단 ⑤ 플레이북에 `commit.format` 참조 실존.
  - 기대결과: ①②⑤ 통과, ③④ 차단.
  - 테스트 적절성 근거: 값 내용은 프로젝트 소유라 검사하지 않는다 — **구조만** 본다는
    계약 자체를 케이스로 고정해야 나중에 과잉 검증이 끼어들지 않는다.
- 완료 기준: 5케이스 통과 + 기존 커밋 형식 무변경(기본값 동일).
- 리스크/충돌: 새 최상위 키 + 플레이북 한 줄. 다른 태스크와 독립.
