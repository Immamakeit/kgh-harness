## 3. 검증 결과

### 린트 — 통과

`shellcheck -S warning install/{setup,update,lib.sh,validate-config} tests/install/run-tests.sh`
→ 경고 0, exit 0. `python3 -m py_compile install/validate_config.py` 통과.

### 코드리뷰 — 인라인 수행 (⚠️ 서브에이전트 아님)

**`HRN-W016`** — 세션 지침에 `Do not call the AgentTool unless the user requested it`
이 명시돼 있어 `stages.verify.dispatch: true` 를 쓸 수 없었다. **제3자 리뷰어의
독립성은 확보되지 않았다.** 구간별 `model` 오버라이드도 같은 이유로 미적용이다.

**인라인 리뷰가 실제로 결함 1건을 잡았다:** `skills` 키가 스키마에만 있고 루트
컨피그·배포 템플릿 어디에도 없었다. `preference-options` T5 에서 내가 세운
계약("스키마에만 넣으면 다음 사람이 문서를 보고 손으로 적어야 한다")을 **같은 작업
안에서 어긴 것**이다 — `commit`·`preferences`·`workdocs` 는 전부 지켰는데 `skills` 만
빠졌다. `b14a5d0` 으로 보완하고 단언 2건으로 고정했다.

**뮤테이션 격리 6회** — 각각 겨냥한 케이스만 죽는 것을 확인했다:

| 뮤테이션 | 결과 |
|---|---|
| `realpath` 비교 제거 (T3) | 소스 트리 배치 3케이스만 FAIL(각 7건 E015), 대조 케이스는 PASS 유지 |
| `workdocs.names` 누락 검사 무력화 (T4) | 부분 지정 케이스만 FAIL |
| 플레이북 `workdocs.names` 전량 치환 (T5) | 해당 단언만 FAIL |
| `commit.format` 치환자 검사 무력화 (T7) | 치환자 누락 케이스만 FAIL |
| `.gitignore` 중복 검사 무력화 (T8) | 재설치 케이스만 FAIL |
| `.gitignore` 선택 분기 무력화 (T8) | 거절 케이스만 FAIL |

**정정 2건을 문서에 남겼다** — 숨기지 않는다:

1. **계획 §6 의 가정이 틀렸다.** "`storage.docs` 를 제거하면 기존 설치본이
   `HRN-E004` 로 멈춘다"고 적었으나, 검증기는 **최상위 키만** 미지 여부를 본다.
   하위 키는 애초에 검증 대상이 아니라 제거해도 차단되지 않는다. 안내를 넣는다는
   결론은 유지하되(비대칭은 실재하는 결함이고 최상위 키를 없앨 때 실제로 필요하다)
   근거를 바로잡고 계획서에 정정 문단을 남겼다. 두 사실은 회귀로 고정했다.
2. **T5 커밋 메시지의 뮤테이션 주장이 틀려 amend 했다.** 플레이북의
   `workdocs.names` 를 한 군데만 되돌리면 단언이 죽지 않는다(파일에 4곳이 있고
   `assert_contains` 는 파일 단위다). 이 단언이 막는 것은 "조항이 통째로 사라지는
   것"이지 "일부가 하드코딩으로 되돌아가는 것"이 아니라는 **한계**를 그대로 적었다.

**단언 3건의 범위를 넓혔다.** 전부 "취지가 아니라 어휘·구조를 잡던" 것을 고친 것이다:
`우선|정한다` → `+이긴다` (문서가 "항상 이긴다"로 같은 취지를 말함) ·
`^  docs:` 앵커 추가 (`workdocs:` 가 `docs:` 를 부분포함해 항상 실패) ·
`HRN-E015` 복구 경로 단언이 표의 파이프를 하나만 건너던 것(세 번째 칸이라 둘을 건너야 함).

### 요건 충족 확인 — 통과

- **셸 회귀**: `bash tests/install/run-tests.sh` → **306 PASS / 0 FAIL** (착수 시점 240 → **+66**)
- **컨피그 검증**: 루트·배포 템플릿 둘 다 exit 0
- **실물 시나리오 재현**: 후보 저장소 상황을 그대로 만들어 돌렸다 — git 저장소 대상에
  설치 → 프로젝트 `skills/` 3종(`tdd-augment-coding`·`grill-me`·`design-doc`) 생성 →
  `skills.project_path: skills` + `project:tdd-augment-coding` 참조.
  `design-doc` 이 양쪽에 있어 **`HRN-E015` 로 차단** → `project:design-doc` 으로
  **해소 후 통과(검사 58항목, 오류 0)** → `.gitignore` 에 설치본 7경로 자동 추가 확인.

**미검증으로 남는 것 (숨기지 않는다)**

- **플레이북 §1-4 의 "실행" 쪽은 셸로 검증할 수 없다.** 검증기가 `HRN-E015` 를 내는
  것은 실물로 확인했지만, 오케스트레이터가 실제로 `project:` 접두사를 보고 그
  파일을 읽는지는 문서 계약(조항 실존)으로만 잡혀 있다. `agent-mode` 이후 계속
  받아들이고 있는 한계다.
- **`workdocs.names`·`commit.format` 을 실제로 다른 값으로 바꿔 문서를 생성해 본 적은
  없다.** 검증기가 구조를 받아들이는 것과, 스킬들이 그 값을 실제로 따르는 것은 다르다.
  후자는 이 레포에서 기본값으로만 돌아 검증되지 않았다.
- **여러 프로젝트 스킬 경로**·**`stages` 밖 스킬 참조**(`set-initial`·`branch-strategy`)의
  프로젝트 오버라이드는 비대상이라 손대지 않았다.
- **이 레포를 자기 자신에게 실제로 설치하는 도그푸딩 전환은 하지 않았다.** 근본 원인을
  짚고 코드는 고쳤지만, 전환 자체는 별도 결정이 필요하다(비대상).

## 4. 직접 확인 시나리오

### 시나리오 1 — 프로젝트 스킬을 쓴다 (정상 경로)

```bash
cd /home/ghkim/dev/kgh-dev-harness
T=$(mktemp -d); git -C "$T" init -q
./install/setup "$T" </dev/null >/dev/null 2>&1
mkdir -p "$T/skills/myskill"; printf -- '---\nname: myskill\n---\n' > "$T/skills/myskill/SKILL.md"
python3 - "$T" <<'PY'
import io,sys
p=sys.argv[1]+"/harness.config.yaml"; s=io.open(p,encoding="utf-8").read()
s=s.replace("  project_path: null","  project_path: skills")
s=s.replace("    skills: [superpowers:requesting-code-review]","    skills: [myskill]")
io.open(p,"w",encoding="utf-8").write(s)
PY
"$T/.harness/install/validate-config" "$T/harness.config.yaml" | tail -3; rm -rf "$T"
```

- **기대 결과:** `검증 통과`. `project_path` 를 켜기 전에는 `HRN-E005` 로 막힌다.

### 시나리오 2 — 이름이 겹치면 막고 물어본다 (부정 케이스, 이 작업의 핵심)

위 시나리오에서 `myskill` 대신 `design-doc` 을 만들고 컨피그를 건드리지 않은 채 검증한다.

- **기대 결과:** `HRN-E015` 로 **차단**되고, 에러가 **양쪽 경로를 모두** 지목한다.
  `stages.design.skills` 를 `[project:design-doc]` 으로 바꾸면 통과한다.
  **조용히 한쪽이 가려지는 일은 없다.**

### 시나리오 3 — 소스 레포에서는 충돌로 오판하지 않는다 (부정 케이스)

```bash
{ cat harness.config.yaml; } | sed 's/^  project_path: null/  project_path: skills/' \
  > ./self-check.local.yaml
./install/validate-config ./self-check.local.yaml | tail -3; rm -f ./self-check.local.yaml
```

- **기대 결과:** `검증 통과`. 이 레포는 프로젝트 루트와 `source_dir` 가 같은 자리라
  방어가 없으면 `HRN-E015` 가 **7건** 터진다(뮤테이션으로 실측).

### 시나리오 4 — `.gitignore` 를 거절하면 아무것도 안 바뀐다 (부정 케이스)

git 저장소를 만들어 `./install/setup` 을 **대화형으로** 실행하고, `.gitignore` 질문에
`2` 를 입력한다.

- **기대 결과:** `.gitignore` 가 바이트 단위로 그대로다. 설치 요약에
  `.gitignore : 사용자 선택으로 미적용` 이 남는다.
  (파이프로는 확인할 수 없다 — `ask_choice` 가 비대화형 폴백으로 기본값 1을 탄다.)
