# 설계 — project-conventions (실프로젝트 규약을 가리킬 수 있게)

## 1. 요구사항 / 의도

사용자 발언(원문):

> "빈 프로젝트뿐만 아니라, 실프로젝트에서도 동작하려면 결국 문서위치든 superpower든
> 서브에이전트든 기존 방식을 훑어서 중복인지, 겹칠때 결정해야 하는 부분인지를
> 인지시키고 선택하거나 입력받는 구조여야 하지 않을까?"

**이 요구는 두 조각이고, 이 설계는 앞 조각(A)만 다룬다** (사용자 확정, 순서 1번):

- **A — 가리킬 수 있게 만들기(이번 범위).** 하네스가 프로젝트의 자원(스킬·문서 이름·
  커밋 규약)을 **참조할 수단** 자체가 없다. 대조해서 "프로젝트 것을 쓰자"고 정해도
  반영할 자리가 없다.
- **B — 무엇을 가리킬지 정하게 하기(다음 작업).** 설치 시 기존 프로젝트를 훑어 겹침을
  찾아 사용자에게 고르게 하는 스킬. **B는 A 없이는 결정만 하고 끝난다.**

이 작업이 나온 경로: 실사용 후보 저장소 도입 검토에서 마찰 8건이 보고됐고, 입구
게이트(cost-bottleneck-check)가 실물 대조로 **하네스 자체 결함 3건 + 부분 결함 2건 +
프로젝트/환경 사정 3건**으로 갈랐다. 이 설계는 그중 하네스 쪽 ①②④⑧을 다룬다.

**브레인스토밍 확정 사항 4건 (사용자 선택, 이 설계는 이것을 구현한다):**

| 결정 | 선택 |
|---|---|
| ① 스킬 이름이 양쪽에 있을 때 | **차단하고 되묻는다** (조용히 가려지는 일 없음) |
| ① 프로젝트 스킬 위치를 아는 법 | **컨피그 키로 받는다** |
| ② 작업 문서 | **역할 3개는 고정, 이름·경로 패턴은 컨피그** |
| ④ 커밋 | **템플릿 + 작업유형 목록 둘 다 컨피그** |

## 2. 작업 대상 및 영향도 (실측)

| 대상 | 현재 상태 | 근거 |
|---|---|---|
| 스킬 참조 해석 | `superpowers:` 접두사만 예외. 나머지는 **`source_dir/skills/<이름>/SKILL.md`** 한 곳에서만 찾고 없으면 `HRN-E005` **exit 1** | `install/validate_config.py:232-239` |
| 같은 계약의 문서 사본 | 플레이북이 같은 규칙을 **또** 적어둠 — "하네스 루트 `skills/`" | `core/playbook.md:145-148` (§1-4) |

| 에러코드 여유 | `E001~E014` · `W010~W020` 사용 중 → **다음 자유 번호 `E015`·`W021`** | `PRD.md` §8 |
| 테스트 커버리지 | `install/setup` 은 **빈 temp 디렉터리로만** 검증됨. "대상이 자기 `skills/` 를 가진 경우" **0건** | `tests/install/run-tests.sh` grep 0건 |

### 왜 지금까지 안 드러났나 (근본 원인)

`source_dir` 는 **하네스 설치 루트**다.

- **소스 레포에서 돌 때**: `source_dir` = 레포 루트 → `source_dir/skills/` 가 곧
  프로젝트 루트 `skills/`. **둘이 같은 자리라 구분이 안 된다.**
- **대상에 설치했을 때**: `source_dir` = `<프로젝트>/.harness` → 프로젝트 루트
  `skills/` 와 갈라진다.

`CLAUDE.md` §7은 "v1이 돌면 이 레포 자신에게 설치해서 dogfooding"이라 적었지만, 실제로는
**설치본이 아니라 소스 트리에서 직접** 돌려왔다. 이 분기가 한 번도 실행된 적이 없다.

## 3. 설계안

### 3-1. 스킬 참조 해석 확장 (①)

**새 최상위 키:**

```yaml
skills:
  project_path: null      # null(기본) = 프로젝트 스킬 탐색 안 함
                          # 예: skills · .claude/skills — 프로젝트 루트 기준 상대경로
```

- **기준점**: 프로젝트 루트 = `dirname(harness.config.yaml)`. 새 관례를 발명하지 않는다 —
  검증기가 이미 받는 값에서 유도한다.
- **해석 규칙(플레이북 §1-5)**: 값이 없거나 `null` 이면 **탐색하지 않는다.** "덜 놀라운
  쪽"은 여기서 명확하다 — 기본값을 `skills` 로 두면, `skills/` 디렉터리를 가진 기존
  설치본이 업데이트만 했는데 갑자기 해석 경로가 바뀌고 이름이 겹치면 **검증이 막힌다.**
  켜는 것은 명시적 선택이어야 한다.

**탐색 순서와 판정 (검증기·플레이북 공통):**

| 조건 | 결과 |
|---|---|
| `superpowers:` 접두사 | 기존대로 Skill 도구 (변경 없음) |
| 하네스에만 있음 | 하네스 스킬 |
| 프로젝트에만 있음 | 프로젝트 스킬 |
| **양쪽에 있음** | **`HRN-E015` 차단** — 어느 쪽인지 컨피그에 명시하게 한다 |
| 어느 쪽에도 없음 | 기존 `HRN-E005` (복구 경로에 프로젝트 경로도 함께 안내) |

**명시 방법**: 충돌한 이름에 한해 `project:` 접두사를 쓴다 — `project:design-doc` 이면
프로젝트 것, `design-doc` 이면 하네스 것. 접두사는 **충돌을 푸는 수단**이지 상시
요구사항이 아니다(`superpowers:` 선례와 같은 형태, 새 문법을 발명하지 않는다).

**도그푸딩 함정 — 반드시 막는다**: 이 레포에서는 프로젝트 루트와 `source_dir` 가
**같은 디렉터리**다. 여기서 `project_path: skills` 를 켜면 8종 전부가 "양쪽에 존재"로
판정돼 `HRN-E015` 가 8번 터진다. → **두 경로의 `realpath` 가 같으면 한 곳으로 취급**하고
충돌 판정을 하지 않는다. 이 케이스를 회귀 테스트에 고정한다.

**결합부 2곳을 함께 고친다**: `validate_config.py`(검증)와 `core/playbook.md` §1-4(실행).
한 곳만 고치면 **검증은 통과하는데 실행이 스킬을 못 찾는** 상태가 된다.

### 3-2. 작업 문서 이름·경로 패턴 (②)

**역할 3개(설계·계획·보고)는 고정한다** — 게이트(⑤ 승인 / ⑥ 확정 / ⑩ 판정)와 묶여 있어
개수·의미를 바꾸면 워크플로가 무너진다. **바뀌는 것은 표시 이름과 하위 경로뿐이다.**

```yaml
workdocs:
  path: .harness/work
  layout: "<작업명>/<YYYY-MM-DD>"     # path 아래 하위 경로 패턴
  names:                              # 역할 → 파일명
    design: 설계.md
    plan:   구현계획.md
    report: 구현후보고.md
```

- 치환자는 `storage.path_template` 이 이미 쓰는 것과 **같은 표기**(`<작업명>`·`<YYYY-MM-DD>`)를
  재사용한다. 새 문법을 만들지 않는다.
- **죽은 키 `storage.docs` 를 정리한다.** 읽는 곳이 0곳이므로 스키마에서 제거하고,
  vault 저장 파일명은 `workdocs.names` 를 따르게 한다(같은 문서를 두 이름으로 부르지 않는다).
- 6곳 하드코딩을 **"컨피그가 정한다"는 참조로 교체**한다. 스킬 문서에는 기본값을
  예시로 남기되 "컨피그가 우선"을 명시한다 — `storage.path_template` 이 이미 쓰는 방식.

### 3-3. 커밋 규약 (④)

```yaml
commit:
  format: "[{type}]: {message}"       # 기본 — 하네스 현행과 동일
  types: [feat, fix, refactor, docs, test, chore, style]
```

- 플레이북 §6의 `[작업유형]: 메시지` 조항을 **`commit.format` 참조로 교체**한다.
- 검증기는 `{type}`·`{message}` 치환자 실존과 `types` 가 비어 있지 않은지만 본다.
  값의 내용(어떤 유형이 옳은가)은 프로젝트가 소유한다.
- 기본값이 현행과 같으므로 **기존 설치본의 커밋 형식은 바뀌지 않는다.**

### 3-4. 대상 `.gitignore` 안내 (⑧)

`install/setup` 이 대상 프로젝트에 `.harness/` 설치본을 넣은 직후, `.gitignore` 처리를
**한 번 묻는다.** 이 레포가 자기 `.gitignore` 에 이미 넣어둔 그 목록을 대상에도 제안한다:

```
.harness/ 설치본을 이 저장소 git 에 커밋할까요?
  1) 커밋 안 함 — .gitignore 에 설치본 6종 경로를 추가한다 (추천)
  2) 커밋함 — 아무것도 바꾸지 않는다
번호 입력 [기본: 1]
```

- `install/lib.sh` 의 `ask_choice` 를 쓴다(비대화형 폴백·재질문 내장).
- `/.harness/work/` 는 **제외 목록에 넣지 않는다** — 작업 산출물은 프로젝트 자산이다
  (이 레포가 자기 `.gitignore` 에 남긴 주석과 같은 판단).
- 이미 항목이 있으면 중복 추가하지 않는다.

### 3-5. 에러 계약 (PRD §8 확장)

| 코드 | 의미 | 조치 |
|---|---|---|
| `HRN-E015` | 스킬 이름이 하네스와 프로젝트 양쪽에 존재 (차단) | (a) 컨피그에서 `project:<이름>` 으로 어느 쪽인지 명시 (b) 한쪽 스킬의 이름을 바꾸거나 `skills.project_path` 를 `null` 로 되돌림 |

`W021` 은 이번에 쓰지 않는다 — 이 작업의 실패 유형은 전부 차단성이다.

## 4. 작업 범위 / 비대상

**범위**: §3-1 ~ §3-5 전부 — 스킬 해석 확장(충돌 차단 포함), 문서 이름·경로 패턴,
커밋 규약 컨피그화, 대상 `.gitignore` 안내, `HRN-E015` 신설, 그리고 **"자기 `skills/` 를
가진 대상" 픽스처를 회귀에 추가**.

**비대상:**

- **B(규약 대조 스킬)** — 다음 작업. 사용자 확정 순서(1번: A 먼저). A를 손으로 써보고
  나서 "무엇을 물어야 하는지"가 정확해진다.
- **③ 템플릿 메타데이터 커스터마이즈** — 프로젝트가 요구하는 frontmatter를 읽어내야
  하므로 B의 영역이다. 지금은 vault 경유 오버라이드(obsidian-cli 탐색 순서 ①)만 있다.
- **⑥ 이슈·PR 접합** — `PRD.md` §3 v1 범위 밖. 미구현이지 결함이 아니다.
- **⑦ 서브에이전트 열화** — 이미 `HRN-W016` 으로 정확히 처리·고지된다. 고칠 것이 없다.
- **⑤ `set-initial` 의 기존 문서 인식 개선** — 지금도 0단계에서 git 청결 확인·`.bak` 을
  선행하므로 데이터 손실 위험은 없다. "제안을 아예 안 띄우는" 것은 `bootstrap.prompt: off`
  로 해결된다. 기존 문서를 **읽고 반영**하는 개선은 B와 함께 본다.
- **`stages.<구간>.skills` 밖의 스킬 참조**(`set-initial`·`branch-strategy` 처럼 명시
  지시로 호출되는 것)의 프로젝트 오버라이드 — v1은 컨피그에 적히는 참조만 다룬다.
- **여러 프로젝트 스킬 경로**(`project_paths` 목록) — 브레인스토밍에서 기각(3번 선택지).
  경로가 셋이면 충돌 판정이 복잡해진다. 필요가 확인되면 별도 작업.
- **이 레포를 자기 자신에게 실제로 설치해 도그푸딩하기** — §2가 짚은 근본 원인이지만,
  이번 범위는 "설치본 경로에서도 맞게 동작하도록 코드를 고치는 것"까지다. 실제 설치
  전환은 별도 결정이 필요하다(`.gitignore`·CI·문서가 전부 소스 트리 기준).

## 5. 승인

**확인이 필요한 지점 3가지 — 반려 사유가 될 만한 것만 추린다:**

1. **`project:` 접두사를 충돌 시에만 쓰는 것**이 맞는가, 아니면 프로젝트 스킬은 **항상**
   접두사를 요구하는 편이 명확한가. (이 설계는 전자 — 평소 컨피그가 짧아지고,
   `superpowers:` 와 달리 프로젝트 스킬은 "이 저장소의 기본"이 될 수 있다고 봤다.)
2. **`storage.docs` 키 제거**가 맞는가. 읽는 곳이 0곳이라 제거를 택했지만, 기존 설치본의
   컨피그에 그 키가 있으면 `HRN-E004`(알 수 없는 키)로 **차단된다.** 제거 대신
   "무시되는 키"로 남기는 선택지도 있다.
3. **`.gitignore` 질문을 `install/setup` 에 넣는 것**이 맞는가. 설치 스크립트가 대상
   저장소의 파일을 고치는 첫 사례가 된다(지금까지는 `harness.config.yaml` 생성뿐).

**승인/반려만 답해주시면 됩니다.** 승인 후 ⑥ 계획 단계로 넘어갑니다.
