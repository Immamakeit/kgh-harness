# 설계 — config/ 스키마 신설 + 검증기

## 1. 요구사항 / 의도

PRD §5가 레포 구조에 `config/ # 스키마 + 디폴트값`을 약속했으나 **실재하지 않는다**
(`ls config/` → No such file or directory). PRD §4의 아키텍처 다이어그램에 있는
`Config Loader / Resolver ← 스키마 검증 + 하네스 규격 대조` 역시 실체가 없다.

그 결과 **컨피그의 오타·드리프트를 아무도 잡지 못한다.** 관찰된 실물 2건:

**(a) PRD §7 예시와 실제 컨피그가 갈라졌다.** PRD §7의 스키마 예시에는 `clarify`·
`impact`·`storage` 구간이 아예 없고 `design.skills`에 `brainstorming`이 들어가 있다.
실제 `harness.config.yaml`은 `clarify`가 별도 구간이고 `design.skills`는 `[design-doc]`뿐이다.

**(b) 모델 목록이 하네스 무관해야 할 `core/`에 하드코딩돼 있고, 안내가 거짓이다.**

```
core/playbook.md:21-22
  - `model` 값이 Claude 어댑터 지원 목록(opus, sonnet, haiku, fable)에 없으면:
    `❌ HRN-E001 — … 조치: (a) 컨피그 값 재입력 (b) 어댑터(adapters/claude/) 수정`
```

`adapters/claude/`에는 `hooks/session-start.sh` 하나뿐이다. 고칠 것이 없으므로
복구 경로 (b)는 성립하지 않는다. CLAUDE.md §5의 "모든 에러는 2가지 복구 경로를
제시한다"가 형식만 지켜지고 있다.

이번 작업의 목적은 **컨피그 오류를 결정적으로(instruction이 아니라 코드로) 잡는 것**이다.

### 브레인스토밍에서 확정된 것 (2026-08-20, 인용)

| # | 결정 |
|---|---|
| 1 | 검증 주체는 **둘 다** — 스키마 파일 1개, 소비처 여러 곳 |
| 2 | 디폴트값은 **schema.yaml 안 `default` 필드**로. 별도 defaults.yaml 만들지 않음 |
| 3 | **2단계 분리** — 구조는 `config/`, 허용값(모델·effort)은 어댑터 소유 |
| 4 | 검증 범위는 **구조 + 참조 실존 둘 다** |
| 5 | 형태는 **독립 실행 스크립트 A안** — 네 소비처가 같은 코드를 호출 |

3번은 PRD §8이 이미 명시한 `① 컨피그 스키마 검증 → ② 활성 하네스의 model/effort 규격
대조` 2단계와 일치한다. 새 개념이 아니라 문서에만 있던 것을 실체화한다.

## 2. 작업 대상 및 영향도 (실측)

| 대상 | 현재 상태 | 이번 변경 |
|---|---|---|
| `config/` | **부재** (PRD §5가 약속) | 신설 — `schema.yaml` 1개 |
| `adapters/claude/` | `hooks/session-start.sh` 1개뿐 | `capabilities.yaml` 신설 |
| `install/validate-config` | 부재 | 신설 (실행 파일) |
| `install/setup` | L215~228 종료 요약. 컨피그 검증 없음 | 검증 호출 + 요약에 결과 1줄 |
| `install/update` | 176줄. 컨피그 보존만, 검증 없음 | 검증 호출 |
| `core/playbook.md:21-22` | 모델 목록 하드코딩 | 목록 삭제 → 검증기 호출 지시로 교체 |
| `PRD.md` §7 | 실제 컨피그와 갈라진 예시 30줄 | 예시 삭제 → `config/schema.yaml` 참조로 교체 |
| `tests/install/run-tests.sh` | 설치 스크립트 테스트 존재 | 검증기 케이스 추가 |

**영향 없음을 확인한 것:**
- `harness.config.yaml` — 구조 무변경. `defaults:` 블록은 "사용자 오버라이드" 역할로
  유지된다. 기존 설치본이 깨지지 않는다 (PRD R10 "사용자 컨피그 보존"과 충돌 없음).
- `install/lib.sh` — 기존 YAML 헬퍼(`yaml_top_keys` L183, `read_active_harness` L193,
  `superpowers_skills_in_config` L225)는 **그대로 둔다**. §4 비대상 참조.

**기존 계약과의 정합:**
- `HRN-E004`(스키마 위반) · `HRN-E001`(model) · `HRN-E002`(effort) · `HRN-E005`(필수
  파일 미발견) · `HRN-W014`(superpowers 미설치, 비차단) — **PRD §8의 기존 코드만 쓴다.
  신규 코드를 만들지 않는다.**
- `python3` 부재 시 열화는 `install/setup` L41~46의 기존 `HAVE_PYTHON3` 패턴을 따른다.

## 3. 설계안

### 3-1. 파일 배치

```
config/
└─ schema.yaml                    # 하네스 무관 구조 + 디폴트값. 단일 진실원

adapters/claude/
└─ capabilities.yaml              # Claude 어댑터가 소유하는 허용값

install/
└─ validate-config                # 실행 파일. 위 둘을 읽어 컨피그를 검증
```

`config/`에는 스키마 데이터만 둔다. 검증 코드는 `install/`에 둔다 — PRD §5가 `config/`를
"스키마 + 디폴트값"으로 정의했으므로 그 정체성을 지킨다.

### 3-2. `config/schema.yaml` 형식

자체 미니 형식이다. JSON Schema를 쓰지 않는다 — `jsonschema` 패키지 의존이 생기고,
지금 필요한 표현력(키·타입·허용값·필수여부·기본값·위임)을 훨씬 넘는다.

```yaml
version: 1

top_level:
  active_harness: { type: string, required: true, validated_by: adapter }
  defaults:       { type: map,    required: false }
  workdocs:       { type: map,    required: false }
  storage:        { type: map,    required: false }
  stages:         { type: map,    required: false }

defaults:
  model:  { type: string, default: sonnet, validated_by: adapter }
  effort: { type: string, default: medium, validated_by: adapter }

workdocs:
  path: { type: string, default: .harness/work }

storage:
  enabled:       { type: bool,   default: true }
  tool:          { type: enum,   values: [obsidian-cli], default: obsidian-cli }
  vault_root:    { type: string, default: null, nullable: true }   # null → HRN-W010
  path_template: { type: string, required: false }
  docs:          { type: list,   default: [설계, 구현계획, 구현후보고] }
  approval:      { type: enum,   values: [auto, required], default: auto }

stages:
  known: [entry_gate, clarify, impact, design, plan, implement,
          verify, report, judgment, storage]
  keys:
    model:    { type: string, validated_by: adapter }
    effort:   { type: string, validated_by: adapter }
    skills:   { type: list,   item: skill_ref }        # 참조 실존 검사 대상
    gate:     { type: enum,   values: [required, auto, optional] }
    enabled:  { type: enum,   values: [true, false, conditional] }
    dispatch: { type: bool }
    loop:     { type: enum,   values: [auto, manual] }
```

`validated_by: adapter`는 "구조는 맞지만 값의 옳고 그름은 내가 모른다 — 어댑터에게
물어라"는 표시다. 이것이 2단계 검증의 이음매다.

### 3-3. `adapters/claude/capabilities.yaml`

```yaml
harness: claude
implemented: true                 # false면 HRN-E010 (codex·ollama)

models: [opus, sonnet, haiku, fable]

effort:
  values: [low, medium, high]
  dispatch_supported: false       # Agent 디스패치는 effort 미지원 (플레이북 §1)
```

`dispatch_supported: false`가 중요하다. 지금 이 사실은 플레이북 산문에만 있어서
`effort: high`를 써도 아무 일이 안 일어나고 사용자는 적용된 줄 안다. 데이터로 옮기면
검증기가 **"effort는 현재 무시됩니다"를 매번 말해줄 수 있다.**

### 3-4. 검증 3단계와 에러 매핑

| 단계 | 무엇을 보나 | 실패 시 |
|---|---|---|
| ① 구조 | 알 수 없는 구간·키, 타입 불일치, 허용값 밖 | `HRN-E004` **차단** |
| ② 값 | `validated_by: adapter`인 키를 capabilities와 대조 | `HRN-E001`(model) / `HRN-E002`(effort) **차단** |
| ③ 참조 실존 | `skills[]` 항목이 실제로 있는가 | 아래 분기 |

③의 분기는 **기존 계약을 그대로 따른다** (새로 만들지 않는다):

- `superpowers:` 접두사 → 미설치여도 `HRN-W014` **경고, 비차단**
  (플레이북 §1의 "차단으로 올리지 않는 이유: superpowers 없이도 나머지가 동작한다")
- 그 외(하네스 소유) → `skills/<이름>/SKILL.md` 없으면 `HRN-E005` **차단**

모든 에러는 CLAUDE.md §5대로 **복구 경로 2개**를 함께 낸다. ①은 (a) 컨피그 값 수정
(b) `config/schema.yaml` 수정. ②는 (a) 컨피그 값 수정 (b) 어댑터 지원 목록 갱신 —
이제 (b)가 가리키는 파일이 실재한다.

### 3-5. 소비처 4곳

```
install/setup     → 컨피그 생성/확인 직후 호출. 실패 시 설치를 완료하되 결과를 요약에 명시
install/update    → 갱신 직후 호출. 스키마가 바뀌었는데 컨피그가 옛 형식이면 여기서 잡힌다
core/playbook.md  → 흐름 시작 시 "python3 있으면 install/validate-config를 실행하라"
사용자            → 컨피그를 손으로 고친 뒤 직접 실행
```

네 곳이 **같은 코드**를 부른다. 검증 로직이 한 벌만 존재한다.

플레이북 §1은 현재 "컨피그를 읽고 검증하라"를 모델 지침으로 적어놨다. 이걸 검증기 호출로
바꾸면 흐름 시작 시의 검증이 모델의 성실성이 아니라 종료코드에 달린다.

### 3-6. 인터페이스와 열화

```
사용법: install/validate-config [컨피그경로]
        (생략 시 현재 디렉토리의 harness.config.yaml)

종료코드: 0 = 통과(경고는 있을 수 있음)
          1 = 차단 오류(HRN-Exxx)
          2 = 검증 불가(python3 부재 등) — 호출자는 이를 실패로 취급하지 않는다
```

`python3` 부재 시: `HRN-W015 — python3 미발견으로 컨피그 검증을 건너뜀` 경고 후 종료
코드 2. 흐름을 막지 않는다. `HRN-W010`(vault_root 미지정)·`HRN-W013`·`HRN-W014`가
전부 비차단인 것과 같은 계약이다.

> **신규 코드 1개 필요:** `HRN-W015`. PRD §8 표에 추가한다. 기존 코드로는 "검증 자체를
> 못 했다"를 표현할 수 없다 — W012는 컨피그 부재, W013은 실행체 부재로 의미가 다르다.

`interactive-script` 표준대로 종료 시 요약을 낸다: 검사한 항목 수, 통과/경고/오류 건수,
적용될 디폴트값. **결과를 숨기지 않는다.**

## 4. 작업 범위 / 비대상

### 범위

1. `config/schema.yaml` 신설
2. `adapters/claude/capabilities.yaml` 신설
3. `install/validate-config` 신설 (3단계 검증 + 열화 + 요약)
4. `install/setup`·`install/update`에서 호출
5. `core/playbook.md` §1 — 하드코딩 모델 목록 삭제, 검증기 호출 지시로 교체
6. `PRD.md` — §7 예시를 `config/schema.yaml` 참조로 교체, §8 표에 `HRN-W015` 추가
7. `tests/install/run-tests.sh`에 검증기 테스트 추가 (RED 선행)

### 비대상 — 알면서 안 하는 것

- **`adapters/codex/`·`adapters/ollama/`의 capabilities.yaml을 만들지 않는다.** 스텁조차
  두지 않는다. `implemented: true/false` 필드만 규격으로 정해두고, 파일이 없으면
  기존 `HRN-E010`으로 처리한다. PRD §10 이월 항목을 앞당기지 않는다.
- **`install/lib.sh`의 기존 YAML 헬퍼를 리팩터링하지 않는다.** `yaml_top_keys`(L183)·
  `read_active_harness`(L193)·`superpowers_skills_in_config`(L225)는 검증기와 기능이
  일부 겹치지만 그대로 둔다. **중복이 남는 것을 알면서 두는 것**이며, 이번에 건드리면
  `setup`·`update`의 검증된 동작까지 함께 흔들린다. 후속 후보로 기록한다.
- **흐름 시작 시 자동 실행을 훅으로 강제하지 않는다.** 플레이북이 "실행하라"고 지시할
  뿐이다. `session-start.sh`를 무겁게 만들면 모든 세션 시작이 느려지고, PRD §4가 확정한
  "얇은 훅" 결정과 어긋난다.
- **`harness.config.yaml`의 구조를 바꾸지 않는다.** `defaults:` 블록 유지. 기존 설치본
  호환을 깨지 않는다.
- **PRD §7.1(저장 규칙) 문안은 건드리지 않는다.** §7의 예시 코드블록만 교체한다.
- **모델 목록의 실시간 검증(API 조회)을 하지 않는다.** `capabilities.yaml`은 손으로
  관리하는 정적 목록이다. `HRN-E009`(런타임 모델 거부 → defaults 폴백)가 이미 그 공백을
  덮고 있다.
