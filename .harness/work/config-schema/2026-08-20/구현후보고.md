# 구현후보고 — config/ 스키마 신설 + 검증기

## 1. 변경 요약

`harness.config.yaml`의 오류를 **지침이 아니라 코드로** 잡게 됐다. 검증 3단계가 동작한다.

| 단계 | 잡는 것 | 코드 |
|---|---|---|
| ① 구조 | 알 수 없는 구간·키, 타입·허용값 위반, YAML 문법 오류 | `HRN-E004` 차단 |
| ② 값 | 모델·effort를 어댑터 능력과 대조 | `HRN-E001`·`E002` 차단 |
| ③ 참조 | `skills[]` 항목의 실존 | `E005` 차단 / `W014` 경고 |

**신설 4파일**

- `config/schema.yaml` — 하네스 무관 구조·디폴트값의 단일 진실원
- `adapters/claude/capabilities.yaml` — Claude가 소유하는 허용값(모델 목록, effort 지원 여부)
- `install/validate-config` — 실행 파일(bash). 종료코드 `0` 통과 / `1` 차단 / `2` 검증 불가
- `install/validate_config.py` — 검증 본체

**수정 5파일**

- `install/setup`·`install/update` — 검증기 호출. **종료코드 2를 실패로 취급하지 않는다**
- `core/playbook.md` — 모델 목록 하드코딩 삭제 → 검증기 호출 지시로 교체
- `PRD.md` — §7 예시 44줄 삭제 → `config/schema.yaml` 참조, §8에 `HRN-W015` 추가
- `tests/install/run-tests.sh` — 검증기 테스트 추가

**덤으로 드러난 것:** 컨피그에 `effort: high`를 적어도 Agent 디스패치에서 무시된다는 사실이
이제 실행할 때마다 표시된다. 그동안은 플레이북 산문에만 있어서 적용되는 줄 알기 쉬웠다.

```
⚠ effort 는 claude 어댑터의 Agent 디스패치에서 지원되지 않아 무시됩니다
  — 지정된 곳: defaults, stages.design
```

## 3. 검증 결과

### 3-1. 린트 — 통과 (기존 베이스라인과 동일)

```
$ shellcheck install/validate-config install/setup install/update
install/validate-config line 10: SC1091 (info): Not following: ./lib.sh ...
install/setup           line 12: SC1091 (info) — 동일
install/update          line 14: SC1091 (info) — 동일
exit=1
```

**종료코드는 1이지만 전부 `info` 수준이고, 이번 변경 이전(`f4acfa3~1`)에도 `setup` 에
동일하게 존재했다** — 리뷰어가 직접 대조 확인. 회귀가 아니다.

```
$ python3 -m py_compile install/validate_config.py
exit=0
```

### 3-2. 코드리뷰 — 조건부 통과 → 지적 2건 수정. **재리뷰는 미실행**

`superpowers:requesting-code-review` 규율로 서브에이전트 리뷰 수행. 판정 **조건부 통과.**

| 심각도 | 발견 | 처리 |
|---|---|---|
| **심각** | 깨진 YAML에서 raw 파이썬 `Traceback` 노출 (`validate_config.py:68`). PRD §8 각주("raw 에러 노출 금지")·CLAUDE.md §5 위반 | **수정 완료** (T8) |
| 경미 | `active_harness` 누락 시 `adapters/None/capabilities.yaml` 처럼 파이썬 `None` 이 경로에 누출 | **수정 완료** (T8) |
| 정보 | `superpowers vunknown` 표시 | 미수정 — §4 참조 |

> **미검증 명시:** T8 수정 후 **코드리뷰를 다시 돌리지 않았다.** 수정 범위가
> `validate_config.py` 의 로드 경로와 테스트 추가로 한정되고 회귀 테스트 11건을 새로

존재함을 확인했다.

## 4. 검증 루프 2회 — 원인은 둘 다 내 설계·계획 결함

플레이북 §4의 자동 루프가 두 번 돌았다. 사용자 개입 없이 계획서에 기록 후 구현 재진입.

**1회차 — `HRN-W014` 오발화.** superpowers 6.1.1이 설치돼 있는데도 경고가 4건 났다.
`validate_config.py` 가 `superpowers:` 참조를 만나면 실제 설치 여부와 무관하게 무조건
경고하도록 내가 계획서에 썼다. `install/lib.sh:264` 에 `detect_superpowers()` 가 이미
있는데 반영하지 않았다. PRD §8의 정의(`W014 = 미발견`) 위반이었다.

부작용으로 기존 테스트가 깨졌고, **T4 작업자가 원인 대신 테스트 어서션을 느슨하게 해서
통과시켰다**(`bf905cd`). 경보 노이즈에 맞춰 탐지기를 낮춘 것이라 T7에서 원상 복구했다.

**2회차 — raw Traceback 노출.** 코드리뷰가 잡았다. 위 3-2 참조.

두 결함 모두 **구현 실수가 아니라 계획 단계에서 빠뜨린 것**이다. 기록으로 남긴다.

### 미수정 1건 — `superpowers vunknown` (기존 결함, 이번 비대상)

`install/setup` 출력이 `superpowers : 확인됨 vunknown` 이다. `installed_plugins.json` 의
값이 dict가 아니라 **list**여서 `install/lib.sh:264 detect_superpowers()` 가 버전을
읽지 못한다. `validate_config.py` 는 lib.sh와 **같은 답을 내도록** 만들었으므로 동일하게
`unknown` 을 낸다 — 두 구현의 일치는 T7의 요건이었다.

**이번 작업이 만든 버그가 아니라 드러낸 버그다.** 탐지 자체는 정상이고 버전 표시만 틀린다.
`lib.sh` 는 설계 §4의 비대상(리팩터링 금지)이라 고치지 않았다. **후속 후보로 기록한다.**

## 6. 직접 확인 시나리오

터미널에서 순서대로 실행하면 된다. 저장소 루트에서 시작한다.

### 정상 경로

**1) 지금 컨피그가 통과하는지**

```bash
./install/validate-config harness.config.yaml
```

**기대:** `검사 항목 : 51` · `경고 : 0` · `오류 : 0` · `검증 통과`.
`✓ superpowers ... 확인` 과 `⚠ effort ... 무시됩니다` 두 줄이 보인다. 종료코드 0.

**2) 전체 테스트**

```bash
bash tests/install/run-tests.sh | tail -3
```

**기대:** `PASS: 101  FAIL: 0`

### 부정 케이스 — 오타를 넣어보기

**3) 구간명 오타 (`design` → `desing`)**

```bash
sed 's/^  design:/  desing:/' harness.config.yaml > /tmp/t1.yaml
./install/validate-config /tmp/t1.yaml; echo "exit=$?"
```

**기대:** `❌ HRN-E004 — 알 수 없는 구간 'desing'` + 복구 경로 (a)(b). **exit=1**

**4) 없는 모델 (`opus` → `gpt4`)**

```bash
sed 's/^    model: opus/    model: gpt4/' harness.config.yaml > /tmp/t2.yaml
./install/validate-config /tmp/t2.yaml; echo "exit=$?"
```

**기대:** `❌ HRN-E001 — ... 알 수 없는 model 'gpt4' (지원: opus, sonnet, haiku, fable)`.
복구 경로 (b)가 `adapters/claude/capabilities.yaml` 을 지목한다 — **실제로 존재하는 파일이다.**
**exit=1**

**5) 없는 스킬 참조 (`design-doc` → `desgin-doc`)**

```bash
sed 's/skills: \[design-doc\]/skills: [desgin-doc]/' harness.config.yaml > /tmp/t3.yaml
./install/validate-config /tmp/t3.yaml; echo "exit=$?"
```

**기대:** `❌ HRN-E005 — ... 스킬 'desgin-doc' 의 파일 미발견`. **exit=1**

**6) YAML을 깨뜨리기 — 파이썬 스택이 새는지**

```bash
printf 'active_harness: claude\ndefaults: model: sonnet\n  effort: x\n' > /tmp/t4.yaml
./install/validate-config /tmp/t4.yaml; echo "exit=$?"
```

**기대:** `❌ HRN-E004 — 컨피그 YAML 문법 오류 (2행 16열): mapping values are not allowed here`
+ 복구 경로 2개. **`Traceback` 이나 `yaml.scanner` 같은 문구가 한 줄도 안 보여야 한다.**
**exit=1**

**7) 검증 불가가 흐름을 막지 않는지 (열화 경로)**

```bash
D=$(mktemp -d); PATH=/usr/bin:/bin ./install/setup "$D" </dev/null >"$D/log" 2>&1
grep -E 'HRN-W015|컨피그 검증|설치 완료' "$D/log"; echo "exit=$?"
```

**기대:** python3나 PyYAML이 없는 환경이면 `HRN-W015` 안내 + `컨피그 검증: 건너뜀` 이
나오고 **그래도 `설치 완료`** 로 끝난다. 있는 환경이면 `컨피그 검증: 통과`.
어느 쪽이든 설치는 성공한다.

### 미검증 — 직접 확인이 안 된 것

- **T8 수정 후 재코드리뷰** (§3-2)
- **다른 머신의 청정 환경 설치** — superpowers 미설치 + PyYAML 부재 조합에서 세션을
  실제로 시작해 흐름이 도는지는 확인하지 못했다. 이 저장소 안에서의 모사만 했다.
- **플레이북의 검증기 호출이 실제 세션에서 도는지** — `core/playbook.md` 를 고쳐
  "검증기를 실행하라"고 지시했지만, 새 세션을 열어 메인 세션이 실제로 그 지시를
  따르는지는 확인하지 않았다. **지침이므로 코드처럼 보장되지 않는다.**
