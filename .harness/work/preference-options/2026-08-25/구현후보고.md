다른데, 그 이유를 스키마 주석에 근거로 남겼다 — `project` 쓰기는 대상 저장소 git

**REFACTOR 확정 사항(T7)**: **파일 선택이 먼저고, 표본 3 임계값은 고른 파일 안에서
적용된다.** 프로젝트 표본이 3 미만이면 전역으로 되돌아가지 않고 스킬 기본값을 쓴다.
대안(프로젝트 오버라이드는 임계값 면제)은 소표본 오학습 방지책을 포기하는 동작
변경이라 기각했다 — 사용자 확정.

## 4. 직접 확인 시나리오

### 시나리오 1 — 학습 파일이 `update` 를 살아남는다 (정상 경로)

```bash
cd /home/ghkim/dev/kgh-dev-harness
T=$(mktemp -d)                                  # 임시 대상 프로젝트
./install/setup "$T" </dev/null >/dev/null 2>&1
printf 'version: 1\nstats:\n  set-initial.commit_format:\n    bracket-type: 9\n' \
  > "$T/.harness/preferences.yaml"
"$T/.harness/install/update" </dev/null >/dev/null 2>&1
cat "$T/.harness/preferences.yaml"; rm -rf "$T"
```

- **기대 결과:** `bracket-type: 9` 가 그대로 출력된다. (T6 이전에는 파일 자체가 사라져
  `cat: No such file or directory` 가 났다.)

### 시나리오 2 — 구버전 설치본에 새 키를 안내한다 (정상 경로)

```bash
T=$(mktemp -d); ./install/setup "$T" </dev/null >/dev/null 2>&1
awk '/^preferences:/{s=1;next} s&&/^[[:space:]]/{next} {s=0;print}' \
  "$T/harness.config.yaml" > "$T/c" && mv "$T/c" "$T/harness.config.yaml"
"$T/.harness/install/update" </dev/null 2>&1 | grep "새 설정 키"
grep -c write_to "$T/harness.config.yaml"; rm -rf "$T"
```

- **기대 결과:** `새 설정 키: preferences` 가 출력되고, 마지막 줄은 `0` 이다
  (안내만 하고 **자동으로 추가하지 않는다**).

### 시나리오 3 — 오타값은 차단하지 않고 `global` 로 떨어진다 (부정 케이스)

```bash
{ cat harness.config.yaml; } | sed 's/^  write_to: global/  write_to: proejct/' > /tmp/typo.yaml
./install/validate-config /tmp/typo.yaml >/dev/null 2>&1; echo "exit=$?"
```

- **기대 결과:** `exit=0`. 스키마는 top_level 하위 스칼라 값을 검사하지 않으므로
  **차단하지 않는다** — 대신 스킬이 이 값을 `global` 로 해석한다(스킬 문서 "쓰기 위치" 절).
  이것은 버그가 아니라 `bootstrap.prompt`·`agent_mode` 와 같은 의도된 한계이며,
  회귀 케이스로 고정돼 있다.

### 시나리오 4 — 알 수 없는 최상위 키는 여전히 차단한다 (부정 케이스)

```bash
{ cat harness.config.yaml; printf 'preferences_typo: {}\n'; } > /tmp/badkey.yaml
./install/validate-config /tmp/badkey.yaml 2>&1 | grep HRN-E004; rm -f /tmp/badkey.yaml /tmp/typo.yaml
```

- **기대 결과:** `HRN-E004` + 복구 경로 2개가 출력된다. `preferences` 를 등록했다고
  해서 오타 키까지 열린 것이 아님을 확인한다.
