# 설계 — preference-options (선호 기반 옵션 추천 + as-recommended 모드)

## 1. 요구사항 / 의도

사용자 발언(원문):

> "`추천대로(as-recommended)` 모드를 키고 끌수 있게 해주기. 이게 켜져있으면 주요
> 질문사항들은 그냥, 추천에 맞춰서 주루룩 쳐내서 빨리 될 수 있게
> 하네스에 자체적으로 내 선택도를 기반으로 옵션들을 보여주는 스킬을 둬서 옵션제시시에
> 호출되게 하기"

오케스트레이터가 정리한 이해(인용) — 검토 결과 **골격은 맞다.** 아래 한 가지만 보강한다:

- (원문 그대로) 두 기능은 짝이다 — 선호 스킬이 추천을 만들고 `as-recommended`가 그 추천을
  자동 채택한다. 선호 스킬 없이 모드만 켜면 추천 근거가 매번 달라져 일관성이 없다.
- (원문 그대로) "내 선택도" = 선호 프로필. 과거 선택 경향을 쌓아 순서·기본번호·추천 표시에 반영한다.
- (원문 그대로) `as-recommended`는 자동 채택하되 조용히는 아니다 — 무엇을 왜 골랐는지 표로 남긴다.
- **보강**: "주요 질문사항들"이 자동 채택 대상이 되려면 그 질문이 **번호 선택형**이어야 한다.
  자유서술 질문(선택지를 만들 수 없는 질문, 플레이북 §6·set-initial 질문 계약이 이미
  구분해 둔 예외)은 추천할 옵션 자체가 없으므로 이 기능의 대상이 아니다. 그리고 되돌릴 길이
  없는 동작(§3-5)은 옵션 형태여도 제외한다 — "빠르게"와 "되돌릴 수 없게"는 다른 문제다.

## 3. 설계안

### 3-1. 스킬: `preference-options`

- **역할**: 어떤 스킬/플레이북이든 **번호 선택형 질문을 내기 직전에** 이 스킬을 참조해
  ① 옵션 순서 ② 기본번호 ③ "(추천)" 표시를 그 사람의 선호 프로필 기준으로 정한다.
- **바꾸지 않는 것**: 질문 계약의 4요소(번호·직접 입력·건너뛰기·기본번호) 틀 자체는
  건드리지 않는다. 이 스킬은 그 틀 **안에서** 순서·기본값·표시만 조정한다. "직접 입력"은
  추천 후보에서 항상 제외한다(자유 텍스트를 대신 창작할 수 없다 — set-initial의
  창작 금지 원칙과 동일 논리).
- **입력 계약**: 호출부(질문을 내는 스킬)는 그 질문에 **안정적인 `question_id`**를 붙여야
  한다(예: `set-initial.commit_format`). 표시 문구가 프로젝트마다 달라도 통계는 이 id로
  누적된다 — 라벨 텍스트로 매칭하면 표현이 바뀔 때마다 학습이 끊긴다.
- **v1 통합 대상은 두 곳만**(§3-7) — 모든 스킬을 한 번에 개조하지 않는다.

### 3-2. 선호 프로필 — 저장 위치와 형태

- **경로**: `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/harness/preferences.yaml`
  (환경변수 폴백은 `install/validate_config.py:86`의 `superpowers_state()`와 동일 관례를 재사용 —
  새 관례를 발명하지 않는다).
- **왜 사용자 전역인가(오픈 이슈 2)**: 취향은 프로젝트가 아니라 사람에게 붙는다는
  오케스트레이터 추천에 동의한다. 프로젝트 컨피그(`harness.config.yaml`)에 두면 프로젝트마다
  선호를 새로 쌓아야 하고, 그 컨피그는 설치 대상마다 존재해 값 자체가 흩어진다.
- **왜 레포 트리가 아닌가**: 이 파일은 소스도 배포물도 아니다. `install/setup`·`install/update`는
  이 파일을 **만들지도, 건드리지도, 복사하지도 않는다.** 스킬이 최초로 추천을 계산할 때
  없으면 그 자리에서 만든다(lazy 생성). `.harnessignore`가 관장하는 "레포 → 대상 프로젝트
  복사" 파이프라인 밖에 있으므로 그 목록에 넣을 항목이 아니다 — 이 경계를 README와
  스킬 문서에 명시해 다음 관리자가 "왜 `.harnessignore`에 없지?"라고 헷갈리지 않게 한다.
- **형식**:

```yaml
version: 1
stats:                             # 자동 축적 — 매 선택마다 +1
  set-initial.commit_format:
    conventional-commits: 5
    bracket-type: 1
    skip: 0
pinned:                            # 사용자가 명시적으로 고정한 것 — 통계보다 우선
  set-initial.branch_strategy: feature-branch-pr
updated: 2026-08-25T13:00:00+09:00
```

- **기록하는 것**: `question_id` + 선택된 `option_id`(안정 식별자, 표시 문구 아님) + 시각.
- **기록하지 않는 것(프라이버시)**:
  - **자유서술 답변 원문**(예: set-initial "무엇을 만듭니까" 답) — 프로젝트 고유 정보가
    섞여 있을 수 있다.
  - **"직접 입력"으로 입력한 텍스트 원문** — "직접 입력을 선택했다"는 빈도만 `option_id:
    custom`으로 집계하고, 입력값 자체는 버린다.
  - 프로젝트명·경로 등 식별정보 — `question_id`는 스킬·질문 종류만 가리키고 어느
    프로젝트에서 나왔는지는 남기지 않는다(전역 프로필의 취지에도 맞다 — 프로젝트 무관
    취향이어야 한다).
- **학습 방식(자동+명시, 둘 다)**:
  1. **자동 축적**: 선택할 때마다 `stats[question_id][option_id] += 1`.
  2. **명시적 고정(pinned)**: 사용자가 "이제부터 항상 X로 해줘"처럼 특정 질문에 대해
     명시적으로 지시하면 `pinned`에 기록한다. 통계와 별개 트랙이며 항상 통계를 이긴다.
- **잘못 학습된 자동 축적이 조용히 나쁜 기본값이 되는 위험 — 방지책**:
  1. **임계값**: 같은 `question_id`의 표본이 **3회 미만**이면 통계를 추천에 반영하지
     않는다 — 스킬 자체의 표 기본값을 그대로 쓴다. 임계값은 v1에서 스킬 문서의
     상수(3)로 두고 컨피그로 노출하지 않는다(실사용 데이터 없이 튜닝 노브를 늘리지
     않는다 — YAGNI).
  2. **항상 근거 표시**: 추천에는 반드시 "(과거 N회 중 M회)" 또는 "(이력 부족 — 스킬
     기본값)"을 붙인다. 근거 없는 추천은 없다 — 사용자가 즉시 이상함을 알아챌 수 있게 한다.
  3. **다음 회차에 자기 교정**: 다른 선택을 하면 그 즉시 그 옵션의 카운트가 올라가
     다음 추천에 반영된다. 되돌리는 별도 절차가 필요 없다.
  4. **삭제/초기화 가능**(§3-2 하단).
- **열람·삭제**: 사용자가 "내 선호 프로필 보여줘" 또는 "선호 프로필 초기화해줘"라고
  명시 요청하면 이 스킬이 처리한다.
  - 보기: 파일 경로와 `stats`·`pinned` 내용을 가공 없이 그대로 보여준다.
  - 초기화: **항상 확인을 받는다**(as-recommended가 켜져 있어도 자동 삭제하지 않는다 —
    이유는 §3-5).


### 3-2b. 저장 위치 개정 — 전역 + 프로젝트 오버라이드 (2026-08-25 추가 — **재승인 대상**)

**§3-2는 "사용자 전역 한 곳"을 전제로 쓰였다. 사용자가 그 전제를 바꿨다.**

경위: 오케스트레이터가 전역 단독을 추천했고 사용자가 프로젝트 저장을 골랐다가,
`CLAUDE.md` 와의 소유 영역 겹침·공개 저장소 유출·여러 사람 사용 시 취향 혼재라는 반론을
듣고 **"전역 + 프로젝트 오버라이드 둘 다"** 로 정했다. 오케스트레이터가 "12태스크가 된다"를
근거로 미룬 것에 대해 사용자가 **"그래도 계획 철저하게 세우면 되잖아"** 라고 반박했고,
그 지적이 맞다 — **규모는 거절 사유가 아니다.**

#### 파일 두 개

| 파일 | 역할 |
|---|---|
| `~/.claude/harness/preferences.yaml` | 전역. 사람에게 붙는 취향 |
| `<프로젝트>/.harness/preferences.yaml` | 프로젝트 오버라이드. 없어도 정상 |

#### 병합 규칙 — **질문 단위 덮어쓰기** (2026-08-25 사용자 확정)

프로젝트 파일에 **그 질문의 기록이 하나라도 있으면 전역을 무시**하고 프로젝트만 본다.
**합산하지 않는다.**

```
전역:      commit_format: {conventional: 12, bracket: 3}
프로젝트:  commit_format: {bracket: 2}
→ 추천: bracket   (전역의 conventional 12는 이 질문에서 보지 않는다)
```

합산(`conventional: 12, bracket: 5` → conventional)을 기각한 이유: **프로젝트에서 명시적으로
다르게 고른 선택이 전역 관성에 묻힌다.** 이 기능의 취지에 정면으로 반한다.
가중 합산은 왜 그 추천이 나왔는지 사용자가 재현할 수 없어 기각한다.

> **개정 (2026-08-25, T7 REFACTOR — 승인 원문 유지, 아래만 덧붙임)**
> 위 예시의 숫자가 §3-2의 임계값 규칙(표본 3회 미만이면 통계를 믿지 않고 스킬 기본값)과
> 모순이었다. 프로젝트 표본이 2면 3 미만이므로 추천은 `bracket` 이 아니라 **스킬 기본값**이다.
> **파일 선택이 먼저고 임계값은 고른 파일 안에서 적용된다** — 표본이 모자라도 전역으로
> 되돌아가지 않는다. 예시 숫자를 `bracket: 4` 로 고치고 임계값 미만 케이스를 별도 예시로
> 명문화했다(`skills/preference-options/SKILL.md` 병합 규칙 절).
> 근거: `tests/skills/preference-options/green-results-b.md` REFACTOR 1 — 독립 관측 3건이
> 모두 임계값 쪽 해석을 따랐다. 임계값을 프로젝트 파일에서 면제하는 대안은 소표본
> 오학습 방지책을 포기하는 동작 변경이라 기각했다(사용자 확정).

#### 쓰기 위치 — 컨피그가 정한다 (2026-08-25 사용자 확정)

```yaml
preferences:
  write_to: global        # global(기본) | project
```

읽기(병합)와 쓰기를 분리한다. 기본이 `global` 이라 지금까지 논의한 대로 굴러가고,
프로젝트 특수 취향이 필요한 사람만 바꾼다.

#### 프로젝트 파일이라서 새로 생기는 방어 두 가지

1. **`install/update` 가 지운다.** `harness_copy` 는 `rsync --delete` 로 소스에 없는 파일을
   대상에서 지운다. 지금 보호받는 것은 `/work/` 와 `/.meta` 둘뿐이다(`install/lib.sh:199`).
   **`/preferences.yaml` 을 제외 목록에 추가하지 않으면 업데이트마다 학습이 날아간다.**
2. **대상 저장소 git에 커밋된다.** 프로젝트 안에 있으니 `git add -A` 에 딸려 들어간다.
   선택 이력이 남의 저장소 히스토리에 박힌다 — 스킬이 프로젝트 파일을 **처음 만들 때**
   `.gitignore` 안내를 한 줄 낸다.

#### 계획 구조 — 3국면 (각 국면이 독립 merge 가능)

- **국면 A — 전역 코어**: 스킬 + 전역 프로필. 이것만으로도 값이 있다.
- **국면 B — 프로젝트 오버라이드**: 두 번째 파일 + 병합 규칙 + `write_to` + 위 방어 2개.
- **국면 C — `as-recommended`**: 컨피그 토글 + 플레이북 규칙 + `set-initial` 통합.

B가 막혀도 A와 C는 살아남는다. §3-2의 "사용자 전역" 서술은 **국면 A의 범위**로 읽는다.

**이 절은 원 설계(2026-08-25 승인) 범위 밖이므로 별도 승인을 받는다.**

### 3-3. `as-recommended` 모드 — 컨피그

```yaml
preferences:                      # 선호 기반 추천 (preference-options 스킬)
  as_recommended: false           # true = 번호 선택형 질문을 추천대로 자동 채택
                                   # (⑤ 설계 승인·⑩ 사용자 판정, 되돌릴 길 없는 동작은 제외 — §3-5)
```

- `config/schema.yaml`의 `top_level`에 `preferences: { type: map, required: false }` 한 줄
  추가(§2에서 확인한 대로 미지 최상위 키는 차단되므로 필수).
- **해석 규칙(신설, `bootstrap.prompt`와 방향이 반대임에 주의)**: `as_recommended`는
  **명시적으로 `true`일 때만 켜진다.** 부재·오타·`true` 아닌 모든 값은 `false`로 취급한다.
  `bootstrap.prompt`는 "off가 아니면 ask"(질문 하나 더 하는 정도라 안전 방향이 "묻는다"쪽)였지만,
  `as_recommended`는 **여러 질문을 건너뛰는 강한 동작**이라 안전 방향이 반대다 — 오타의
  결과가 "의도치 않게 자동 진행"이면 피해가 크므로, 애매하면 항상 끈 것으로 본다.
  하위 키는 `bootstrap`과 같은 수준(구조만 검증, 값 해석은 플레이북 규칙)으로 둔다.

### 3-4. `as-recommended` 모드 — 동작

1. 번호 선택형 질문(들)을 내기 직전, `preference-options`로 각 질문의 추천 옵션·근거를 계산한다.
2. **한 구간에 여러 질문이 몰려 있으면**(예: set-initial 3단계 6문항) 하나씩 대화형으로
   묻지 않고 **표 하나로 모아 보여준 뒤 자동 진행**한다 — "주루룩 쳐낸다"는 원문 요구가
   여기서 실현된다.

   ```
   [as-recommended] 아래 항목을 추천대로 자동 선택했습니다.
   | 질문 | 선택 | 근거 |
   |---|---|---|
   | Q1 커밋 메시지 형식 | 2) Conventional Commits | 이력 5/6 |
   | Q2 커밋 단위 | 1) 파일 변경마다 | 이력 부족 — 스킬 기본값 |
   되돌리려면 "Q1 다시"처럼 말씀하시면 그 항목만 다시 묻습니다.
   ```

3. 자유서술 질문(선택지 없음)은 그대로 대화형으로 남는다 — 추천할 옵션이 없다.
4. **자동 채택에서 제외되는 것 — 원칙 하나로 통일**: *"이 저장소의 되돌릴 길 확보 장치
   (git 청결 확인 / `.bak`)가 미치지 않는, 되돌릴 수 없는 동작."* v1에서 이 원칙에 해당하는
   경우는 셋이다.
   - ⑤ 설계 승인 게이트, ⑩ 사용자 판정 게이트 (오픈 이슈 1의 가정) — 워크플로 그 자체의
     인간 개입 지점이다.
   - 선호 프로필 **삭제** 확인 — 이 파일은 레포 밖에 있어 git이나 `.bak`의 보호를 받지
     않는다. 지우면 그걸로 끝이라 유일하게 "되돌릴 길이 아예 없는" 동작이다.
   - (참고) 문서 **덮어쓰기 자체**(set-initial 0단계의 "전부 새로 만든다" 등)는 이 원칙에
     걸리지 않는다 — set-initial이 이미 그 앞에서 git 청결 확인/`.bak` 생성을 **게이트와
     무관하게** 항상 수행하기 때문이다(`skills/set-initial/SKILL.md:28-58`). 되돌릴 길은
     추천 계층이 아니라 각 스킬의 기존 규율이 보장한다 — 이 설계가 그 규율을 약화하지 않는다.
5. `preference-options`로 계산된 근거표는 **판정/승인 게이트 자체에는 절대 쓰이지 않는다**
   (4의 원칙에 이미 포함).

### 3-5. 되돌리기

- 자동 채택은 **조용히 확정되지 않는다** — 근거표가 그 자리에 남는다. 사용자가 특정 항목을
  잘못됐다고 지목하면("Q1 다시", "그건 아니야") 그 항목만 재질문하고, 이미 그 결과에
  의존해 진행된 후속 단계가 있으면 그 단계부터 다시 탄다(일반 대화 중 답을 정정하는 것과
  같은 절차 — 새 메커니즘을 만들지 않는다).
- §3-4-4의 세 예외(승인·판정·프로필 삭제)는 애초에 자동 채택되지 않으므로 "잘못 자동
  진행되어 되돌릴 수 없는" 상황 자체가 구조적으로 생기지 않는다.
- 파일이 이미 쓰인 뒤라면(set-initial 4단계 이후 등) "되돌리기"는 이 기능 고유의 문제가
  아니라 일반적인 재작업 요청과 같다 — set-initial의 되돌릴 길 확보(git/`.bak`)가 그대로
  적용된다.

### 3-6. 에러/경고 계약 (PRD §8 확장 필요 — 구현 시 반영)

| 코드 | 의미 | 조치 |
|---|---|---|
| `HRN-W017` | 선호 프로필 파일 손상/파싱 실패 (비차단 — 프로필 없이 스킬 기본값으로 진행) | (a) `~/.claude/harness/preferences.yaml`을 고치거나 삭제(다음 접근 시 재생성) (b) `preferences.as_recommended`를 꺼서 추천 계층 자체를 우회 |
| `HRN-W018` | 선호 프로필 쓰기 실패, 권한 등 (비차단 — 이번 선택은 학습에 반영 안 됨, 진행은 계속) | (a) `~/.claude/harness/` 권한 확인 (b) `CLAUDE_CONFIG_DIR`로 쓰기 가능한 경로 지정 |

두 코드 모두 **결과를 절대 막지 않는다** — 추천 계층이 실패해도 질문 자체(번호·직접입력·
건너뛰기·기본번호)는 항상 정상 동작해야 한다는 게 이 설계의 안전판이다.

## 4. 작업 범위 / 비대상

**범위**: §3-1 ~ §3-7 전부 — 스킬 신설, 프로필 저장 계약, `as-recommended` 컨피그·해석
규칙, 플레이북·set-initial 통합, 신규 에러코드 2종, 문서화.

**비대상**:

- **`install/lib.sh`의 `ask_choice`(셸 레벨) 프로필 연동.** 설치 스크립트는 프로젝트당
  1회성이라 학습 이득이 낮고, bash에서 YAML/JSON을 읽으려면 `jq`/`python3` 의존을
  새로 지는데(현재 `install/`은 순수 셸 + `validate_config.py`만 python 의존) 이득 대비
  비용이 크다.
- **`cost-bottleneck-check`·`design-doc`·`plan-doc`의 질문 지점 통합.** v1은 set-initial +
  플레이북 총칙 두 곳만(§3-7). design-doc·plan-doc의 승인/범위 게이트 질문은 애초에
  §3-4-4의 자동 채택 제외 대상이라 통합 실익도 적다.
- **⑤ 설계 승인·⑩ 사용자 판정 게이트의 자동화.** 오픈 이슈 1의 가정("아니오")에 따른
  명시적 비대상 — 이 둘이 자동화되면 "승인 전 구현 금지" 규율이 무너진다.
- **프로젝트별(비-전역) 선호 프로필.** v1은 사용자 전역 하나로 고정. 프로젝트 오버레이는
  실사용 후 필요가 확인되면 별도 작업.
- **시간 가중치·최신성 감쇠 등 고급 학습 알고리즘.** v1은 단순 누적 카운트 + 임계값
  하나뿐이다. 데이터가 쌓이기 전에 정교화하는 것은 과설계다.
- **`install/setup`이 선호 프로필을 만들거나 초기화 마법사를 도는 것.** 프로필은
  스킬이 최초 필요 시 lazy 생성한다 — 설치 절차에 넣지 않는다.
- **`ask_choice`를 포함해 이 기능이 다루지 않는 지점에서의 "빠른 진행" 단축키류 UX**
  (예: 전역 "전부 기본값으로" 플래그). `as-recommended`는 프로필 기반 추천을 자동
  채택하는 것이지, 표의 기본값을 무조건 자동 채택하는 별개 기능이 아니다 — 혼동하지 않는다
  (이력이 없으면 결과적으로 표 기본값과 같아질 뿐이다).
