### T2 — `install/lib.sh` : `vault_root_state()`

`detect_obsidian_vaults()` 바로 뒤에 둔다(같은 주제). `yaml_get`(269행) 재사용.

```bash
# storage.vault_root 의 3상태 판정. 표준출력: ok|empty|missing, 그 뒤 탭+경로.
# python 검증기(validate_config.py)와 **상태 이름을 맞춘다** — 같은 것을 두 이름으로
# 부르면 사용자가 보는 메시지가 갈린다.
vault_root_state() {
  local cfg="$1" vr
  vr="$(yaml_get "$cfg" "storage.vault_root" 2>/dev/null || true)"
  case "$vr" in ""|"null"|"~") printf 'empty\t\n'; return 0 ;; esac
  if [ -d "$vr" ]; then printf 'ok\t%s\n' "$vr"; else printf 'missing\t%s\n' "$vr"; fi
}
```

`null`·`~` 을 `empty` 로 접는 이유: YAML 에서 셋 다 "미지정"이고, 템플릿이 실제로
`vault_root: null` 을 배포한다. 문자열 `"null"` 인 디렉터리를 만들어 `ok` 를 받는 황당한
경로를 막는다.

### T3 — `install/validate_config.py` : `W023`

`main()` 의 `②-b workdocs.names` 절 **앞**에 넣는다(storage 블록 검사 자리). `warn()`
헬퍼 재사용 — 출력 형식이 이미 `조치: (a)/(b)` 2경로 계약을 만족한다.

```python
    # ── ②-a storage.vault_root 실존 ───────────────────────────────────────
    # W010(미지정)은 "넣어라", W023(죽은 경로)은 "고쳐라" — 조치가 다르므로 코드를 나눈다.
    # 차단하지 않는다: 볼트가 다른 PC 것이거나 드라이브가 안 붙었을 수 있다(설계 §3-1).
    vr = (cfg.get("storage") or {}).get("vault_root")
    if vr not in (None, "", "~"):
        checked += 1
        if not os.path.isdir(str(vr)):
            warn("W023", f"storage.vault_root 의 경로가 없습니다 ({vr})",
                 "실제 vault 경로로 고친 뒤 install/setup 을 다시 실행하세요",
                 "다른 PC 의 볼트라면 그대로 두세요 — 문서는 로컬에 쌓이고 ⑪ 저장만 미뤄집니다")
```

`checked += 1` 을 `global` 선언 없이 쓸 수 없다 — `main()` 안이라 모듈 전역을 건드리므로
**기존 코드가 하는 방식을 따른다**(파일 내 `checked` 증가 패턴 확인 후 동일하게).

### T4 — `install/setup` §5 재방문

현재 `if [ "$CONFIG_CREATED" -eq 1 ]; then` (225행) 을 다음으로 바꾼다:

```bash
VR_STATE="empty"; VR_PATH=""
if [ -f "$TARGET_CONFIG" ]; then
```

### T7 — `pre-tool-use.sh` (핵심)

`fail_open()` 을 다음으로 교체. 순서가 중요하다 — **로그를 먼저** 쓴다(확실한 경로를
먼저 확보하고, 뒤이은 JSON 출력이 어떻게 해석되든 기록은 남는다).

```bash
GATE_LOG="${PROJECT_DIR}/.harness/gate.log"

# fail-open 기록을 파일에 남긴다. **이 함수의 실패는 조용히 넘긴다** — 로그를 못 써서
# 게이트가 작업을 세우면 fail-open 의 취지를 거스른다. 이 설계가 허용하는 유일한 침묵이고,
# 그래서 침묵을 여기 한 곳에 **가둬** 둔다(설계 §3-3).
log_fail_open() {
  mkdir -p "$(dirname "$GATE_LOG")" 2>/dev/null || return 0
  printf '%s\tW021\tfail-open\t%s\t%s\t%s\n' \
    "$(date -Iseconds 2>/dev/null || date)" "$1" "${2:-?}" "${3:-?}" >> "$GATE_LOG" 2>/dev/null || true
}

fail_open() {
  local why="$1"
  log_fail_open "$why" "${TOOL_NAME:-?}" "${TOOL_TARGET:-?}"

  # stdout JSON — systemMessage(사용자) · additionalContext(모델).
  # permissionDecision 은 **넣지 않는다**: "allow" 는 권한 프롬프트를 건너뛴다. fail-open 의
  # 뜻은 "훅이 없는 것처럼 진행"이지 권한 승격이 아니다(설계 §3-3).
  # 두 필드가 PreToolUse 에서 실제로 표시되는지는 **미확인**이라 로그가 중심이다.
  MSG="⚠️ HRN-W021 — 승인 게이트 판정 전제 미충족(${why}) — 이번 호출은 통과시킵니다. 기록: ${GATE_LOG}"
  if command -v python3 >/dev/null 2>&1; then
    MSG="$MSG" python3 -I -c 'import json,os;m=os.environ["MSG"];print(json.dumps({"systemMessage":m,"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":m}},ensure_ascii=False))' 2>/dev/null || true
  fi

  printf '%s\n' "$MSG" >&2          # 디버그 로깅 사용자용 — 비용 0 이라 남긴다
  printf '   조치: (a) 위 사유를 고친 뒤 재시도 (b) 게이트 없이 진행 — 게이트 고장이 작업을 세우지 않습니다.\n' >&2
  exit 0
}
```

**함정:** `python3` 부재가 `fail_open` 의 흔한 사유인데 JSON 을 python 으로 만든다 —
그 경우 JSON 은 빠지고 **로그와 stderr 만** 남는다. 로그를 중심에 둔 설계가 바로 이걸
견디게 한다. `command -v` 로 감싸는 이유가 이것이고, 주석에 적는다.

`TOOL_NAME`·`TOOL_TARGET` 는 판정 단계에서 이미 뽑는 값이 있으면 재사용하고, 없으면
`?` 로 둔다 — 로그 한 줄 때문에 fail-open 경로에서 JSON 파싱을 새로 하지 않는다.

**§3-5 경로 교정:** 차단 메시지의 `` `.harness/install/approve` `` 를 실제 해석값으로.
`session-start.sh`(22~27행)와 같은 후보 탐색을 쓴다:

