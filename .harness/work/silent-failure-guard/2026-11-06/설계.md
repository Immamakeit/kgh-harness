# 설계 — silent-failure-guard

## 1. 요구사항 / 의도

볼트(`C:\gh-vaults\llm-wiki`)를 대조해 찾은 6건 중 사용자가 **① + ⑥** 을 선택했다.
둘은 같은 병(病)이다 — **실패가 아무에게도 안 보인다.** 볼트 `script-standards.md` 가
*"silent 에러를 엄격히 금지한다"* · *"절대 결과를 숨기지 않는다"* 로 명문화한 조항의
정면 위반이고, 둘 다 **내가** 만들었거나 방치한 것이다.

### ① `vault_root` 가 죽은 경로를 가리켜도 아무것도 안 잡는다

- 컨피그: `/mnt/c/gh-obsidian-vaults/LLM-Wiki` (2026-08-14 지정) — **상위 폴더부터 없다.**
- 실제: `/mnt/c/gh-vaults/llm-wiki` — `obsidian.json` 기준 등록 vault **1개, 이것뿐**.
- 못 잡는 이유 3가지 (실측):
  - `HRN-W010` 은 **빈 값**만 잡는다 → 틀린 값은 통과
  - `config/schema.yaml` 은 `vault_root: { type: string, nullable: true }` → 실존 검사 없음
  - `install/setup` 의 vault 탐지는 `if [ "$CONFIG_CREATED" -eq 1 ]` 블록 안 → **신규 생성
    때만** 돌고 기존 설치는 영구 방치
- 결과: ⑪ 저장이 CLI 폴백(`HRN-W011`)으로 **vault 밖에 유령 트리를 만들며** "저장 완료"를
  보고할 수 있다. 사용자는 볼트를 열어도 문서가 없다.
- 탐지기 자체는 멀쩡하다 — `detect_obsidian_vaults` 를 지금 돌리면
  `llm-wiki<TAB>/mnt/c/gh-vaults/llm-wiki` 를 정확히 반환한다. **호출 조건이 좁은 게 문제다.**

### ⑥ `HRN-W021` fail-open 경고가 아무에게도 안 간다

Claude Code 공식 훅 문서 확인:

> "Claude **never** sees stderr from a hook that exits 0. To read it yourself on events
> such as `PreToolUse`, enable debug logging."

`pre-tool-use.sh` 의 `fail_open()` 은 `printf ... >&2` + `exit 0` 이다. 즉 **디버그 로깅을
켠 사람만** 본다. 게이트가 조용히 고장난 채 모든 호출을 통과시키는 상태가 성립하고,
그 사실이 어디에도 안 남는다. 주석에 `silent 금지` 라고 적어놓고 silent 에러를 만들었다.

**차단 경로는 정상이다** — 같은 문서가 exit 2 에 대해 *"Stderr is the blocking reason, and
Claude receives it as the tool's error"* 로 확인한다. ①(게이트 집행) 자체는 손댈 필요 없다.

## 3. 설계안

### 3-1. `HRN-W023` 의 해석 방향 (PRD §1-5 규약)

> `HRN-W023` — `storage.vault_root` 가 지정됐으나 그 경로가 실존하지 않음 (경고, 비차단)

**방향: 경고, 비차단. 단 ⑪ 저장은 건너뛴다.** 이유를 분리해 적는다 —

- **차단하지 않는 이유:** 볼트는 **다른 PC** 의 것이거나 언마운트된 드라이브일 수 있다
  (사용자 표현: *"이pc에서는"*). 실존하지 않는다고 설치·검증·작업 전체를 세우는 것은
  "가장 덜 놀라운 쪽"이 아니다.
- **저장을 건너뛰는 이유:** 쓰기를 허용하면 vault 밖에 유령 트리가 생기고 "저장됨" 보고가
  거짓이 된다. 이것은 침묵보다 나쁘다 — 사용자가 **확인했다고 믿게** 만든다.
- 즉 `W010`(미지정)과 **같은 처리**로 수렴시킨다: 작업은 계속, 문서는 로컬 보관, 경고.
  코드를 따로 두는 이유는 조치가 다르기 때문이다(W010 = 넣어라 / W023 = 고쳐라).

### 3-2. `install/setup` 의 vault 재방문 — 묻는 조건을 좁게

현재: `CONFIG_CREATED -eq 1` 일 때만 묻는다.
변경: `CONFIG_CREATED -eq 1` **또는** `vault_root_state = missing` 일 때 묻는다.

가드 3개를 같이 넣는다 —

1. **정상이면 안 묻는다** (`ok` · 지금과 동일). 잔소리 금지.
2. **비대화형이면 안 묻는다** — TTY 없으면 `HRN-W023` 경고만 내고 값을 유지한다.
   CI·스크립트 설치를 세우지 않는다(`install/approve` 의 비대화형 계약과 같은 태도).
3. 선택지에 **"그대로 둔다 (다른 PC 의 볼트다)"** 를 넣는다. 이걸 고르면 값 유지 + 경고.
   다중 PC 가 전제인 환경에서 "고치지 않는 것"이 정답인 경우가 실재한다.

`empty`(미지정) 는 지금 동작 유지 — `W010`, 묻지 않는다(이미 신규 생성 경로에서 물었다).

### 3-3. `fail_open()` 3중 출력 — 하나는 확실하고 둘은 최선 노력

| 경로 | 받는 쪽 | 확실성 |
|---|---|---|
| **파일 로그** `${PROJECT_DIR}/.harness/gate.log` | 사용자 (언제든 열어볼 수 있다) | **확실** |
| stdout JSON `systemMessage` | 사용자 (문서: *"Warning message shown to the user"*) | 최선 노력 — PreToolUse 에서 **실측 미확인** |
| stdout JSON `hookSpecificOutput.additionalContext` | 모델 | 최선 노력 — 같음 |
| stderr (유지) | 디버그 로깅 사용자 | 비용 0 이라 남긴다 |

**파일 로그를 설계의 중심에 두는 이유:** 공식 문서가 *"Some events discard it, and each
event's section says so"* 라고만 하고 PreToolUse 절은 `systemMessage` 를 언급하지 않는다.
검증하지 못한 필드에 "silent 금지"를 걸 수 없다 (볼트 `Memory.md` §6: *"추측으로 내용을
채우지 않는다 — 모르면 확인 필요로 명시"*). 로그는 내가 보증할 수 있다.

**`permissionDecision` 은 넣지 않는다.** `"allow"` 는 문서상 *"skips the permission
prompt"* 다 — fail-open 의 뜻은 "**훅이 없는 것처럼** 진행"이지 "권한 프롬프트를 건너뛴다"
가 아니다. 게이트 고장을 권한 승격으로 바꾸면 안전 쪽이 아니라 반대쪽으로 실패한다.
키를 생략해 결정 없음으로 둔다.

로그 형식 (한 줄, 파싱 가능):

```
2026-11-06T14:22:01+09:00	W021	fail-open	<사유>	<도구>	<대상>
```

로그 쓰기 자체가 실패하면(권한 등) **조용히 넘어간다** — 로그 실패가 작업을 세우면
fail-open 의 취지를 거스른다. 이것이 이 설계에서 유일하게 허용하는 침묵이고, 그 이유를
코드 주석에 남긴다.

### 3-4. `install/approve --list` 꼬리 한 줄

`--list` 출력 맨 끝에 `gate.log` 의 fail-open 건수를 한 줄 붙인다:

```
⚠️ fail-open 기록 3건 (최근: 2026-11-06T14:22:01+09:00 — python3 부재)
   전체: .harness/gate.log
```

0건이면 줄을 내지 않는다. 사용자가 게이트 상태를 **묻는 유일한 명령**이 이것이라,
조용한 고장을 깨는 가장 짧은 경로다.

## 4. 작업 범위 / 비대상

**범위:** §2 표의 A~L. 새 HRN 코드는 `W023` **1개만**.

**비대상 (명시):**
- 볼트 대조 결과 **②③④⑤** (MOC 의무 위반 · 승인 원장 이원화 · workflow 문서 역류) —
  사용자가 1번을 골랐다. 별 작업으로 남긴다.
- 차단 경로(exit 2 + stderr) 변경 — 문서상 정상 확인됨.
- `permissionDecision` / `updatedInput` 도입 — §3-3 근거.
- `gate.log` 로테이션·상한 — 한 줄짜리 추가 로그이고 fail-open 은 희귀 사건이다.
  필요해지면 그때 별 작업으로. (지금 넣으면 안 쓰는 코드가 된다)
- 새 컨피그 키 0개 — 로그 경로는 고정이다. 끌 수 있게 만들면 "조용히 하기"를 다시
  선택지로 돌려놓는 셈이다.
- `obsidian-cli` 스킬의 MOC 갱신 단계 (= 대조 결과 ②) — 이 작업에서 손대지 않는다.
