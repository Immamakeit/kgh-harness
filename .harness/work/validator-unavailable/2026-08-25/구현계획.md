### T2. 플레이북 §1-3 분기표 완성

- 범위(In/Out): In — `0`·`1`·`2`·`없음`·**`실행 불가`** 다섯 갈래로 정리 / Out — 검증기 자체 수정
- 선행조건: T1
- 체크리스트:
  - [ ] `검증기가 없으면 HRN-E005` 와 **`있으나 실행 불가면 HRN-W020`** 을 나란히 둔다
  - [ ] `W020` 은 **비차단** 임을 명시 — 보고하고 흐름은 계속한다
  - [ ] `<사유>` 에 관찰한 사실을 적게 한다(§3의 `HRN-W016` 근거 명시 규율과 동일 원칙)
- 작업 방법 예시:
  ```
  검증기가 없으면 `HRN-E005` 를 보고하고 install/update 를 안내한다.
  검증기가 있는데 실행되지 않으면(실행 권한 없음·승인 거부·정책 차단 등)
  `HRN-W020` 을 보고하고 흐름은 계속한다 — 사유 자리에는 관찰한 사실을 적는다.
  ```
- 테스트 방식: 절차 — T4의 계약 단언으로 문장 실존 확인. 기대결과 — 단언 PASS, 문단을
  지우면 FAIL. 근거 — 플레이북은 LLM이 읽는 문서라 행동은 못 잡아도 **사라지는 것은** 잡는다.
- 완료 기준: 다섯 갈래가 모두 문서에 있고 T4가 그것을 고정한다.
- 리스크/충돌: `core/playbook.md` 단독.

### T3. `install/setup`·`install/update` 분기 쪼개기
- 목적: 파일이 있는데 "없음"이라고 말하는 오보를 없앤다.
- 범위(In/Out): In — 존재 여부와 실행 가능 여부를 갈라 `hrn_warn "W020"` / Out — 검증 로직 변경
- 선행조건: T2
- 체크리스트:
  - [ ] `[ -x ]` 단일 분기를 `[ -f ]`(존재) → 실행 가능 여부 순으로 쪼갠다
  - [ ] 존재하지 않으면 기존 메시지 유지(회귀 없음)
  - [ ] 존재하는데 실행 불가면 `hrn_warn "W020"` + 복구 경로 2개
  - [ ] 종료 요약의 `CONFIG_VALID` 문구도 두 경우를 구분
  - [ ] `install/update` 도 같은 형태로 (문구는 update 맥락에 맞게)
- 작업 방법 예시:
  ```bash
  if [ ! -f "${SCRIPT_DIR}/validate-config" ]; then
    CONFIG_VALID="건너뜀 (검증기 없음 — install/update로 최신본을 받으세요)"
  elif [ ! -x "${SCRIPT_DIR}/validate-config" ]; then
    hrn_warn "W020" "컨피그 검증기를 실행할 수 없습니다 (파일은 존재, 사유: 실행 권한 없음)" \
      "chmod +x ${SCRIPT_DIR}/validate-config 후 재실행하세요" \
      "검증 없이 진행 — 컨피그 오타는 해당 구간에 도달할 때 드러납니다"
    CONFIG_VALID="건너뜀 (검증기 실행 불가 — 위 HRN-W020 참조)"
  else
    ... 기존 종료코드 분기 ...
  fi
  ```
- 테스트 방식: 절차 — 실행 비트를 뗀 검증기로 setup 을 돌려 출력·요약을 단언.
  기대결과 — `HRN-W020` 출력, 설치 자체는 rc=0으로 완료(비차단). 근거 — 설치는 되돌리기
  어려운 파일 조작이라 분기 변경은 회귀 테스트가 유일한 안전망이다.
- 완료 기준: 위 단언 PASS + 기존 161 PASS 유지.
- 리스크/충돌: 두 셸 스크립트. `shellcheck -S warning` 경고 0 유지.

### T4. 회귀 테스트
- 목적: 새 계약을 고정한다.
- 범위(In/Out): In — 셸 동작 2케이스 + 플레이북 계약 2단언 / Out — 에이전트 행동 검증(불가)
- 선행조건: T2·T3
- 체크리스트:
  - [ ] 실행 비트 뗀 검증기 → setup 이 `HRN-W020` 출력, rc=0
  - [ ] 검증기 파일 자체가 없음 → 기존 "검증기 없음" 메시지 유지(회귀 방지)
  - [ ] 플레이북에 `W020` 분기 문장 실존
  - [ ] 플레이북에 "비차단" 취지 실존
  - [ ] **root 실행 시 실행 비트 케이스는 건너뛰고 사유를 남긴다** (root는 권한 무시)
- 테스트 방식: 절차 — 전체 스위트 실행 + 뮤테이션(분기를 되돌리면 FAIL 하는지).
  기대결과 — 161 + 신규, FAIL 0. 근거 — 오늘 `agent-mode` 에서 뮤테이션이 "통과만 시키는
  테스트"를 걸러냈다. 같은 방식을 쓴다.
- 완료 기준: FAIL 0 + 뮤테이션에서 신규 케이스만 정확히 죽는다.
- 리스크/충돌: 테스트 파일 단독.
