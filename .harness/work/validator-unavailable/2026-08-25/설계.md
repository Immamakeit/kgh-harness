# 설계 — validator-unavailable (`HRN-W020`)

## 1. 요구사항 / 의도

`agent-mode` 의 T10 실사용 관찰(`tests/playbook/agent-mode/observation-single.md`)에서
드러난 결함이다. 관찰된 세션이 이렇게 보고했다:

> ⚠️ **HRN-W015 — 컨피그 검증 불가.** `.harness/install/validate-config` 실행이 이 세션의
> 권한 정책에 막혔습니다(파일 자체는 존재).

**코드 선택이 계약과 어긋난다.** `HRN-W015` 는 "python3·PyYAML 미충족"이고, 플레이북은
"검증기가 **없으면** `HRN-E005`" 만 정한다. **파일은 있는데 실행 자체가 안 되는 경우**에
해당하는 칸이 계약에 없다. 에이전트는 가장 가까운 코드를 골라 비차단으로 진행했고 그
판단 자체는 합리적이었지만, 잘못된 복구 경로("python3를 설치하세요")를 받게 된다.

**이 관찰이 없었으면 드러나지 않았을 결함이다.**

## 2. 작업 대상 및 영향도 (실측)

| 위치 | 현재 상태 | 문제 |
|---|---|---|
| `core/playbook.md` §1-3 | 분기가 `0`·`1`·`2`·"검증기가 없으면 E005" 넷뿐 | **실행 불가 칸이 없다** — 종료코드가 아예 안 나오는 경우 |
| `install/setup:323` | `if [ -x "${SCRIPT_DIR}/validate-config" ]` … `else CONFIG_VALID="건너뜀 (검증기 없음 …)"` | 파일이 **멀쩡히 있는데** "없음"이라고 보고한다 — 오보 |
| `install/update:167` | 같은 형태 (`"건너뜀 (검증기 없음 — 소스가 오래됐을 수 있음)"`) | 〃 |
| `PRD.md` §8 | `W020` 미등재 | 대장 규칙(§8, T0에서 신설)상 **코드보다 등재가 먼저**다 |
| `install/validate-config` | 스스로는 이 상황을 보고할 수 없다 | 실행이 안 되는데 자기 입으로 말할 수 없다 — **호출자 책임**이다 |

원인은 여러 갈래인데(실행 권한 없음·승인 거부·정책 차단) **복구 방법은 한 갈래**다 —
"실행할 수 있게 해준 뒤 재시도". 그래서 코드를 여러 개로 쪼개지 않는다.

## 3. 설계안

### 3-1. 신규 `HRN-W020` (비차단)

```
⚠️ HRN-W020 — 컨피그 검증기를 실행할 수 없습니다 (파일은 존재, 사유: <실측 사유>)
  조치 1: 실행 권한을 부여하거나(chmod +x) 해당 명령 실행을 허용한 뒤 재검증
  조치 2: 검증 없이 진행 — 컨피그 오타는 해당 구간에 도달할 때 드러납니다
```

- **W계열(비차단)인 이유**: 검증은 선택이고 흐름은 계속 굴러가야 한다. 검증기를 못 돌린
  것으로 작업 전체를 막는 것은 과잉이다. `W015` 와 같은 층위다.
- **기존 코드에 흡수하지 않는 이유**: `W015` 의 복구 경로는 "python3/PyYAML 설치"다.
  권한이 막힌 사람에게 이걸 주면 **엉뚱한 곳을 고치게 만든다.** HRN 체계의 존재 이유가
  정확한 복구 경로인데 그것을 배신한다.
- `<실측 사유>` 는 지어내지 않는다 — 실행 비트 부재/거부 응답 등 **관찰한 사실**을 적는다
  (플레이북 §3의 `HRN-W016` 근거 명시 규율과 같은 원칙).

### 3-2. 손댈 곳 4군데

1. **`PRD.md` §8에 먼저 등재** — T0에서 만든 대장 규칙("코드보다 표에 먼저 등재")을
   우리가 먼저 지킨다. 구현 완료 후 `(예정)` 표기를 지운다.
2. **플레이북 §1-3 분기표 완성** — 빠진 칸을 채운다. 이것이 근본 원인이다.
   `검증기 없음 → E005` 와 `있으나 실행 불가 → W020` 을 나란히 둔다.
3. **`install/setup`·`install/update`** — `[ -x ]` 한 줄로 "없음"과 "실행 불가"를 뭉뚱그리는
   분기를 **`[ -f ]` 로 존재를 먼저 보고** 그다음 실행 가능 여부를 보게 쪼갠다.
   존재하지 않으면 기존 메시지, 존재하는데 실행 불가면 `hrn_warn "W020"`.
4. **회귀 테스트** — 실행 비트를 뗀 검증기로 setup 을 돌려 `W020` 이 나오는지,
   그리고 플레이북 분기표에 그 칸이 실존하는지(`agent-mode` T7 계약 테스트 방식).

### 3-3. RED→GREEN→REFACTOR 적용 여부

**적용하지 않는다.** `CLAUDE.md` §4의 규율은 **스킬**에 대한 것이고, 이번 작업은 신규
스킬이 아니라 **에러 계약 확장 + 셸 분기 수정**이다. 대신 §3-2의 4번 회귀 테스트가
그 자리를 대신한다 — 실행 비트를 떼고 실제로 `W020` 이 나오는지 실물로 확인한다.

## 4. 작업 범위 / 비대상

- **범위:** §3-1 ~ §3-2 전부.
- **비대상:**
  - **원인별 코드 세분화** (권한 없음 / 승인 거부 / 정책 차단을 각각 다른 코드로) —
    복구 방법이 한 갈래라 쪼갤 값이 없다. 코드 인플레만 부른다.
  - **`install/validate-config` 자신의 수정** — 실행이 안 되는 상황을 스스로 보고할 수
    없다. 호출자 책임이다.
  - **`HRN-E003` 정리** (PRD에 선언됐으나 구현체에 트리거 경로가 없음, T0 감사에서 발견) —
    반대 방향의 불일치라 이번 건과 성격이 다르다. 별도 작업으로 남긴다.
  - **에이전트가 실제로 이 코드를 골라 쓰는지의 행동 검증** — `agent-mode` 와 같은 한계다.
    문서 계약 테스트로 규칙 실존만 고정한다.
  - **`branch-strategy`·`preference-options` 의 코드 등재** — 각자 자기 차례에 한다.
